Certify store identities over numeral expressions of one value

Pull request levnach/z3#88 into master · state OPEN · 2026-11-07T08:36:07Z · loop iteration 88

This pull request is open and not merged. The change under review is commit 8f5883c92.

In one paragraph

This PR lets Lean check rewrite steps where Z3 applied a store identity to an index or value written as a numeral expression. Z3's rewriter compares such indices by value. It treats (* 1 2) and (- 3 1) as the same index, 2. The reconstructor compared them as written. So the simp call in the generated lemma never fired, and grind failed. Now each numeral expression first gets a small proved fact, such as 1 * 2 = 2. After that, the store identities match, as they did for Z3. Valid certificates from such inputs now become Lean-checked refutations. Every new fact is proved inside Lean, so nothing new is trusted.

Background

Before this PR, the pipeline already certified many array inputs. These included chains of stores, selects, and constant arrays over Int and Real sorts. It recognized a store identity only when both indices were the very same term. An index such as (/ 2 2) next to 1.0 broke that check. The project plan listed this as still open after iteration 86, as "unnormalized numeral indices". The work serves milestone 4, "Broader theories and integration", where arrays are one of the planned extensions.

What changed

  • You can now get a Lean proof for a rewrite step that collapses two stores at indices like (* 1 2) and (- 3 1).
  • A value read back and stored at an equal index, as in (store a (/ 2 2) (select a 1.0)), now folds to a in Lean too.
  • A constant stored into its own constant array is recognized even when written as (+ 1 0).
  • Each numeral expression is replaced by its value first, using a fact that grind proves, applied in pre-order.
  • Division by zero is never evaluated, because Z3 leaves it uninterpreted while Lean defines x / 0 = 0.
  • Six new documented inputs, a test that removes the new facts, and a random generator option now guard this behavior.

An analogy helps here. Picture a librarian who files books on shelf "1×2" and shelf "3−1" as two different shelves. Z3 knows both labels mean shelf 2. The new facts tell Lean the same thing before it starts sorting.

The new logic lives in the reconstructor, proof_to_lean.py. The tests sit in the array test module. The plan document gained a dated note that closes the open item. A second commit, made after review, caches each expression's value and stops early on non-numeral arguments.

Worked example

This input is store_over_a_store_at_products, one of the six new test inputs. All three pieces below come from real runs of the pipeline for this report.

(a) The input

(set-logic ALL)
(declare-const a (Array Int Int))
(declare-const b (Array Int Int))
(declare-const v Int)
(declare-const w Int)
(declare-const p Bool)
(assert (or p (= b (store (store a (* 1 2) v) (- 3 1) w))))
(assert (not p))
(assert (not (= b (store a 2 w))))
(check-sat)

Writing w at index 2 overwrites v at index 2, so b must equal (store a 2 w). The last assertion denies that.

(b) Before

The pre-change exporter produced a certificate, and the pre-change reconstructor wrote a Lean file without complaint. Lean then rejected the rewrite step. The first error line, and the hypothesis grind got stuck on, were:

example.lean:95:33: error: `grind` failed
...
left : _atoms 0 ∨ term_1 _atoms _vars _m = _store (_store (term_2 _atoms _vars _m) 2 (_vars 0)) 2 (_vars 1)

Grind does see both indices as 2, but it has no rule that collapses two stores at one index.

(c) After

Lean accepted the new file. The check script printed "Lean checks passed."

The two indices are kept exactly as written, 1 * 2 and 3 - 1, and the second store sits on top of the first.

private theorem _store_store {I E : Type} (a : I -> E) (i : I) (v w : E) :
    _store (_store a i v) i w = _store a i w := by
  funext _j
  by_cases _h : _j = i <;> simp [_store, _h]

This is the store identity itself, proved in Lean. It only applies when both indices are syntactically the same i.

Review

The reviewer approved the PR. There were no blocker, major, or minor findings. Two small "nit" findings came up.

Nit 1, repeated work. The reviewer built indices that double at each level, (+ t t) nested 16 deep. The value function had no memory, so it recomputed shared parts again and again. Reconstruction took 0.62 seconds. This mattered because certificates share subterms heavily, and repeated work can grow fast. The fix caches each node's value and stops at the first argument that is not a numeral. Time dropped to 0.35 seconds. The rest is the existing rendering of a large output.

Nit 2, extra facts. The reviewer noticed that every numeral expression in a step gets a fact, not only store indices and values. An unrelated (+ 1.0 1.0) in an arithmetic atom also gets one. This is harmless, because each fact is a closed identity proved by grind. The facts appear only in the last fallback. The author left it unchanged. Limiting the facts would need more code and could miss a needed fact.

Risks and open questions

  • If grind ever failed to prove one numeral fact, that fallback would fail where it once succeeded. No such failure appeared in the tests or the 673 sweep certificates.
  • The store-identity check now says yes more often. A step that fails anyway costs one more attempt. This affects time, not soundness.
  • Comparing an if-then-else term of store chains with a store chain over constant arrays still fails Lean. This is Real/Int seed 102, and it fails with plain numerals too.
  • Two helpers that state read facts still stop at stores by exact identity. With value-equal indices they state extra facts. This is sound but not minimal.

What comes next

The reviewer and the author both name the seed 102 case as the next candidate. The proposed fix adds a converse fact for each branch of the if-then-else term. Making the read facts minimal under value-equal indices is a smaller follow-up.

Glossary

array
A map from indices to values. (Array Int Int) maps Int indices to Int values.
Boolean
A value that is either true or false, of sort Bool.
certificate
The proof record Z3 exports for an unsat result. The reconstructor reads it.
constant array
An array with the same value at every index, such as ((as const (Array Int Int)) 1).
grind
A Lean tactic that combines equality reasoning, arithmetic, and case splits to close a goal.
if-then-else term (ite)
A term that picks one of two values using a Boolean condition: (ite c x y).
index
The position at which an array is read or written.
lemma
A small proved statement used inside a larger proof. Each rewrite step becomes one lemma in the generated file.
numeral
A number written directly, such as 2 or 1.0.
numeral expression
Numerals combined by + - * / or to_real, such as (* 1 2). Its value is a fixed number.
pre-order rewriting
Rewriting a term before its subterms. In simp, ↓ marks a rule for this. It stops an inner rewrite from spoiling a match on the outer term.
reconstructor
The program that turns a certificate into a Lean file.
refutation
A proof that a set of assertions implies False.
rewrite step
A proof step where a term is replaced by an equal, simpler term.
rewriter
The part of Z3 that simplifies terms by fixed rules, such as evaluating (* 1 2) to 2.
seed
A number that fixes a random generator's choices, so a random input can be recreated.
select
Reading an array. (select a i) is the value of a at index i.
simp
A Lean tactic that rewrites a goal with a given list of equations.
sort
The type of a term, such as Int, Real, Bool, or (Array Int Int).
store
Writing an array. (store a i v) is a copy of a with value v at index i.
store identity
An equation that removes a redundant store. Example: (store (store a i v) i w) equals (store a i w).
subterm
A term that appears inside a larger term. (+ 1 1) is a subterm of (- (+ 1 1) 0).
tactic
A command that tells Lean how to build part of a proof.
