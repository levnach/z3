Ignore trimmer deletions of clauses the proof never added

Pull request #36 on levnach/z3 · OPEN · opened 2026-10-24T05:03:06Z · loop iteration 36

This pull request is not merged. It targets master and contains one commit, 2e65224, on top of base commit 3f0a614.

In one paragraph

The native proof trimmer cuts a clause log down to the dependency core the refutation needs. On one QF_LRA input from the z3test corpus it crashed with an internal error. It had recorded deletions of clauses it never added, and its backward pass revived them. A revived clause took part in unit propagation but was registered nowhere, so the core pointed at a clause the proof never had. Now the trimmer ignores deletions logged after its conflict and records one only when it held a copy of the clause. The failing input now trims, exports in seconds, and its Lean certificate checks with the standard axioms. The trimmer stays an untrusted hint: the Python replay re-derives every retained step by RUP, and Lean checks the result.

Background

The pipeline already exported QF_LRA clause logs and proved them in Lean, including the large hard16 input fixed on 2026-10-22. Since then a trimmer failure makes the exporter replay the untrimmed log instead of aborting. For the LassoRanker file this fallback produced Lean text too large to check within the corpus scan's time budget, so the file stayed untriaged. The work serves milestone 3, equality and linear arithmetic, and the corpus scan that finds inputs the pipeline cannot yet certify.

What changed

Think of the trimmer as an editor marking which pages of a proof are needed. It used to note pages torn out after the proof had ended and paste them back in later. Now it records a removal only for a page that was really in the binder.

  • Deletions after the conflict are ignored. The trimmer finds its conflict as soon as the clause set becomes inconsistent, often thousands of steps before Z3 logs the empty clause.
  • A deletion is recorded only when a copy was held. The new helper detach looks for a clause object or an attached binary clause in its watch list. A never-added clause or a unit clause leaves nothing to revive.
  • A C++ unit test pins both placements of the never-added clause (or (not b) c d), deleted after the conflict and before it. The old trimmer fails it with the production error.
  • A Python test runs the same logs through the real executable with warnings turned into errors, so a silent fallback cannot hide the defect.
  • The plan document gains a dated section on the defect and the fix.

Review

Verdict: APPROVE, with no blocker, major, or minor findings and two nits. The reviewer rebuilt the tree, reran the suites, and read the solver code to confirm that reviving a unit was a no-op.

  1. Nit, the test depends on propagation order. It only catches the old bug if the revived phantom clause implies d before the registered binary clause does. A change to watch-list order could let the old code pass, silently weakening the guard. Not changed: without the third clause the unit c is no longer derivable, so any order-independent variant would be an invalid log. The Python test is a second guard.
  2. Nit, documentation order. The new dated section sits between a 2026-10-19 entry and the 2026-10-22 entry. Not changed: it sits directly before the earlier trimmer note, which keeps the two adjacent.

Risks and open questions

  • Ignoring later deletions assumes the conflict is the proof's end. A clause set inconsistent at one step stays inconsistent later, so the earlier core is a valid proof. A wrong core would be rejected by the Python replay and by Lean.
  • Unit deletions are no longer recorded. Reviving one was a no-op, so output for logs without phantom clauses is unchanged, as hard16 confirms.
  • A theory lemma deleted under other literals than the trimmer assumed now stays attached. A later step may cite it, which is a valid earlier clause.
  • The binary-watch check scans one watch list per binary deletion. Z3 does not log binary deletions today.
  • CI results are unknown at the time of this report.

What comes next

  • Mark core membership per clause id rather than per literal set, so the trimmer emits only the final clause's closure instead of every logged copy.
  • Scan the larger LassoRanker files skipped by size, and the clocksynchro_3clocks input whose Lean check times out.

Glossary

assertion
A formula the input declares to be true. In SMT-LIB it is written (assert ...).
axiom
A statement a proof checker accepts without proof. Lean's standard ones are propext, Classical.choice, and Quot.sound. A certificate that depends only on these trusts nothing about the solver.
binary clause
A clause with exactly two literals, such as (or (not x) d). Solvers store these directly in watch lists instead of as clause objects.
Boolean
A value that is either true or false. The sort Bool.
certificate
A machine-checkable record of why a result holds. Here, the proof steps exported from Z3 and the Lean file built from them.
clause
A disjunction of literals, for example (or (not b) c x). It is satisfied when at least one literal is true.
clause log
Z3's running record of every clause it added, inferred, or deleted while solving, written as assume, infer, and del lines.
conflict
The moment unit propagation finds a clause whose literals are all false. The clause set is then inconsistent.
dependency core
The subset of logged steps that the final empty clause actually depends on. Everything outside the core can be dropped without weakening the proof.
linear arithmetic
Reasoning about sums of variables times constants compared with constants, such as 2x + y ≤ 5. No products of variables.
literal
A Boolean variable or its negation, such as c or (not c).
proof trimmer
The C++ component in Z3 that replays a clause log by unit propagation, finds the conflict, and computes the dependency core by probing which earlier clauses each step needs. Its output is a hint that is checked again later.
QF_LRA
The SMT-LIB logic of quantifier-free linear real arithmetic. Formulas mix Boolean structure with linear constraints over real numbers.
refutation
A proof that a set of assertions is inconsistent, ending in the empty clause or in False.
resolution
The rule that combines two clauses sharing a literal and its negation into one clause without them. Unit resolution is the case where one of the two clauses is a single literal.
RUP (reverse unit propagation)
A way to check an inferred clause: assume all its literals are false and confirm that unit propagation over the listed premises reaches a conflict.
SMT-LIB
The standard text format for SMT problems, with commands such as declare-const, assert, and check-sat. The input in the worked example is written in it.
sort
The type of a value, such as Int, Real, or Bool.
theory lemma
A clause that a theory solver, for example the arithmetic solver, proves valid on its own and hands to the Boolean search.
unit clause
A clause with a single literal. Adding it fixes that literal's value for the rest of the search.
unit propagation
Repeatedly finding a clause with all but one literal false and setting the remaining literal true, until nothing changes or a conflict appears.
watch list
The per-literal index a solver keeps of the clauses that must be revisited when that literal becomes false. A binary clause is attached by placing it in the watch lists of its two literals.
