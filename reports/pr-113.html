Bind proof steps under hypotheses inside their one consumer in Lean

Pull request levnach/z3#113 · OPEN · opened 2026-11-11T02:54:15Z · loop iteration 112

This pull request is open and not merged. The change under review is commit 2761034. It contains two commits on top of the base 46bd831.

In one paragraph

Z3 turns a long refutation into many small lemmas, and the reconstructor writes each one as a Lean theorem. A proof step that depends on a hypothesis used to be written as a function of that hypothesis. Every step that used it had to repeat the hypothesis and re-apply the function. This PR places such a step inside the one step that uses it, as a let binding with no extra binders. Lemmas also receive the interpretation as an implicit argument. The proof itself is unchanged. Only the layout of the Lean text changes, and the text gets much smaller. That matters because Lean's memory during elaboration grows with the text. The SMT-LIB difference logic benchmark plan-21 used to exhaust the 8 GB limit. It now passes the Lean kernel check.

Background

Before this PR, the pipeline already produced correct certificates for this fragment. Small inputs passed. But large search-style refutations, made of many unit resolutions under hypotheses, produced huge Lean files. QF_IDL plan-21 had failed with a kernel memory error since iteration 096. The QF_IDL DTP_k2_n35 benchmark failed the same way. This work serves milestone 3, equality and linear arithmetic, at the size of real SMT-LIB benchmarks.

What changed

  • A proof step under hypotheses that exactly one other step uses is now written inside that step, so the hypotheses are not restated and nothing is re-applied.
  • Each outlined lemma now states its own step directly, as a fun over its hypotheses, instead of copying its statement into a second binding.
  • Lemmas take the interpretation implicitly, so importing a lemma is now just proof_step_N _inputs.
  • The reconstructor now stops with a clear error if an interpretation binder cannot be made implicit, instead of writing a file Lean would reject.
  • New tests cover the nested layout, the depth limit of 32 nested steps, and the full plan-21 benchmark in the slow test tier.

Think of a recipe card that says "see step 4" for a sub-recipe used only once. Printing the sub-recipe right inside the step saves the cross-reference and the repeated list of ingredients.

Review

The reviewer approved with no blocker, major or minor findings. There were three nits, and all were fixed.

SeverityFindingResolution
nitBinders with parenthesised types stay explicit silentlyfixed: generation now fails
nitNo test reaches the nesting depth limitfixed: new test
nitGenerator docstring quoted the wrong seedfixed

The silent binder. The reviewer read the pattern that turns interpretation binders into implicit ones. It only matches types without parentheses. A future binder such as (_f : (Nat -> Int) -> Int) would stay explicit. Every lemma import would then have a wrong argument, and Lean would reject the certificate. Nothing current is affected. The fix makes the reconstructor stop with a clear error, so a future problem shows up at once.

The untested limit. The reviewer tried depth limits of 1, 4, 32 and a million. On the test inputs, 32 never made a difference. So the fallback path was never exercised in Lean. A new test sets the limit to 1 and checks that Lean still accepts the file.

The docstring. The generator's comment gave figures for seed 1, but the test uses seed 2. It now gives both.

The reviewer also suggested recording plan-21's peak memory whenever the slow tier runs. That was left as a follow-up.

Risks and open questions

  • The trust boundary is unchanged. The theorem statement is byte-identical between base and new output on every compared input.
  • plan-21 peaks at about 7.5 GB against an 8 GB cap. A Lean upgrade or a change in Z3's proof could push it over again.
  • Lemmas rely on Lean inferring the implicit interpretation from the type of _inputs. The main theorem passes it explicitly.
  • The local gate and CI results are not known at the time of writing.

What comes next

  • DTP_k2_n35 still fails. It now gets through 11,991 of 17,084 lemmas, up from 7,921.
  • The remaining bulk is lemma imports, Or.elim resolution terms, and re-applied shared steps.
  • The QF_AX file swap_t2_np_sf_ai_00009_002 still fails.
  • Recording plan-21's peak memory would catch a regression early.

Glossary

binder
A named parameter with a type, such as (_hyp41 : formula_41), introduced by a function or theorem.
certificate
A file of proof evidence that an independent checker can verify without trusting the solver.
clause
A disjunction of literals, such as (or p (not q)). It is true when at least one literal is true.
difference logic
Integer arithmetic where every atom bounds a difference of two variables, such as a - b >= 2. Its SMT-LIB name is QF_IDL.
elaboration
Lean's step that turns written text into fully explicit terms, filling in implicit arguments and checking types.
hypothesis
A fact assumed temporarily inside a proof. A later lemma step discharges it, for example by concluding its negation.
implicit argument
An argument written in braces, such as {_atoms}, that Lean fills in itself from the types of the other arguments.
interpretation
An assignment of meanings to the symbols of a formula. Here it is the functions _atoms and _vars that give each Boolean atom and integer variable a value.
kernel
The small trusted core of Lean that does the final type check of every proof.
lemma
A proved statement used inside a larger proof. In Z3's proofs, the lemma rule also turns a derivation of False from a hypothesis into the hypothesis's negation.
let binding
A local name for a value, written let x := v. It can be used in the lines that follow.
literal
An atom or its negation, such as p or (not p).
proof step
One inference in a proof, deriving a conclusion from earlier steps by one rule.
refutation
A proof that a set of formulas leads to False, so they cannot all be true together.
theorem
A named statement in Lean together with its proof. Lean checks the proof when the file is compiled.
unit resolution
The rule that removes false literals from a clause. From (or p q) and (not p) it derives q.
