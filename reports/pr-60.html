This pull request is open and not merged. The change it proposes is commit ee3564f.

In one paragraph

Z3's own checker for clause logs now understands the rem operator when the divisor is a nonzero integer numeral. For every rem term, the arithmetic solver logs two theory axioms, each a two-literal clause. Before, the native checker verified only one of them. The other went to the SMT fallback. Now both verify natively. The Python checker and the Lean refutations do not change, since they already checked these steps. So the Lean trust boundary stays where it was, and Z3's own diagnostic checker gets stronger.

Background

The previous iteration, PR #59, taught the Python exporter and Lean to certify rem by a nonzero numeral over the sort Int. Z3's native arith checker still accepted only one of the two rem axioms. The axiom whose guard literal is valid passed. The other needs the defining identity of rem, which the checker did not know. After this PR, the only native fallbacks left in those logs are cut steps, by design. The work serves milestone 3, "Equality and linear arithmetic", and keeps the C++ checker useful for diagnostics.

What changed

  • Z3's native arith checker can now verify both rem axioms, for positive and for negative divisors.
  • It does this by rewriting (rem u k) as s * (u - k * (div u k)), where s is the sign of k, which is Z3's own definition of rem.
  • It still refuses rem by zero or by a term, and bounds on rem.
  • New C++ unit tests show 7 rem clauses that must be accepted and 7 that must be rejected.
  • A new Python test checks that a real Z3 log with both divisor signs replays with no SMT fallback.
  • The project plan gains a dated note, "Native checks of the rem axioms (2026-10-31)".

An analogy: a grader knew the rule for mod but sent every rem question to a calculator. Now the grader knows that rem is mod, with a sign flip for negative divisors.

Worked example

This PR changes the native checker, not Lean reconstruction. So the example shows real native hints and replay output, plus the unchanged Lean result.

(a) The input

The number 2x is even, so its remainder by 4 is 0 or 2, never more than 2.

(set-logic QF_LIA)
(declare-const x Int)
(assert (> (rem (* 2 x) 4) 2))
(check-sat)

It is the rem_prod input of the implementer's probe script. Its clause log holds the two rem axioms:

(declare-fun x () Int)
(define-const $7 Int (* 2 x))
(define-const $17 Int (mod $7 4))
...
(define-const $19 Bool (>= 4 0))
(define-const $9 Int (rem $7 4))
(define-const $21 Bool (= $9 $17))
(declare-fun arith (Bool Bool) Proof)
(define-const $34 Bool (not $21))
(define-const $36 Proof (arith $19 $34))
(infer (not $19) $21 $36)
(define-const $18 Int (- $17))
(define-const $35 Bool (= $9 $18))
(define-const $38 Bool (not $35))
(define-const $37 Bool (not $19))
(define-const $39 Proof (arith $37 $38))
(infer $19 $35 $39)
...

The first infer says "4 < 0, or rem equals mod". Only the rem identity justifies it. The second says "4 ≥ 0, or rem equals minus mod", and its guard is valid.

Risks and open questions

  • The native checker now accepts more steps. A wrong acceptance would be a soundness bug in Z3's native checking, not in the Lean certificates.
  • Mitigations: Z3's own rem definition, negative unit tests, and two fuzz runs without an unsound acceptance.
  • Some valid clauses, such as those mixing k and -k divisors, are still rejected. That is safe but incomplete.
  • CI results for this PR are unknown to this report.

What comes next

  • Native rem bounds, which Z3 does not emit today.

Glossary

clause
A disjunction of literals: it holds when at least one of its literals is true. Example: (or (not p) q).
clause log
A file in which the solver records each clause it derives, with a hint saying why it holds. A checker can replay it step by step.
cut
An integer reasoning step that strengthens a bound by rounding, such as from 2x <= 3 to x <= 1.
div, mod
Integer division and its remainder. For a nonzero k, u = k * (div u k) + (mod u k), and mod is never negative.
Farkas lemma
A proof that some linear inequalities conflict, given as coefficients whose weighted sum yields a false fact like 0 < 0. Shown as farkas in the replay counters.
fuzzing
Testing with many automatically generated inputs to find cases that break a program.
guard
The condition literal of an axiom split into cases, such as (>= k 0) in the rem axioms.
hash-consing
Storing each distinct term once, so equal terms are the same object and cancel when subtracted.
hint
The label on a logged step that tells the checker which rule to use, such as arith, farkas, or cut.
integer numeral
A literal constant number such as 3 or (- 3), as opposed to a term with variables.
literal
An atomic formula or its negation. Example: (>= k 0) and (not (>= k 0)).
refutation
A proof that a set of assertions leads to False, so they cannot all hold.
rem
Z3's integer remainder. It equals (mod t k) when k >= 0 and (- (mod t k)) otherwise.
SMT fallback
When no native rule checks a step, the replay asks an SMT solver to confirm it. The output marks such a step verified-smt. It is weaker evidence than a rule check.
sort
The type of a value in SMT-LIB, such as Int, Real, or Bool.
soundness
A checker is sound if it never accepts a false step.
tactic
A Lean command that builds part of a proof automatically. omega decides linear integer arithmetic.
theory axiom
A clause that holds because of what a theory's symbols mean, here arithmetic, rather than because of earlier steps.
trust boundary
The set of components a result's correctness depends on. Code outside it can have bugs without making a wrong proof pass.
valid
True under every assignment of values. (>= 4 0) is valid. A formula that is not valid is falsifiable.
