In one paragraph

Z3's older engine, called the legacy core, writes down a complete proof object: a full chain of reasoning steps, including every step that shows two things are equal. Before this PR, that proof object could be exported and checked in Lean only for problems made of plain true/false variables. This PR extends the export and the Lean reconstruction to problems with unknown functions, that is functions with a name but no definition, over values of any declared type. Each equality step becomes an explicit Lean proof term, and Lean's type checker confirms the whole chain without automation rediscovering the reasoning.

Background

Before this PR, problems with unknown functions were certified only through the clause log, a record of learned clauses from Z3's newer engine. That route leaves equality reasoning as hints for a Lean automation tactic to fill in, and it starts after Z3's preprocessing. The legacy proof object already had the missing steps, but the exporter refused it beyond plain true/false problems, and the reconstructor only knew equality rules between statements, not between values. This serves the plan's third milestone, equality and linear arithmetic, and was the first item on its backlog.

What changed

  • Export from the legacy core. You can now export the legacy proof object of a problem with unknown functions, where before the exporter refused.
  • Equalities between values. Steps like "a equals b and b equals c, so a equals c" become Lean proof terms when a, b, and c are values, not just statements.
  • Equal inputs give equal outputs. "a equals b, so f(a) equals f(b)" is now a direct Lean term, like two identical keys opening the same lock. This also covers if-then-else values and "all different" claims.
  • Swapped sides. A new rule accepts Z3's step that swaps the two sides of an equality or of an and/or.
  • Fewer helper lemmas. A rewrite that changes nothing is proved in place, so most of these proofs need no automation tactic.
  • Unchanged defaults. Automatic mode still sends these problems to the clause log. Users opt in with --core legacy.

Worked example

This input declares a type, two values of it, an unknown function f, and an unknown test p. It says a and b are equal, p holds for f(a), and p fails for f(b). That cannot all be true.

Input

(set-logic QF_UF)
(declare-sort U 0)
(declare-fun a () U)
(declare-fun b () U)
(declare-fun f (U) U)
(declare-fun p (U) Bool)
(assert (= a b))
(assert (p (f a)))
(assert (not (p (f b))))
(check-sat)

Before

The exporter from the parent commit, asked for the legacy proof object, stopped with this error and exit code 2:

proof_certificate.py: error: uninterpreted functions requires the clause-log exporter (fragment qf_uf)

Feeding the new certificate to the old reconstructor also failed, because it only knew congruence between statements:

The old default mode did accept this input through the clause log. The new path is the legacy proof object, which the old code rejected as shown.

After

The current exporter with --core legacy produced a certificate with two congruence steps, and the reconstructor generated this Lean file.

def term_0 (...) : _U := _elems 0
def term_1 (...) : _U := _elems 1
def formula_2 (...) : Prop := ((term_0 ...) = (term_1 ...))
def term_3 (...) : _U := _funs 0 [(term_0 ...)]
def formula_4 (...) : Prop := _preds 0 [(term_3 ...)]
def term_5 (...) : _U := _funs 0 [(term_1 ...)]
def formula_6 (...) : Prop := _preds 0 [(term_5 ...)]
def formula_7 (...) : Prop := (Not (formula_6 ...))
...

These name the pieces: a and b are elements 0 and 1, f(a) and f(b) are function 0 applied to each, and p(f(a)) and p(f(b)) are test 0 applied to those.

theorem unsat (_atoms : Nat -> Prop) (_U : Type) (_elems : Nat -> _U)
    (_funs : Nat -> List _U -> _U) (_preds : Nat -> List _U -> Prop) (_bool : Prop -> _U)
    (_h0 : (formula_2 ...))
    (_h1 : (formula_4 ...))
    (_h2 : (formula_7 ...))
    : False :=
  ...

The theorem says: for any type, any elements, any functions, and any tests, the three assertions together lead to a contradiction.

  let _step_17 : (formula_16 ...) :=
    (congrArg (_funs 0) (congr (congrArg List.cons _step_15) (Eq.refl [])))
  let _step_19 : (formula_18 ...) :=
    (Iff.of_eq (congrArg (_preds 0) (congr (congrArg List.cons _step_17) (Eq.refl []))))
  let _step_20 : (formula_6 ...) :=
    (Iff.mp _step_19 _step_11)
  ...
  let _step_26 : False :=
    (False.elim (_step_24 _step_20))

Step 17 is the new feature: from a = b it builds f(a) = f(b) by applying f to equal argument lists. Step 19 does the same for p, giving "p(f(a)) if and only if p(f(b))", and the final steps combine that with the assertions into a contradiction.

The Lean check accepted the file. Its output ended with Lean checks passed.

Review

The reviewer approved with no blocking, major, or minor findings. They re-ran the suites, drove the command line end to end, and built several tampered certificates by hand. Every forgery was rejected, by the Python checks or by Lean. Four small findings, called nits, remained.

  1. Ill-typed fallback (fixed). The reviewer imagined a congruence step with no arguments, concluding that a value equals itself. The code would have emitted a term for statements, so Lean would reject a valid certificate. Z3 never emits that step, and the outcome was a false rejection, never a false acceptance. It was fixed anyway, with a new test and a one-off Lean check.
  2. Outdated documentation (fixed). One README sentence still said every rewrite is checked by a truth table. It now lists the three cases and points to the new section.
  3. Pinned random seeds (kept). The new tests pin random seeds and require a certain amount of congruence reasoning, so an unrelated change to Z3's search could break them. This matches an existing pattern, and the failure message says to re-pick the seed.
  4. Duplicate classification (kept). One function re-classifies assertions its callers already classified. The extra pass is cheap, and changing the signature would break a caller in the companion test repository.

Risks and open questions

  • Shared code paths now branch on whether a step relates values or statements. For statements the emitted text is unchanged, as the existing suites confirm.
  • Gate clauses are matched differently, so an "all different" claim is identified with its pairwise inequalities. A wrong match can only cause a Lean rejection, since the lemma is always checked.
  • The swapped-sides rule for and, or, and exclusive-or was exercised only by a hand-written Lean probe. Z3 did not emit those shapes on any scanned input.
  • The largest proof measured had about 1,230 steps. Behaviour on much larger proofs is unknown.

What comes next

  • Add unknown-function inputs and a legacy-core cell to the regression matrix in the companion test repository, so this path is exercised beyond unit tests.
  • Make the legacy proof object usable for linear arithmetic, which needs Z3's C++ side to record coefficients its arithmetic lemmas currently omit.
  • Measure much larger legacy proofs with unknown functions.

Glossary

  • Legacy core: Z3's older, default engine, which records a complete proof object when proofs are requested.
  • Proof object: the full tree of reasoning steps the legacy core produces, including every equality step.
  • Clause log: the learned-clause record of Z3's newer engine, which leaves equality reasoning as hints.
  • Unknown function (uninterpreted function): a function with a name and argument types but no definition.
  • Congruence (monotonicity step): equal inputs give equal outputs, so a = b implies f(a) = f(b).
  • Commutativity step: Z3's step that swaps the two sides of an equality or of an and/or.
  • Gate clause (def-axiom): a clause relating a compound expression to its parts.
  • Proof term: an explicit Lean expression checked by Lean's core without automation.
  • grind: a Lean automation tactic that searches for a proof on its own.
