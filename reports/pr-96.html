In one paragraph

This PR changes how the Lean reconstructor writes proofs about propositional clauses. Its prover searches with propagation and case splits. Now it also tracks which steps each closed branch really uses. When a branch closes without its own hypothesis, the whole split is dropped. This is called backjumping. Every proof also keeps only the steps it uses. As a result, the wide cnf lemma of the difference logic circuit ckt_PROP1_tf_10 now gets a structural proof. Before, Lean ran out of heartbeats on the lemma's fallback tactic, so the whole refutation failed. Lean now accepts it. Other large inputs, such as BubbleSort, MinMax and parity, also check several times faster. Lean still checks every line, and the trusted base is unchanged.

Background

A first Lean measurement of small QF_IDL sample files found about a third of them verified. Three RTCL circuit inputs failed in the same way. Each has a single assertion built from long chains of if-then-else terms over integer comparisons. Z3 derives a wide clause from such a chain. A cnf lemma must then show that the clause follows from the assertion. The clause is propositionally valid, but the prover split atoms 31 levels deep and gave up. This work serves milestone 3 of the plan, equality and linear arithmetic. It reuses the Boolean proof machinery from milestone 2.

What changed

  • The propositional prover now drops a case split when one branch closes without its hypothesis, so the proof skips the other branches.
  • Every generated propositional proof now keeps only the have steps it actually uses, so Lean has far less to check.
  • You can now certify the SMT-LIB circuit ckt_PROP1_tf_10 in Lean, and it ships as a new test input.
  • A new Lean test checks that circuit's lemma with its fallback removed, so only the new structural proof can pass it.
  • A new unit test, which needs no Lean, shows backjumping on a tiny clause set and checks that every kept step is used.
  • The plan document and the examples README now describe this behavior.

An analogy: you reason "either the key is in the drawer, or it is not". In the first case your argument never mentions the drawer. Then the case analysis was pointless, and backjumping deletes it. Trimming is like deleting side calculations the final answer never used. Only the emitted proof text changes. No rule or axiom was added.

Review

The reviewer approved. There were no blocker, major or minor findings.

One nit, fixed. The reviewer noticed that the new circuit test only checked that a structural attempt existed. It did not check that Lean accepted that attempt rather than the fallback. So a future fallback that happened to succeed could hide a broken structural proof. The fix makes the test delete the fallback before running Lean. As a negative check, the last line of the structural proof was deleted, and Lean rejected the file with "unsolved goals". The test now catches exactly the failure it targets.

Three suggestions, left as follow-ups. Drop unused bridge steps in the cnf lemma too. Charge the search budget for kept text, not generated text. Assert that each emitted step is a single line. None of these affects soundness.

Risks and open questions

  • Every proof from the propositional prover now has different text. Tests that pin exact text still pass.
  • The trimming reads the proof text. It assumes the prover's step names look like _f12 and that each step fits on one line. A future multi-line step would make Lean reject the proof. That is visible, never unsound.
  • The search budget still counts generated text, not kept text. This is conservative.
  • The larger circuits tf_20 and tf_30 still fall back and fail in Lean. Their search explodes even with 100 times the budget.
  • Two other QF_IDL Lean failures, DTP_k2_n35 and plan-21, were not investigated.
  • GitHub CI results after the merge are not known to this report.

What comes next

The search for the larger circuits likely needs clause learning, or guidance from a SAT solver's own refutation. Two candidates are named: probing for failed literals before splitting, and replaying a Z3 propositional proof of the clause. The review's three suggestions are also open.

Glossary

assertion
A formula the input states as true, written (assert ...) in SMT-LIB.
atom
A smallest true-or-false piece of a formula, such as a Boolean constant p or a comparison x - y >= 3.
backjumping
Leaving a case split early when one branch's proof turns out not to need that branch's hypothesis. The proof then holds without the split.
Boolean
The sort with exactly two values, true and false. SMT-LIB writes it Bool.
case split
Proving a goal by considering each possibility in turn, for example "p is true" and then "p is false".
clause
A disjunction of literals, such as p or not q or x < 3. It is true when at least one literal is true.
clause learning
A search technique that records why a branch failed as a new clause, so the search never repeats the same mistake.
cnf lemma
A lemma linking a clause Z3 works with to the original assertion it came from. Here it is proved by propositional reasoning.
difference logic
Integer or real constraints of the form x - y <= c. The SMT-LIB logic QF_IDL is integer difference logic without quantifiers.
fallback
A second proof attempt used when the first one fails. Here it unfolds every definition and calls an automatic tactic.
heartbeat
Lean's unit of work. When a proof step uses more heartbeats than allowed, Lean stops with a timeout error.
hypothesis
A fact assumed inside a proof, such as "p is true" in one branch of a case split.
if-then-else term
A term that picks one of two values by a condition. SMT-LIB writes it (ite c a b): a when c holds, else b.
lemma
A helper theorem proved once and then used by the main proof.
literal
An atom or the negation of an atom, such as p or not p.
propagation
Deriving forced facts from known ones. For example, from p or q and not p, conclude q.
propositionally valid
True for every true/false assignment to its atoms, using only the Boolean connectives and not what the atoms mean.
refutation
A proof that a set of formulas cannot all be true at once, ending in False.
structural proof
A proof written out as explicit small steps, as opposed to a single call to an automatic tactic.
tactic
A Lean command that builds part of a proof automatically, such as omega for integer arithmetic or grind.
trusted base
The code and axioms that must be correct for a checked proof to be believed. Here it is Lean's kernel and standard axioms.
