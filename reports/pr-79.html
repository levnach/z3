Make clause logs with array maps readable by the proof trimmer

Pull request levnach/z3#79 · State: OPEN · Opened 2026-11-06T16:44:58Z · Loop iteration 79

This pull request is open and not merged. The change it proposes is commit e4d7e3f.

In one paragraph

Z3's proof trimmer could not read back any clause log that contained an array map. The log used a mapped uninterpreted function without a declaration. It also wrote a built-in function such as <= without its signature. The exporter then fell back to the untrimmed log. Its replay rejects any log holding the default-value axiom of a map, even when the refutation never uses that axiom. This PR makes Z3 declare every mapped function and print every mapped built-in with its signature. Now the trimmer reads map logs, drops the unused axiom, and Lean checks the result. No Lean code changed, and the trust boundary is the same.

Background

The previous PR certified maps of Boolean connectives, arithmetic, comparisons, if-then-else terms, and uninterpreted functions through the clause log. Large logs go through the trimmer first, but for map logs that step always failed. A random map sweep in the previous iteration found two unsat inputs rejected for this reason. This PR serves milestone 4 of the plan, "Broader theories and integration", where arrays are one of the extensions.

What changed

  • C++, declaration collector: a clause log now declares a mapped uninterpreted function, such as f, before the map that uses it.
  • C++, clause-log printer: a map of a built-in is now written with its signature, as in (_ map (<= (Int Int) Bool)), so Z3's own parser can read it back.
  • Python replay: the replay reads both the old and the new map form, and rejects a logged signature that does not match the function it rebuilds.
  • End result: map logs are now trimmed, so an unused default-value axiom no longer causes a rejection.
  • Side effect: other printers that share the collector, such as Solver.sexpr(), now also declare mapped functions, so their output parses back too.

An analogy: the old log was a recipe that said "apply f to every cell" but never said what f was. A cook could follow it from memory, but a second cook who only had the page could not. The trimmer is that second cook.

Review

The reviewer approved the change, with no blocker and no major finding.

  • Minor, fixed. The reviewer logged small datatype inputs and found that the new printer changed them too. Testers printed as (_ is (nil () L)) instead of the standard (_ is nil). Z3 still read them, but other tools would see a non-standard form. The fix limits signature printing to maps, and a new test pins the standard forms.
  • Nit, fixed. The plan said "Z3's other output is unchanged," but Solver.sexpr() now declares mapped functions. The document now says so.
  • Suggestion, not changed. A map of a map, such as (_ map (_ map f)), still lacks an inner signature. It is rare, the replay rejects it cleanly, and it is left as a follow-up.

Risks and open questions

  • The collector is shared, so Solver.sexpr() output changes for inputs with a mapped uninterpreted function. No z3test expected output contains a map.
  • One new test relies on Z3's search still producing the default-value axiom for seed 151. A heuristic change could break it.
  • Z3's general printer still prints (_ map <=), which Z3 cannot parse back.

What comes next

  • Give nested maps an inner signature.
  • Scan other log heads, such as built-ins under a map and Skolem constants, for trimmer read failures.
  • Certify inputs whose refutation really needs the default-value axiom. These stay rejected for now.

Glossary

array
A value that maps every index to an element, like a table with one cell per index. (Array Int Bool) has Int indices and Bool elements.
array map
The operator (_ map f), which builds a new array by applying f to each cell. ((_ map f) a) holds f(a[i]) at every index i.
axiom
A fact accepted as a starting point without proof inside the system.
Boolean
The sort Bool, with the two values true and false.
built-in function
A function whose meaning is fixed by the theory, such as +, <=, or ite. It is also called an interpreted function.
clause
A disjunction of literals, such as a or not b. At least one literal must be true.
clause log
A file in which the solver records each clause it adds or learns, with a hint on why it holds.
declaration
A line that introduces a name with its sort or signature, such as (declare-fun f (Int) Int).
default-value axiom
An axiom about the value an array holds at indices that were never written. Z3 may derive it for a map during its search.
if-then-else term
The term (ite c x y), which equals x when c is true and y otherwise.
lemma
A small proved statement used as a step in a larger proof.
literal
An atomic formula or its negation, such as p or not p.
proof trimmer
A Z3 mode that reads a clause log and keeps only the steps the final contradiction depends on.
refutation
A proof that a set of assertions leads to a contradiction, so they cannot all be true.
replay
Re-reading a clause log step by step and rebuilding each step as a checked fact.
signature
The argument sorts and the result sort of a function. The signature of <= on integers is (Int Int) Bool.
sort
The type of a value, such as Int, Real, Bool, or an array sort.
tactic
A Lean command that builds part of a proof automatically. omega solves integer arithmetic, and grind combines several reasoning methods.
theorem
A statement together with a proof that Lean has checked.
trust boundary
The line between parts whose output is checked and parts that must be trusted. Here the trimmer stays outside it, because every kept step is replayed and checked in Lean.
uninterpreted function
A function symbol with no fixed meaning, only a signature. The solver may pick any function that fits the assertions.
