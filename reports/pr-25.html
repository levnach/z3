Prove the logged clause in the proof checker's SMT fallback

Pull request levnach/z3#25 · state OPEN · opened 2026-10-21T01:23:35Z · loop iteration 25

This pull request is not merged. The report describes the change at commit 9790165b, which sits on top of base commit a7dd4c26. There is no merge commit.

In one paragraph

Z3's own proof replay checks every logged clause against its hint. When no native checker accepts the hint, an SMT fallback asks a fresh solver to refute the negation of a verification condition. Before this PR, that condition was the logged clause joined with the hint's clause. Whenever the hint's clause was a tautology, any logged clause passed as verified, even a satisfiable one. The fallback now refutes the negation of the logged clause by itself. A plugin's shortcut condition is used only after a subsumption test and a RUP check show that the logged clause follows from the hint's clause. The C++ replay is the diagnostic safety net behind the Lean certificates, and a net that accepts a satisfiable clause says nothing about a refutation.

Background

Before this PR the replay checked Boolean, equality, arithmetic, and alldiff gate clauses natively, and the fallback covered the hints of the theory plugins for arrays, datatypes, quantifiers, and floating point. The previous iteration's review found that a valid alldiff hint with a logged clause strictly inside the hint's clause was accepted through the fallback, although the dropped literal was not false by RUP. The hole predates that checker and affected every plugin without its own verification condition. A second gap sat next to it: the quantifier instantiation shortcut accepted the logged clause without relating it to the hint's clause at all. Milestone 4 of the plan keeps the C++ checker for diagnostics, and the regression matrix depends on its verdicts being meaningful. This PR closes the replay's soundness hole and changes nothing in the Python exporter or the Lean reconstruction.

What changed

  • The fallback proves the right thing. A logged clause is accepted only if a solver refutes its negation under the replay's assumptions, with no help from the hint's clause.
  • Shortcuts need a bridge to the logged clause. A plugin's simplified condition is honoured only when every logged literal occurs in the hint's clause and the dropped literals are false by RUP. The plugin's receipt vouches for the hint's clause, so the checker first confirms that the logged clause is covered by it.
  • One shared test for "follows from the hint". The native path and the fallback use the same subsumption-plus-RUP computation, found in follows_from_hint.
  • The checker reports instead of exiting. The step checker returns true or false, so a unit test can drive it directly, while the two command-line callers still stop the process on a failed step.
  • Diagnostics mean what they say. The line unit ... is not rup is printed only when the step is finally rejected, because z3test's matrix classifies any output containing it as a rejection.
  • A direct unit test of the fallback. Seven probes cover the rejected case, the natively verified case, valid and invalid array hints, and logged clauses outside the hint's clause.

Worked example

This PR changes the native C++ checker only, so the example shows a replay log and the checker's verdict before and after, not Lean code. The input is the probe from the previous iteration's review, which the PR's new unit test reproduces. It declares an uninterpreted sort U with three constants and assumes that they are not all distinct. It then logs the unit clause that they are distinct, under an alldiff hint whose clause is "distinct, or some pair is equal". The hint's clause is a tautology. The logged unit is not.

(a) The input

(declare-sort U 0)(declare-fun a () U)(declare-fun b () U)(declare-fun c () U)
(define-const $15 Bool (= a b))(define-const $16 Bool (= b c))(define-const $13 Bool (= a c))
(define-const $9 Bool (distinct a b c))(define-const $14 Bool (or $15 $13 $16))
(declare-fun alldiff (Bool Bool) Proof)(declare-fun rup () Proof)
(assume (not $9))
(infer $9 (alldiff $9 $14))
(infer rup)

The file is one physical line of declarations followed by the three replay steps. The declarations are wrapped here for readability only.

(b) Before: the baseline build accepted the step

Run by the implementer on the build of the base commit at the start of this iteration, with solver.proof.check=true:

unit (not (or (= a b) (= a c) (= b c))) is not rup
(proofs -alldiff 1)
(verified-smt
(alldiff (distinct a b c) (or (= a b) (= a c) (= b c)))
 (distinct a b c))
(proofs +rup 1 -alldiff 1)
exit=0

The native alldiff checker correctly refused the step, because the dropped literal was not false by RUP. The fallback then "verified" it anyway, and the final rup step closed a refutation of a satisfiable assumption.

(c) After: the current build rejects the step with a countermodel

Run for this report on the PR's head commit, same command:

(proofs -alldiff 1)
unit (not (or (= a b) (= a c) (= b c))) is not rup
did not verify: l_true
(distinct a b c)
vc:

(distinct a b c)
hint: (alldiff (distinct a b c) (or (= a b) (= a c) (= b c)))
...
(define-fun b () U
  U!val!0)
(define-fun c () U
  U!val!1)
(define-fun a () U
  U!val!0)
...
exit=0

The verification condition is now the logged clause alone. The solver finds a countermodel in which a and b are the same element, so the step is rejected and no verified-smt line appears. The exit status is still zero, as before, because the frontends have not changed.

The second commit's effect is visible on the reviewer's array probe, a valid logged unit (= a a) under an array hint whose dropped literal is not RUP. On the current build it prints (proofs -array 1) followed by (verified-smt ...) and no is not rup line, which is exactly what the matrix classifier needs.

No Lean file is produced for this example. The Lean suites were run unchanged to confirm nothing on that side moved, see the next section.

Review

The reviewer approved the change and found no blocker or major issue. They reproduced the probe before and after, wrote four extra probes for the quantifier paths, and could not make the new code accept a clause the solver had not proved.

Minor: a diagnostic that lied to the matrix

The reviewer noticed that the shared RUP test now runs for hints no plugin checks natively, such as array hints. They built a probe with a valid logged unit whose dropped literal is not RUP. The checker printed unit (= b a) is not rup and then verified the step through the fallback. That is correct, but z3test's matrix script treats any output containing that phrase as a rejection, so a canary that used to pass would have failed CI. The second commit buffers the message and prints it only just before did not verify. The unit test asserts the phrase is present on rejected steps and absent on that fallback success.

Nit: noisy unit-test logs

The new test helper captured the checker's output and then echoed it back, so a passing run of the full unit-test suite contained several did not verify blocks with model dumps. Anyone grepping the logs that the memory-safety workflow saves would have found false hits. The echo was removed, and the full suite's output no longer contains the phrase.

Suggestion, not acted on

The quantifier plugin's tautology shortcut is counted as a native hit, +inst, so the matrix cannot tell it apart from a real native check. This is pre-existing counter behaviour and was left for a later revision of the hint statistics.

Risks and open questions

  • Acceptance is strictly stronger. A replay that was verified only because the hint's clause was a tautology now ends in did not verify. The canaries, the SMT2 corpus, and the Lean matrices show no such case, but external logs might.
  • Quantifier steps may get slower. An instantiation clause that differs from the hint's clause beyond RUP-false dropped literals is now proved against the full quantified premise. This is sound but can be expensive, and no such input is in the corpora.
  • Exit status still hides failures. A refuted replay exits with status zero, so CI sees a rejection only through the printed text, which the matrix script relies on.
  • CI is pending. Most workflows had not finished at report time, and the local runs are not a substitute for the CI result.
  • A stale annotation remains. The canary list still marks t8.smt2 as checker-rejected, although it has replayed as an unverified fallback since before this change.

What comes next

  • Return a nonzero exit status from the replay frontends on a refuted step, once the matrix script no longer depends on the printed text.
  • Give the quantifier tautology shortcut its own counter so the matrix can tell it from a native check.
  • Remove the stale t8.smt2 annotation in z3test.
  • Carry the alldiff gate clauses into the Python exporter and the Lean reconstruction, and handle single-argument distinct in Lean. Both remain on the backlog.

Glossary

assumption
A clause that the replay takes as given, usually an input assertion. Example: (assume (not $9)).
Boolean
The sort of truth values, true and false, and the connectives over them such as and, or, and not.
clause
A disjunction of literals, that is, an "or" of simple statements. Example: (or (= a b) (= a c)).
countermodel
An assignment of values that makes the negated condition true, showing that the claimed clause does not follow. Example: a = b above.
distinct
The SMT-LIB predicate stating that all its arguments are pairwise different. Example: (distinct a b c).
hint (proof hint)
A short justification attached to a logged clause that names the rule and its ingredients, so a checker knows what to verify. Example: (alldiff $9 $14).
literal
An atomic statement or its negation. Example: (= a b) or (not (= a b)).
proof replay
Running Z3's own checker over the clause log of a solve and verifying each inferred clause from its hint.
quantifier instantiation
Deriving a concrete instance from a "for all" statement by substituting a term for the bound variable.
refutation
A proof that a set of statements is contradictory, ending in the empty clause.
regression matrix
The z3test script that replays benchmark files under several proof settings and reports whether each cell verified, fell back, or was rejected.
RUP (reverse unit propagation)
A cheap test that a clause follows from the clauses so far: assume all its literals false and look for a contradiction by unit propagation alone.
satisfiable
A statement that can be made true by some assignment of values. Its negation is therefore not a theorem.
SMT fallback
The replay's last resort: when no native checker accepts a step, a fresh solver is asked to refute the negation of a verification condition.
soundness
The property that a checker accepts only clauses that genuinely follow. A soundness hole is a way to make it accept something false.
subsumption
One clause subsumes another when every literal of the first occurs in the second. The shorter clause is then at least as strong.
tautology
A clause that is true under every assignment, in the relevant theory. Example: (or (distinct a b c) (= a b) (= a c) (= b c)).
theory
A fixed interpretation of some symbols, such as arithmetic, arrays, datatypes, or floating point, that a checker plugin specialises in.
uninterpreted sort
A sort with no built-in meaning, so its elements can only be compared for equality. Example: (declare-sort U 0).
unit clause
A clause with exactly one literal. Example: (distinct a b c) on its own.
verification condition
The clause the fallback must prove. The solver is given its negation and must report that no assignment satisfies it.
