In one paragraph

The certificate pipeline now handles inputs that pick one of two values of a user-declared type with an if-then-else. A user-declared type is a kind of value with no built-in meaning, so the only facts about it are those the input states. Before, the exporter rejected any such if-then-else, even though Z3 solved the input at once and recorded a full proof. Now the proof becomes a Lean file that Lean accepts with no trusted shortcut. Random testing of the new path also uncovered two older gaps in the proof replay, both fixed here.

Background

Since iteration 2 the pipeline has certified proofs over one user-declared type with constants, unknown functions, equality, and "all different" constraints. An unknown function is one the input names but never defines. If-then-else over that type was rejected, although it had worked over real numbers since iteration 1 and Z3's proof record treats both alike. The work serves milestone 3 of the plan, which asks to complete each fragment end to end before starting another.

What changed

  • Exporter. An input with an if-then-else over the user-declared type is now classified as supported instead of rejected.
  • Replay. Each such term gets two "gate" rules, like a railway switch: when the condition holds the term equals the first branch, otherwise the second.
  • Lean reconstruction. The term becomes Lean's own if-then-else, and the gates are proved with two standard Lean lemmas, as for real numbers.
  • True/false if-then-else fix. Two extra rules Z3 records without the condition were rejected as invalid built-in truths and are now recognized.
  • Fallback lemma fix. When no single assertion explains a recorded clause, the replay now uses a small conflicting subset of assertions, called an unsat core, and no longer drops a literal it still needs.
  • Clearer errors. Running out of the replay's resource budget now reports a resource error instead of a misleading mismatch.

Worked example

This input was built from the pull request's new tests and run through the old and the new pipeline. The first assertion says c equals a when the condition holds and b otherwise. The other two rule out both cases.

(a) The input

(declare-sort U 0)
(declare-fun a () U)
(declare-fun b () U)
(declare-fun c () U)
(declare-const q Bool)
(assert (= c (ite q a b)))
(assert (or (not q) (not (= c a))))
(assert (or q (not (= c b))))

The user-declared type becomes a type variable, and the if-then-else becomes Lean's own if-then-else over it, with a classical instance so Lean need not decide the condition by algorithm.

private theorem def_axiom_15 ... [_df1 : Decidable (formula_1 ...)]
    : (formula_14 ...) :=
  @Decidable.byCases (formula_1 ...) _ _df1
    (fun _hc => (Or.inr (ite_eq_left _hc))) (fun _hnc => (Or.inl _hnc))

private theorem def_axiom_18 ... [_df1 : Decidable (formula_1 ...)]
    : (formula_17 ...) :=
  @Decidable.byCases (formula_1 ...) _ _df1
    (fun _hc => (Or.inl _hc)) (fun _hnc => (Or.inr (ite_eq_right _hnc)))

These are the two gate rules. Each splits on the condition and uses a standard Lean lemma to show the term equals the matching branch.

Review

The reviewer approved the change with no blocker, major, or minor findings. They re-ran every suite, confirmed that each new test fails against the old library, and tampered with inputs. Swapped branches and wrongly typed conditions were all rejected before Lean ran. Three small "nit" findings remained.

  • Misleading error when the budget runs out. The reviewer saw that an inner solver call that ran out of its resource budget was treated like "no conflicting subset exists", so a large input would see a mismatch message that hid the real cause. Fixed in the follow-up commit: the replay now reports a resource-limit error, pinned by a test that lowers the limit to one.
  • A test bound that leans on Z3's choice of core. One new test pins the fallback lemma to three literals, assuming Z3's conflicting subset leaves out an irrelevant assertion. Not changed: the suggested looser bound equals three here, no platform-dependent arithmetic is involved, and a failure would signal a real change in Z3.
  • Gate rules not indexed for trimmed records. The new gate rules are not in the index used when a trimmed proof record omits them. Nothing fails today because trimmed records carry those rules explicitly. Not changed, since the same was already true for real numbers and a fix needs a design decision.

Risks and open questions

  • The fallback lemma now uses a conflicting subset instead of all assertions, in every fragment. Any such subset still implies the clause, so the lemma stays valid, and the real-arithmetic matrix confirms it.
  • Z3's conflicting subsets are not minimal. On an input with many assertions the fallback could hand Lean a slow lemma with many hypotheses. Not measured beyond the random stress set.
  • The replay visits more nodes per literal when searching for if-then-else terms. For inputs without such terms the generated Lean text is unchanged.
  • Still rejected at merge time: a second user-declared type, mixing the type with arithmetic, unknown functions with true/false or real arguments, and integer arithmetic.

What comes next

  • Add an input of this kind to the shared regression corpus, which lives outside this repository, so the CI proof matrix covers the path directly.
  • Take up the remaining rejected shapes. The repository history shows the next two pull requests addressed several user-declared types and true/false arguments.
  • Decide how to index gate rules for trimmed proof records, and measure the fallback lemma on inputs with many assertions.

Glossary

If-then-else term
A value equal to one branch when a condition holds and the other branch otherwise. Written ite in the input language.
User-declared type
A kind of value the input names without giving it a built-in meaning. The "uninterpreted sort" of the title.
Unknown function
A function the input names but never defines.
Gate rule
One of two facts tying an if-then-else to a branch, depending on the condition.
Built-in truth
A rule Z3 records as true by its shape alone. Called a "def-axiom" in the proof record.
Proof record and replay
Z3's step-by-step log of derived clauses, and the Python code that checks each step and builds the certificate.
Fallback lemma
The replay's last resort when no single assertion explains a recorded clause.
Unsat core
A subset of the assertions that already has no solution. Small, but not always the smallest.
Trimmed record
A proof record with the steps not needed for the final contradiction removed.
Resource budget
A limit on the work an inner solver call may do during replay before giving up.
QF_UF
The input fragment with equality and unknown functions over user-declared types, and no arithmetic.
