Certify Bool-argument uninterpreted functions in QF_UF refutations

Pull request: levnach/z3 #6 Merge commit: 89a4c55 Merged: 2026-10-13T00:50:45Z Loop iteration: 6

In one paragraph

Before this change the pipeline refused any input in which an unknown function took a true/false value as an argument. An unknown function is one the input names but never defines. Such inputs are common in problems derived from hardware designs. Now the exporter accepts them and Lean checks the result. The theorem gains one extra map, written _bool, that carries each true/false argument into the single value type the theorem already uses. Think of it as putting a yes/no answer into an envelope so it can sit in the same tray as the other items. As a side benefit, the clause-log replay now skips a bookkeeping variable that Z3 sometimes logs under a name the input never declared. That variable used to make the exporter reject even plain inputs with a negated single fact.

Background

Iterations 2, 4, and 5 built the QF_UF slice, the part of the pipeline for equality reasoning over unknown functions without arithmetic. It already handled if-then-else and several kinds of value collapsed into one Lean type. But every argument of an unknown function had to be of an unknown kind. A true/false argument was rejected at the exporter, before any proof was produced. This change serves milestone 3 of the plan, equality and linear arithmetic, and was the first item in the backlog.

What changed

  • Exporter. Unknown functions and predicates, functions whose result is true or false, may now take true/false arguments. Functions whose arguments are all true/false in an input with no unknown kind of value are still rejected, with a message naming the function.
  • Clause-log replay. When Z3 asserts a single true/false fact, it sometimes logs a phantom variable named k!0 standing for its internal "true". The replay now drops clauses over such a phantom instead of rejecting the input. A dropped clause can only make a later step fail loudly, never pass wrongly.
  • Lean encoding. The theorem takes one more input, the envelope map, and every true/false argument is written as that map applied to the argument's formula. Nothing claims the envelope for "true" differs from the one for "false", and no proof step needs that.
  • Lean proof help. Each lemma proved by the automatic grind tactic now first states that every true/false argument it mentions is either true or false. Some random tests failed until this hint was added.

Worked example

This input declares an unknown kind of value and an unknown function from true/false values to it. The first two facts force q to be true. The third says the function gives different results on q and on "true", which is then impossible.

(declare-fun f (Bool) U)
(declare-const q Bool)
(declare-const s Bool)
(assert (or s q))
(assert (or (not s) q))
(assert (not (= (f q) (f true))))

Review

The reviewer approved with no blocking or major findings. One minor issue, one nit, and one suggestion were all addressed before merge.

  • Minor: a test that could not fail. Comments said two test inputs make Z3 log the phantom variable. The reviewer ran them three times each and found no phantom at all. The cause was a set-logic line at the top of each input, which stops Z3 from logging it. So the test checking that the phantom was removed passed for nothing, and a regression would have gone unnoticed. The fix removed the line and made the tests first confirm the raw log contains the phantom, then that the certificate does not.
  • Nit: a stale count. The plan document said three random instances were pinned. There are five. Corrected.
  • Suggestion: document the trust boundary. The rule that drops phantom clauses is now written next to the other replay decisions in the exporter README.

Risks and open questions

  • Every QF_UF theorem changed shape. The new binder appears even without true/false arguments. The suite and the stress runs over the old generators cover this. Other fragments are unchanged.
  • The soundness argument is informal. That the envelope map keeps the theorem honest is argued in the README, like the earlier collapses. It is not proved in Lean.
  • Phantom dropping applies to every fragment. It cannot make a wrong proof pass. But it is keyed on the name prefix k!, and a solver change could alter when the phantom appears. The live tests would then fail with a clear message.
  • Open questions. Why a set-logic line suppresses the phantom was not tracked down. The new hints may add case splits, though every stress lemma stayed under a second.

What comes next

  • Functions whose arguments are all true/false with no unknown kind of value. Z3 replaces these with fresh names, so a different approach is needed.
  • Mixing unknown functions with real-number arithmetic.
  • QF_UF inputs in the z3test regression corpus, so the CI matrix checks this fragment directly.

Glossary

Unknown function
A function the input declares but never defines. Also called an uninterpreted function.
Predicate
An unknown function whose result is a true/false value.
QF_UF
Inputs with unknown functions and equality, but no numbers and no quantifiers.
Clause log
Z3's record of the clauses it assumed, derived, and deleted, which the exporter replays into a proof.
Phantom variable
A variable such as k!0 in the clause log but not in the input. It stands for Z3's internal "true".
Envelope map (_bool)
The new theorem input that carries a true/false value into the single value type.
Excluded middle
The fact that any statement is either true or false.
Standard axioms
The three axioms Lean proofs commonly rely on. Every certificate here uses only these.
