Certify maps of functions, arithmetic, and ite in Lean via clause log

Pull request levnach/z3#77 · state OPEN · 2026-11-06T08:42:55Z · loop iteration 78

This pull request is open and not merged. The change it proposes ends at commit 5b077fd. It has two commits on top of master.

In one paragraph

This PR widens which array maps the pipeline can certify through the clause log. Before, a map could only apply one of four Boolean connectives to sets. Now it may also apply xor, equality, distinct, Int and Real addition and subtraction, comparisons, the if-then-else term, and any uninterpreted function or predicate of up to three arguments. The elements may be of an uninterpreted sort, Int, Real, or Bool. The PR also fixes a missing fact for reads that the rewriter evaluates through a store down to a map. So more unsat inputs with maps now end in a refutation that Lean's kernel checks. The trust boundary is unchanged: no new axiom and no sorry.

Background

PR #74 added maps and set operators, but only for not, and, or, and => over sets. Every other map was rejected by the exporter with "maps are supported over the connectives not, and, or, => only". This rejection hit maps of an uninterpreted function, of +, and of <=, even though Z3 solves such inputs. The plan's backlog listed this as "Maps of other functions". The work serves milestone 4 of the plan, broader theories, in its part on arrays.

What changed

  • You can now certify maps of xor, =, distinct, Int and Real + and -, the comparisons, and ite.
  • You can now certify a map of an uninterpreted function or predicate with one to three arguments, even if the input never applies it directly.
  • Mapped arrays may now hold elements of an uninterpreted sort, Int, Real, or Bool, and all arguments must share one index sort.
  • A read that the rewriter evaluates by skipping a store at another numeral index, down to a map, now gets the facts Lean needs.
  • A certificate that swaps the mapped function or its signature, or a clause log with an ill-sorted map head, is now rejected cleanly.

An analogy for a map: it works like a spreadsheet column formula. Column B holds f of column A, row by row. A read of B at row 3 is just f of A at row 3. Lean proves each such read fact by rfl, because the map is written as a lambda whose body matches the way other terms are printed.

Worked example

This input is the PR's test map_function_read. It maps an uninterpreted function f over the array a. All outputs below come from real runs of the scripts.

(a) The input

(declare-fun f (Int) Int)
(declare-fun a () (Array Int Int))
(declare-fun b () (Array Int Int))
(assert (= b ((_ map f) a)))
(assert (= (select a 3) 4))
(assert (not (= (select b 3) (f 4))))
(check-sat)

Array b is f applied to every cell of a. Cell 3 of a is 4, so cell 3 of b must be f(4). The last assertion denies that.

(b) Before: the exporter at the PR's base commit

proof_certificate.py: error: maps are supported over the connectives not, and, or, => only: ((_ map f) a)

The old exporter stopped here, so the old reconstructor was never reached.

(c) After: the Lean file the reconstructor writes now

-- Int function 0: "f"
-- Array 0: "b"
-- Array 1: "a"
...
structure Interpretation where
  ...
  ifuns : Nat -> List U -> Int
  arrs_ii : Nat -> Int -> Int

The symbols are listed by number, and the model gives Lean a meaning for f and both arrays.

def _map1 {I E G : Type} (f : E -> G) (a : I -> E) : I -> G := fun _i => f (a _i)
...
def term_2 (_atoms : Nat -> Prop) (_vars : Nat -> Int) (_m : Interpretation) : (Int -> Int) :=
  (_map1 (fun (_v0 : Int) => (_m.ifuns 0 [(_m.int _v0)])) (term_1 _atoms _vars _m))

The map is now polymorphic, and the term ((_ map f) a) becomes _map1 of a lambda that calls f.

theorem unsat (_atoms : Nat -> Prop) (_vars : Nat -> Int) (_m : Interpretation)
    (_h0 : (formula_3 _atoms _vars _m))
    (_h1 : (formula_7 _atoms _vars _m))
    (_h2 : (formula_11 _atoms _vars _m))
    : False :=
  ...

The theorem says the three assertions together imply False, for every interpretation.

private theorem th_lemma_22 (_atoms : Nat -> Prop) (_vars : Nat -> Int) (_m : Interpretation)
    : (formula_21 _atoms _vars _m) := by
  unfold formula_21 term_20 term_19 term_5 term_4
  have _t2 : (term_2 _atoms _vars _m) = (_map1 (fun (_v0 : Int) => (_m.ifuns 0 [(_m.int _v0)])) ((term_1 _atoms _vars _m))) := rfl
  have _m19 : _select ((term_2 _atoms _vars _m)) (((3 : Int))) = (_m.ifuns 0 [(_m.int (_select ((term_1 _atoms _vars _m)) (((3 : Int)))))]) := rfl
  first | omega | grind (splits := 64)

This lemma states that reading the map at 3 equals f of reading a at 3, proved by rfl and then closed by a tactic.

The reconstructor printed "Lean checked the refutation". A separate run of scripts/check_lean.sh on the file ended with "Lean checks passed." So Lean accepted the file.

Review

The reviewer approved the change. There were no blocker or major findings.

  • Minor: a crash instead of a clean rejection. The reviewer fed the replay a hand-made clause log with <= mapped over an uninterpreted sort, and - mapped over Bool. Z3 itself never logs such maps. The replay crashed with a Python TypeError instead of a proper export error. Nothing reached Lean, so soundness was never at risk. It mattered because bad input should always fail with a clear message. The fix catches that error and reports "ill-sorted map in the clause log". A regression check now covers both heads and not over a sort.
  • Nit: a path readers could not follow. The plan cited a sweep script that lives only on the loop machine. It now calls the sweep a one-off run outside the repository.
  • Nit: an incomplete list. The README did not say that uninterpreted functions of four or more arguments are rejected. The README and the plan now say so, and the plan also names connectives of three or more arguments.

Risks and open questions

  • The local gate failed in the Lean reconstruction step, and the cause is not recorded. The PR stays open until that is resolved.
  • Each map of a commutative function adds one grind call per lemma that reaches it. It is cheap on the tests but could slow map-heavy inputs.
  • A read of a map over stores now states more facts, which grows with long store chains.
  • The map lambdas copy how other terms are printed. If that printing changes and the copy does not, Lean will fail. It would not be unsound.
  • Z3's native trimmer cannot re-read map logs. Map logs of 4 KB or more fall back to the slower untrimmed replay, with a warning.
  • No z3test file newly certifies. Its other maps are sat or use eval or apply.

What comes next

  • Get a passing local gate run, or explain the failed step, before the PR can merge.
  • Fix Z3's clause-log printer in C++ so the trimmer can read map logs again. This is in the backlog.
  • Still rejected: maps of *, conversions, abs, functions of four or more arguments, and maps over arrays of arrays.
  • The default-map axiom is still rejected. Two of the 92 unsat sweep inputs needed it.

Glossary

array
A total function from an index sort to an element sort. (Array Int Int) maps each Int to an Int.
axiom
A statement Lean accepts without proof. Adding one widens what must be trusted.
Boolean
The sort Bool, whose values are true and false.
certificate
The file the exporter writes. It records the proof steps so another tool can check them.
clause
A disjunction of literals, such as (or p (not q)). A literal is an atom or its negation.
clause log
Z3's record of the clauses it learned and the theory facts behind them, used here as proof evidence.
commutativity
The property that argument order does not matter, as in x + y = y + x.
distinct
The SMT-LIB function that is true when its arguments are pairwise unequal.
exporter
The script that turns Z3's proof evidence into a certificate, or rejects inputs it cannot handle.
if-then-else term
A term (ite c x y) whose value is x when c holds and y otherwise.
kernel
The small core of Lean that checks every proof. Trust rests on it.
lambda
An unnamed function, such as fun x => x + 1.
lemma
A small proved statement used as a step toward a larger theorem.
map
An array term ((_ map f) a b) that applies f at every index. Its cell i is f of cell i of a and of b.
numeral
A constant number written in the input, such as 3 or 2.5.
polymorphic
Defined once for many types. A polymorphic map works for Int, Real, Bool, or sort elements.
predicate
A function whose result is Boolean, such as (p x).
reconstructor
The script that turns a certificate into a Lean file with a proof.
refutation
A proof that a set of assertions implies false, so they cannot all hold.
replay
The step that re-reads the clause log and rebuilds its terms before export.
rewriter
The part of Z3 that simplifies terms before and during solving.
rfl
Lean's proof that two sides are equal by unfolding definitions. It needs no search.
set
An array with Bool elements. Cell i is true when i is in the set.
sorry
A Lean placeholder that skips a proof. A certified file must contain none.
sort
The type of a value, such as Int, Real, Bool, or an array sort.
store
The array term (store a i v), which is a with cell i set to v.
tactic
A Lean command that searches for a proof, such as omega for linear integer arithmetic or grind.
trimmer
Z3's tool that shortens a clause log to the steps a proof needs.
trust boundary
The set of things one must trust for a result to be believed, here Lean's kernel and its standard axioms.
uninterpreted function
A function symbol with no fixed meaning. Only equal arguments must give equal results.
uninterpreted sort
A sort declared by name with no fixed values, such as (declare-sort E 0).
xor
Exclusive or. It is true when exactly one of its two Boolean arguments is true.
