Certify maps of functions, arithmetic, and ite in Lean via clause log

Pull request levnach/z3#77 into master · State: OPEN · Date: 2026-11-06T08:42:55Z · Loop iteration 78

This pull request is open and not merged. The change under review is commit 5b077fd. The PR holds two commits, and this report covers both.

In one paragraph

Before this PR, the pipeline could certify an array map only when the mapped function was one of the connectives not, and, or, or =>. Now it also certifies maps of xor, =, distinct, integer and real arithmetic (+, -, and the comparisons), the if-then-else term, and uninterpreted functions and predicates of up to three arguments. The elements may be of an uninterpreted sort, Int, Real, or Boolean. These inputs go through the clause log, and Lean's kernel checks the resulting refutation. The PR also closes a gap in the read facts: a read that the rewriter pushed past a store into a map now gets its facts. The trust boundary is unchanged: no sorry and no new axiom.

Background

The previous PR, #74, added maps over sets, but only for the four connectives. Every other map was rejected with the message "maps are supported over the connectives not, and, or, => only". That happened even though Z3 solves such inputs, for example a map of <= as in z3test's t155.smt2. Arrays over Bool indices (#75) and nested arrays (#76) were already certified. This PR serves Milestone 4, "Broader theories and integration", where arrays are one of the listed extensions.

What changed

  • You can now certify a map of an uninterpreted function or predicate with one, two, or three arguments, even when the input never applies that function directly.
  • You can now certify maps of integer and real +, -, <=, <, >=, >, and of xor, =, distinct, and ite.
  • Maps of the commutative functions (xor, =, distinct, +) get a commutativity fact, so "f of a and b equals f of b and a" can be proved for the whole array.
  • A read that the rewriter evaluates below a skipped store now gets the map's read facts, so three inputs from a random sweep that failed in Lean now verify.
  • A tampered certificate cannot swap the mapped function or its signature, because the reconstructor ties it to the input's own symbol.
  • A malformed clause log with an ill-sorted map head is now rejected with a clean error instead of a Python crash.

By component: the exporter (proof_certificate.py) now names the mapped function and checks its sorts. The clause-log replay (proof_clause_log.py) rebuilds built-in map heads that Z3 logs without a signature. The reconstructor (proof_to_lean.py) makes Lean's _map1 and _map2 work for any element types and adds _map3 for three arrays. Think of a map as a cookie cutter applied at every index: the reconstructor now accepts any cutter shape, not only four.

This input is the PR's test map_comparison. It has the same shape as z3test's t155.smt2. The array c holds, at every index, whether a is at most b there. At index 3 that is 4 <= 5, which is true, yet the last assertion says it is false.

The theorem says that the four assertions together imply False, for every interpretation of the symbols.

private theorem th_lemma_58 (_atoms : Nat -> Prop) (_vars : Nat -> Int) (_m : Interpretation)
    : (formula_48 _atoms _vars _m) := by
  unfold formula_48 formula_40 formula_28 term_9 term_6 term_5
  have _t3 : (term_3 _atoms _vars _m) = (_map2 (fun (_v0 : Int) (_v1 : Int) => (_v0 <= _v1)) ((term_1 _atoms _vars _m)) ((term_2 _atoms _vars _m))) := rfl
  have _m40 : _select ((term_3 _atoms _vars _m)) (((3 : Int))) = ((_select ((term_1 _atoms _vars _m)) (((3 : Int)))) <= (_select ((term_2 _atoms _vars _m)) (((3 : Int))))) := rfl
  first | omega | grind (splits := 64)

This lemma states that reading the map at 3 equals a[3] <= b[3], proved by rfl and closed by a tactic.

Review

The reviewer approved the PR with no blocker and no major finding.

  • Minor: a crash on a malformed log. The reviewer fed the replay a clause log with an ill-sorted map head, such as <= over an uninterpreted sort. Z3 never logs such a head, but a tampered log could. The replay crashed with a Python TypeError instead of a clean rejection. Nothing reached Lean, so this was not a soundness problem. It was fixed: the error is now caught and reported as a rejected map, and a regression test was added.
  • Nit: a local path in the plan. The plan cited a sweep script that exists only in the loop's scratch space. Readers could not reproduce the claim from it. It was fixed: the plan now describes the sweep as a one-off run outside the repository.
  • Nit: an incomplete list of rejected maps. The README did not say that functions of four or more arguments are rejected. It was fixed in the README and the plan.

Risks and open questions

  • Each commutative map adds one more grind call. It is cheap on the tests, but map-heavy inputs might get slow.
  • A read of a map over a long store chain now states more facts.
  • Map bodies copy how terms are printed elsewhere. If one printer changes and the other does not, Lean fails. That is a failure, not unsoundness.
  • Z3's native trimmer cannot re-read map logs. Map logs of 4 KB or more fall back to a slower replay, with a warning.
  • No z3test file newly certifies, because its other maps are sat or use eval.

What comes next

  • Fix Z3's log printer in C++ so the trimmer can re-read map logs. This is in the backlog.
  • Maps of *, conversions, abs, functions of four or more arguments, and maps over arrays of arrays remain rejected.
  • The default-map axiom is still unsupported. Two of the sweep's unsat inputs need it.

Glossary

arithmetic (linear)
Terms built from numbers, variables, +, -, and comparisons such as <=.
array
A total function from an index sort to an element sort. (Array Int Bool) maps each integer to true or false.
array map
The SMT-LIB term ((_ map f) a b): a new array whose value at each index i is f(a[i], b[i]).
axiom
A statement accepted without proof. Adding new ones would weaken what a Lean check guarantees.
Boolean
The sort with exactly two values, true and false. SMT-LIB calls it Bool.
clause
A disjunction of literals, such as p or not q.
clause log
A record of the clauses the solver derived or added while it searched, which can be replayed step by step.
commutativity
The property f(x, y) = f(y, x). Addition is commutative, subtraction is not.
congruence
The rule that equal arguments give equal results: if a = b, then f(a) = f(b).
connective
A Boolean operator such as not, and, or, =>, or xor.
distinct
The SMT-LIB predicate that is true when its arguments are pairwise different.
if-then-else term (ite)
(ite c x y) has the value x when c is true and y otherwise.
kernel
The small core of Lean that checks every proof. Trust in a result rests on it.
lambda
An unnamed function written inline, such as fun x y => x <= y.
lemma
A small proved statement used as a step in a larger proof.
literal
An atomic formula or its negation, such as p or not p.
predicate
A function whose result is Boolean, such as (p x).
read (select)
(select a i) is the value of array a at index i.
refutation
A proof that a set of assertions leads to a contradiction, so they cannot all be true.
rewriter
The part of Z3 that simplifies terms before solving, for example turning (+ 1 2) into 3.
sort
The type of a value, such as Int, Real, or Bool.
store
(store a i v) is the array a with the value at index i replaced by v.
tactic
A Lean command that searches for a proof automatically, such as omega for integer arithmetic or grind.
trust boundary
The set of things a result relies on without checking them, such as Lean's kernel and its standard axioms.
uninterpreted function
A function symbol with no fixed meaning. Only congruence is known about it. Example: (declare-fun f (Int) Int).
uninterpreted sort
A sort declared with no built-in meaning, such as (declare-sort E 0).
