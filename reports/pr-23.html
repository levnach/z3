Check xor gate clauses in the native Tseitin proof checker

Pull request #23 in levnach/z3 · OPEN · opened 2026-10-20T03:23:11Z · loop iteration 23

This pull request is not merged. The change under review is commit 246396e5a, which sits on top of base commit 7d383c3fd.

In one paragraph

Z3's native proof checker has a plugin that checks Tseitin gate clauses. That plugin accepted invalid gate clauses for xor. It counted how many literals of the clause mentioned a gate argument, instead of reading the polarity of each one. For a negated gate it looked at the wrong node and accepted nearly anything. This PR replaces the count with a real evaluation of the xor under the assignment that falsifies the other literals. The checker now rejects a clause that is not a tautology and still accepts the four clauses Z3 emits per gate. A native hint that passes the checker counts as trusted evidence during proof replay, so this hole could let an unsound refutation through unnoticed.

Background

Before this PR the native checker already had branches for and, or, ite, implication and Boolean equality gates, and the Lean side verified Boolean refutations through its own def-axiom rule. The xor branch accepted gate clauses that have a countermodel. Iterations 20 to 22 repaired similar gaps in the Farkas and implied-equality checkers. The plan treats checker correctness as its own obligation and keeps the C++ checker as a trusted diagnostic beside the Lean path in milestones 3 and 4.

What changed

  • Native checker: an xor gate clause is now accepted only when every gate argument is fixed by another clause literal or is a constant, and the gate then takes the value that makes the clause true.
  • Negated gates: the checker now reads the arguments of the xor itself, not of the outer not node, so a clause ending in a negated xor no longer passes automatically.
  • Regression tests: a unit test covers the four defining clauses, every wrong polarity, free, repeated, constant and nested arguments, and unaffected and gates. A replay test requires all four hints of a hand-written xor log to verify natively.
  • Test reliability: the unit test now installs an exit guard, so a replay that quits early fails the test binary instead of skipping later checks. The second commit makes the guard's cleanup safe when the parser throws.
  • Documentation: a dated plan note records the bug and its counterexamples.

An analogy: a gate clause is a wiring rule saying the output wire must agree with its inputs. The old check counted how many input wires the rule mentioned. The new check sets each wire and reads the output.

Worked example

This PR changes the native C++ checker, not the Lean reconstruction, so the example is a native clause log with real checker verdicts before and after the fix.

(a) The input: a clause log with one invalid xor gate clause

The log defines a gate for (xor a b) and claims that (or (not a) (not $1)) follows from the gate alone. It does not. With a true and b false both literals are false. The file comes from the PR's regression scratch work.

The whole fix is one small helper. It flips a running Boolean for each argument that is true under the falsifying assignment and fails if an argument is left free.

bool theory_checker::xor_holds(app* x, bool expected) {
    bool value = false;
    for (expr* arg : *x) {
        if (m.is_true(arg) || is_complement(arg))
            value = !value;
        else if (!m.is_false(arg) && !is_marked(arg))
            return false;
    }
    return value == expected;
}

Lean check. The Lean pipeline was also run on the SMT-LIB problem behind the log, and the Lean check passed. In the generated file the rewriter has already turned the xor into a negated Boolean equality, so Lean never sees an xor gate.

Review

The reviewer approved the change after reading the diff, the checker's marking helpers, and the replay frontend's failure path. Two minor findings were fixed in the second commit. No blocker or major finding was raised.

  • Minor: cleanup was not exception-safe. The reviewer traced what happens when the parser throws inside the replay helper. The captured stream was only restored on a normal return, so the exit guard could point at a destroyed buffer. The fix moves the state into a scoped object that restores it on any exit path. A crash in the guard would have hidden the real failure.
  • Minor: wrong counterexamples in the prose. The reviewer checked the note and comments against the truth table. The note did not name the falsifying assignments, and a four-argument example had the wrong parity. Both were corrected so a reader can verify each example by hand.

Risks and open questions

  • Only checker acceptance changes. One possible regression is rejecting a clause Z3 emits, and the tests cover its four clauses per gate.
  • Live clause logs rarely contain xor hints because of the rewriter. The fix closes a soundness gap rather than certifying new inputs.
  • A clause with both polarities of an argument may still be accepted, which is sound because it is a tautology on its own.
  • The exit guard calls a hard exit inside an exit handler, but only while a replay is in progress.
  • CI results are not yet known.

What comes next

  • The production replay frontend still exits with status zero on a refuted proof. The guard here is test-only, and fixing the frontend is a separate follow-up.
  • The alldiff checker plugin still trusts every hint it is given. The backlog lists the shapes Z3 emits and the evidence a real check would need.
  • The loop stops with this C++ PR open. It is not merged automatically.

Glossary

assignment
A choice of true or false for every Boolean variable. Example: a = true, b = false.
clause
A disjunction ("or") of literals. It is true when at least one literal is true.
clause log
A text record of the clauses a solver learned, each with a hint saying how it was justified, so a checker can replay the run.
countermodel
An assignment that makes a claimed-valid formula false. It is proof that the claim is wrong.
def-axiom
The proof rule that introduces the defining clauses of a Boolean gate. Lean checks it independently of the native checker.
Farkas lemma
A rule for linear arithmetic: if a nonnegative weighted sum of inequalities gives a contradiction, the inequalities cannot all hold.
gate clause
One of the clauses that tie a fresh variable to the connective it names. For $1 = (xor a b) there are four of them.
hint
A tag on a clause in a clause log naming the checker that should verify it, such as tseitin, farkas or rup.
implied equality
An equality that follows from a set of linear inequalities because they force two terms to be equal.
literal
A Boolean variable or its negation, such as a or (not a).
parity
Whether a count is even or odd. An xor is true exactly when an odd number of its arguments are true.
polarity
Whether a literal is positive (a) or negative ((not a)).
proof checker
A program that checks each step of a proof against its rule and rejects steps that do not follow. Z3's native one is written in C++.
proof replay
Reading a clause log back and verifying every clause with the checker named by its hint.
refutation
A proof that a set of assertions is contradictory, ending in the empty clause or in False.
rewriter
The simplification stage that replaces a term by an equivalent one before solving. Here it turns (xor a b) into (not (= a b)).
RUP (unit propagation)
Reverse unit propagation: a clause is justified if assuming all its literals false and propagating the known clauses reaches a conflict.
tautology
A formula that is true under every assignment. A correct gate clause is a tautology once the gate variable is read as its definition.
Tseitin transformation
The standard way to turn a formula into clauses by naming each subformula with a fresh variable and adding gate clauses for it.
xor
Exclusive or. (xor a b) is true when exactly one of a and b is true.
