Certify scripts with print-only commands, define-const, and exit

Pull request levnach/z3#93 · State: OPEN · Date: 2026-11-08T01:29:08Z · Loop iteration 93

This pull request is open and not merged. The change it proposes is commit d2e84e804. It contains two commits. The first adds the feature. The second fixes a problem found in review.

In one paragraph

The exporter's frontend reads an SMT-LIB script and picks the query to certify. Before this PR, it refused the whole script if it contained a command that only prints, such as simplify, apply, or get-value. Now it drops those commands, because they never change the assertion stack. It also reads define-const as a definition and stops reading at exit, just as Z3 does. One safety rule stays: a dropped command must not hide a named term. With this change, four more Z3 regression files produce a refutation that Lean checks. The certificate and the Lean theorem are unchanged in kind. Only the set of accepted scripts grew.

Background

A fresh scan of the 959 files in the z3test regressions/smt2 folder classified every query. All 35 unsat queries inside the certified fragments already exported and verified in Lean. The remaining gap was the frontend. It rejected scripts over commands that touch no assertion, over text after exit, and over harmless options like :trace. This work serves the regression-methodology priority and Milestone 4 of the plan. That milestone asks for a frontend that preserves the exact scope context and rejects unsupported configurations explicitly.

What changed

  • You can now certify a script that contains get-value, eval, simplify, apply, display, or get-assertions. The exporter drops them.
  • You can now use define-const, which the frontend reads like a define-fun with no arguments.
  • You can now end a script with exit and leave anything after it, even text that does not parse.
  • You can now set the debug options :trace and :trace_file_name, and :global-decls false, which is Z3's default.
  • You still get a clear rejection if a dropped command contains a :named label, because Z3 would register that name.

All code changes are in the Python exporter. There are no C++ or Lean library changes. Think of the frontend as a clerk copying a recipe. Lines like "show me the bowl" can be skipped. A line that quietly names an ingredient cannot be skipped, because later steps may use that name.

Review

Major, fixed. The reviewer asked what happens to a :named label inside a dropped command. They wrote a five-line script. It labels x as p inside simplify, then defines p as true and asserts not p. Z3 keeps the label even though the command only prints. So Z3 rejects the later definition and answers sat. The exporter dropped the label and kept the definition. Lean then checked an "unsat" theorem for a script Z3 calls sat. That breaks the core promise that a certificate describes the real query. The fix rejects any dropped command that contains :named. The reviewer's script, a get-value variant, and three more are now rejected test cases.

Nit, fixed. The plan note cited a scratch file outside the repository. It now describes the scan in words.

Suggestion, done. t119.smt2 has no check-sat. The note now says the certified statement is that its final state is unsat.

Risks and open questions

  • Dropping a command is sound only if Z3 changes neither the assertions, the declarations, nor the query count for it. The author checked this in the Z3 sources for each dropped command.
  • The :named check matches the keyword token. Strings and quoted symbols are separate tokens, so they cannot trigger or hide it.
  • The CI result and the local gate result are not known to this report.

What comes next

  • Still rejected: minimize, maximize, assert-soft, and :opt.* options, because they change what check-sat answers.
  • Also still rejected: get-consequences, include, :error-behavior, and :global-decls true.
  • The unsat queries in z3test crash.smt2 need lblpos labels and the :nnf.sk-hack option. That is a possible follow-up.

Glossary

assertion
A formula the script states as true, written (assert ...).
assertion stack
The current list of declarations and assertions, organized in scopes that push and pop open and close.
certificate
A file holding the evidence for an unsat answer, which a separate checker can verify.
clause
A disjunction of literals, such as x < 0 or y = 1. It is true if at least one literal is true.
definition
A name bound to a fixed term, such as (define-const y Int (+ x 1)). Every use of y means x + 1.
fragment
A restricted family of formulas, such as quantifier-free linear integer arithmetic (qf_lia).
frontend
The part of a tool that reads the input text and turns it into an internal form.
hypothesis
An assumption a theorem takes as given. Here each assertion becomes one hypothesis.
if-then-else term
A term (ite c t e) whose value is t when condition c holds and e otherwise. Example: abs a is (ite (>= a 0) a (- a)).
lemma
A small proved fact used as a step in a larger proof.
literal
An atomic formula or its negation, such as p or not p.
named term
A term given a label with (! t :named p). The label p then stands for t.
option
A setting given with set-option, such as :produce-models true.
query
One satisfiability question in a script, usually a check-sat over the assertions in force at that point.
refutation
A proof that a set of assertions leads to false, so they cannot all hold.
scope
A level of the assertion stack. push opens one and pop removes it with everything declared or asserted inside.
sound
A step is sound if it never turns a true claim into a false one. Here it means no satisfiable script gets an unsat certificate.
tactic
A command that transforms goals. Z3's apply runs a tactic and prints the result. Lean tactics like omega build proofs.
theorem
A statement with a proof that Lean has checked. Here it says the assertions imply False.
