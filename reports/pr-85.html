In one paragraph

Z3's rewriter decides an equality between two arrays by comparing two store chains built over constant arrays. To replay that rewrite in Lean, the reconstructor states small read facts, one per array level and index. Their number grows quadratically, so above a cap of 64 the reconstructor used to drop them all. Without them the grind tactic failed, already for two chains of five stores. This PR keeps only the reads that Z3's rewriter itself evaluates. Those are far fewer, so long comparisons now reach a refutation that Lean accepts. A second cap of 640 keeps very long chains from exhausting memory.

Background

The previous iterations taught the pipeline about constant arrays, their default values, and the extensionality converse of a chain comparison. That worked for short store chains. Two chains of four stores verified, but five stores already crossed the cap and failed. In a random sweep, 25 of 45 unsat inputs failed this way. The fix was listed as a backlog item after iteration 84. It serves milestone 4 of the plan, "Broader theories and integration", which treats arrays as their own extension.

What changed

  • Comparisons of long store chains over constant arrays now verify in Lean, where only up to four stores per chain did before.
  • Above the old cap, the reconstructor states only the reads each compared chain needs, walking down until a store at the same index or the constant array.
  • A second cap stops that walk from growing without bound, so very long chains check as quickly as they did before this PR.
  • New tests add a long-chain input, a random generator of chain comparisons, and a check of the second cap.

Think of the reads as a checklist that Lean works through. The old checklist covered every array at every index, so it was cut entirely when too long. The new one lists only the boxes the rewriter actually opens.

Worked example

This input, built from the PR's documented test input, compares two five-store chains in opposite orders. The values come from an uninterpreted function u. Since x = y, the chains are equal, which contradicts the first two assertions.

Review

Major: the targeted reads had no bound

The reviewer built two 64-store chains over the constant arrays of 0 and 1, compared under a guard. Z3 decides that comparison by the two default values alone, so no read is needed. Before the PR, Lean checked it in about one second. With the first version of this PR, Lean was killed at 13.5 GB of memory. So an input that certified before would now fail. The implementer added the second cap. Above it, the rewrite states no reads, as before. The 64-store case went back to 1.2 s. A new test checks the cap without running Lean.

Nit: a test compared a hand-computed number

One test checked that a written-out number exceeded the cap. It would have kept passing if the input stopped exceeding it. The test now rebuilds the input with the first cap lifted and counts exactly 84 reads.

Suggestions not taken

The reviewer also suggested skipping equalities with different default values. The general cap already covers that case. Factoring the reads shared by the rewrite's branches was left as a follow-up, because it changes every constant-array rewrite.

Risks and open questions

  • Equal chains of about 25 or more stores need more than 640 reads. Lean still rejects them, as before this PR.
  • The 640 cap was measured on one macOS machine. Memory use on CI runners may differ.
  • Above the first cap, an equality with a plain array or a function application on one side still gets no reads. No failing input is known.
  • The existing random constant-array generator never crosses the first cap, so that mix is untested.

What comes next

  • State each shared read once instead of in every branch of the rewrite's proof. That would cut the cost by about two thirds.
  • Alternatively, state only the reads on the path the rewriter takes, to reach longer chains.
  • Add a generator that mixes long chains with plain array constants, and sweep chains of 20 to 50 stores.

Glossary

array
A map from indices to values, such as (Array Int Int). Unlike a list, it has a value at every index.
congruence
The rule that equal inputs give equal outputs. If a = b then (select a 3) = (select b 3).
constant array
An array with the same value at every index, written ((as const (Array Int Int)) 0).
default value
The value an array holds at all but finitely many indices. For a constant array of 0 it is 0.
extensionality
The rule that two arrays are equal when they agree at every index.
grind
A Lean tactic that searches for a proof by combining equalities, case splits, and arithmetic.
lemma
A small proved statement used as a step in a larger proof.
quadratic growth
Growth like n times n. Doubling the chain length roughly quadruples the number of facts.
read
Looking up an array at one index, written (select a i).
refutation
A proof that a set of assertions leads to False.
rewrite
A step where the solver replaces a formula by a simpler equivalent one. Each rewrite becomes a lemma in Lean.
sort
The type of a value, such as Int, Real, Bool, or (Array Int Int).
store
An array with one index changed, written (store a i v). It equals a except that index i holds v.
store chain
Several stores nested on top of each other, such as (store (store a 0 v) 1 w).
tactic
A Lean command that builds part of a proof automatically.
uninterpreted function
A function symbol with no fixed meaning. The only rule is congruence. Example: (declare-fun u (Int) Int).
