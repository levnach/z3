Certify long store-chain comparisons over constant arrays in Lean

Pull request levnach/z3#85 · state OPEN · 2026-11-07T05:28:55Z · loop iteration 85

This pull request is open and not merged. The change it proposes is commit 3ee5355a3, on top of base commit 5fb92d433.

In one paragraph

Z3's rewriter decides whether two store chains over constant arrays are equal by comparing them at each stored index. Lean proves each such rewrite step with the grind tactic, helped by read facts about what each select returns. Their number grows quadratically, so above a cap of 64 the reconstructor dropped them all. Two chains of five stores then already failed in Lean. This PR keeps, above the cap, only the reads the rewriter itself performs. Long chain comparisons now end in a refutation that Lean accepts. A second cap at 640 reads protects Lean's memory on very long chains.

Background

Iteration 84 added an extensionality fact for store-chain comparisons. Its premises are the values of both chains at each stored index. At or below 64 read facts, the reconstructor supplied them. Above that it kept only the default value facts, and 25 of 45 unsat seeds in a random sweep failed. The work serves milestone 4 of the plan, "Broader theories and integration", for the theory of arrays.

What changed

  • Long store-chain comparisons now verify, because the reconstructor states the reads Z3's rewriter evaluates.
  • Each read walks down a chain only to the outermost store at its index, so the facts follow the compared chains only.
  • Past 640 targeted reads, a second cap drops all read facts, so very long chains cost no more than before.
  • New tests cover a documented input, two pinned random seeds, and the second cap.

The first of the two commits adds the targeted reads, and the second adds the cap after review. No C++ changed, and no axiom or sorry was added.

Worked example

Think of a store chain as a stack of notes over a default board. To read a slot, you look from the newest note down and stop at the first note for that slot. The new read facts record exactly those looks.

(a) The input

This input shortens the PR's test input long_store_chains_over_two_constants. Its stored values come from an uninterpreted function. Both chains store the same values at indices 0 to 4, in opposite order. The Boolean p is false, so the chains must differ, yet x = y makes them equal.

(set-logic QF_ALIA)
(declare-const x Int)
(declare-const y Int)
(declare-const p Bool)
(declare-fun u (Int) Int)
(assert (or p (not (= (store (store (store (store (store ((as const (Array Int Int)) x) 0 (u 0)) 1 (u 1)) 2 (u 2)) 3 (u 3)) 4 (u 4))
                      (store (store (store (store (store ((as const (Array Int Int)) y) 4 (u 4)) 3 (u 3)) 2 (u 2)) 1 (u 1)) 0 (u 0))))))
(assert (not p))
(assert (= x y))
(check-sat)

Review

The first review asked for changes, with one major finding and one nit.

Major: the targeted reads had no bound

The reviewer compared two 64-store chains over constant arrays holding 0 and 1. Z3 decides this from the defaults alone, and Lean checked it in 1.2 seconds before the PR. With the first commit, Lean was killed at about 13.5 GB of memory. Chains this long are normal in memory-model encodings, so inputs that certified before would have failed. The fix is the second cap: past 640 targeted reads, no read facts are stated, as before. The reviewer's input checks in 1.2 seconds again, and a new test guards the cap.

Nit: a test compared a hand-computed number

One test checked a hand-written constant against the cap, which proved nothing about the input. The test now rebuilds the input with the cap disabled and counts exactly 84 read facts. A suggestion to share read facts across proof branches was deferred as a follow-up.

Risks and open questions

  • Equal chains of about 25 or more stores exceed 640 reads, so Lean still rejects them, as before.
  • The cap was calibrated on one macOS machine, and CI runners may use more memory.
  • Above the old cap, an equality with a plain array on one side still gets no read facts. No failing input is known.

What comes next

  • Share the read facts across the branches of the rewrite proof, cutting their cost by about two thirds.
  • Add a generator that mixes long chains with plain array constants, and sweep chains of 20 to 50 stores.

Glossary

array
A map from indices to elements, read with select and updated with store. Example: (Array Int Int).
Boolean
The sort with the two values true and false, written Bool.
congruence
The rule that equal inputs give equal outputs: if a = b, then f a = f b.
constant array
An array with the same element at every index. Example: ((as const (Array Int Int)) x).
default value
The element an array holds at all but finitely many indices, such as x for a constant array of x with a few stores.
extensionality
The rule that two arrays are equal when they agree at every index.
grind
A Lean tactic that proves goals by combining congruence, case splits, and arithmetic.
read fact
In this project, a lemma that states the value of one select from an array at one index.
refutation
A proof that a set of assertions leads to False.
rewrite step, rewriter
A step that replaces a term with a simpler, equivalent term. The rewriter is the part of Z3 that performs these steps, and each one needs its own proof in Lean.
select
Reading an array at an index. (select a i) is the element of a at i.
sort
The type of a value, such as Int, Bool, or (Array Int Int).
store
Writing an array at an index. (store a i v) is a with the element at i replaced by v.
store chain
Several stores nested on top of one array. Example: (store (store a 0 u) 1 w).
tactic
A command that tells Lean how to build a proof, such as omega or grind.
uninterpreted function
A function symbol with no fixed meaning, only its sort. Equal arguments still give equal results. Example: (declare-fun u (Int) Int).
