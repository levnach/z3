State enumeration cases of applications over folded definitions

Pull request levnach/z3#112 · State: OPEN · Opened 2026-11-11T00:58:13Z · Loop iteration 111

This pull request is open and not merged. Its change commit is 2056d91. It contains two commits on top of base 43a341e.

In one paragraph

Each theory lemma over an enumeration sort receives one fact per application of an uninterpreted function that returns that sort. The fact says the value is one of the sort's constructors. Before this PR, the fact spelled out the application's arguments in full. When an argument was a deep chain of if-then-else terms, the whole chain was copied every time. Now the fact names the arguments by their Lean definitions. It is set aside with revert and rewritten by the same unfold as the goal. On the PR's eight-level test input, the Lean file shrank from 27.2 MB to 0.57 MB. Lean ran out of resources on the old file but checks the new one in about a second. So a refutation that used to be rejected now gets a checked certificate. The trust boundary does not move.

Background

Iterations 107 to 110 kept if-then-else terms folded inside euf lemmas, so that a chain appears once, by name. The enumeration facts were left behind and still wrote every chain out. On inputs with a few nested chains, those facts made up almost the whole certificate. This work belongs to milestone 4 of the plan, broader theories, where enumeration datatypes were added on 2026-11-06. It builds on milestone 3's congruence reasoning.

What changed

  • Enumeration facts about function applications now refer to the arguments by name instead of copying them, when the input has no arrays.
  • Inputs with long if-then-else chains under uninterpreted functions now produce small Lean files that Lean can check.
  • A new test generator builds such chains at any depth, and two new tests check the folded form and run Lean on depth 8.
  • One more pinned random seed now guards a subtle Int case that the reviewer found untested.
  • The README and the plan describe the new behaviour.

An analogy: the old facts were like a report that pastes a whole appendix into every footnote. The new facts say "see appendix B" and let one shared step expand it. In the code, the new function is _folded_enumeration_cases in the reconstructor. Constants, array reads, and inputs with arrays still get the old written-out facts.

Worked example

The input is the PR's own test generator at depth 8. I ran the current scripts and the base commit's scripts on it. Everything quoted below comes from those runs.

(a) The input

Two copies of the same chain start from equal values, yet the input claims their ends differ. The full file has 27 lines. Stages 2 to 7 of each copy repeat stage 1's pattern and are cut here. 

(set-logic ALL)
(declare-datatypes ((Color 0)) (((red) (green) (blue))))
(declare-fun f (Color) Color)
(declare-fun p (Color) Bool)
(declare-fun g (Color Color) Color)
(declare-const u0 Color)
(define-fun u1 () Color (ite (p u0) (f u0) (ite (= u0 green) blue (g u0 red))))
...
(define-fun u8 () Color (ite (p u7) (f u7) (ite (= u7 green) blue (g u7 red))))
(declare-const w0 Color)
...                       ; w1 to w8: the same chain, starting from w0
(assert (= u0 w0))
(assert (not (= u8 w8)))
(check-sat)

These fields say that f and g always return red, green, or blue, and the three colors differ.

Each subterm gets one definition, so stage u1 is written once and later referred to by name.

private theorem th_lemma_216 (_atoms : Nat -> Prop) (_m : Interpretation)
    : (formula_215 _atoms _m) := by
  have _ec13 := _m.enum_fcases_0 [(term_11 _atoms _m)]
  revert _ec13
  unfold formula_215 formula_214 formula_213 formula_188 formula_180 formula_68 term_13 term_5
  intro _ec13
  have _ed := _m.enum_distinct
  grind (splits := 64)

This is the new feature: the fact names its argument as term_11, is reverted, unfolded together with the goal, and introduced again.

Review

The reviewer approved the PR. There were no blockers and no major findings.

  • Minor: an untested design choice. The new code hands the arguments, not the application itself, to the unfold step. In some Int lemmas the application's definition is already unfolded, and unfold fails on a name that is gone. The reviewer deliberately broke the code to name the application too. All 31 enumeration tests still passed, yet 11 real inputs then failed in Lean. So a future edit could have reintroduced the bug unnoticed. The fix pinned Int seed 53 in the test seeds, and the broken copy now fails that test.
  • Nit: a narrow pattern. A test's regular expression matched only one-digit field numbers. An input with ten or more enumeration functions would have failed spuriously. The pattern now accepts any number of digits.
  • Suggestion: a dense README sentence. It was rewritten as a plain separate sentence.

Risks and open questions

  • The change affects only completeness. A fact Lean cannot check rejects the certificate. Nothing is skipped or trusted.
  • Of the 155 changed inputs, 146 grew by up to 5%. Lean time on them stayed the same within noise.
  • CI results and the local gate were not yet known when this page was written.

What comes next

  • With arrays, enumeration facts are still written out in full.
  • A 16-level chain with three extra "not equal" assertions is 247 MB and runs out of kernel memory. That size comes from proof steps, which is a separate item.
  • The chain generator produces no datatype lemmas, so datatype lemmas with folded if-then-else terms still need their own generator.

Glossary

application
A function applied to arguments, such as (f u0) or (g u0 red).
certificate
A file of evidence from the solver that an independent checker can verify step by step.
clause
A disjunction of literals, such as (or (not (p u0)) (= u1 (f u0))).
congruence
The rule that equal arguments give equal results. If a = b, then f(a) = f(b).
constructor
One of the named values that build a datatype. Here red, green, and blue are the constructors of Color.
datatype
A sort whose values are built from constructors, declared in SMT-LIB with declare-datatypes.
definition (Lean def)
A named Lean expression. Other code can use the short name instead of repeating the expression.
enumeration sort
A datatype whose constructors take no arguments, so it has a fixed finite list of values, like Color.
euf
The theory of equality with uninterpreted functions. Its lemmas follow from congruence and from equality being reflexive, symmetric, and transitive.
if-then-else term (ite)
A term that picks one of two values by a Boolean condition. (ite c x y) is x when c is true and y otherwise.
literal
A Boolean atom or its negation, such as (p u0) or (not (= u0 w0)).
refutation
A proof that a set of assertions leads to a contradiction, that is, to False.
revert / intro
Lean tactics. revert moves a fact back into the goal as an assumption. intro takes it out again.
sort
The type of a value in SMT-LIB, such as Int, Bool, or Color.
tactic
A Lean command that builds part of a proof. unfold, revert, and grind are tactics.
theory lemma
A clause that holds because of a background theory such as equality or arithmetic, not just because of Boolean logic.
trust boundary
The line between what the checker verifies and what must simply be trusted. In this PR every new fact is still checked by Lean, so nothing new is trusted.
unfold
A Lean tactic that replaces a definition's name with its body, so other tactics can see inside it.
uninterpreted function
A function symbol with no fixed meaning. The only thing known about it is congruence. Here f, g, and p are uninterpreted.
