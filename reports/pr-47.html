Project and-elim operands from shared tails of wide conjunctions

Pull request #47 on levnach/z3 · MERGED · merged 2026-10-30T05:39:26Z · merge commit 8954db3ec · loop iteration 47

In one paragraph

Some Z3 refutations eliminate almost every operand of one very wide conjunction. Before this PR, the reconstructor wrote each and-elim as a projection that walked from the very start of the conjunction. The total work grew quadratically with the width. Lean then ran out of heartbeats and rejected the certificate. Now the reconstructor names a tail of the conjunction every 32 operands with a let binding. Each projection starts from the nearest tail. A 600-operand implication chain and a 1,200-operand Real and Boolean chain now check in Lean. No axiom or sorry was added.

Background

Before this PR, small conjunctions reconstructed fine. Wide ones also worked when only a few operands were eliminated. The failure needed a legacy proof object whose refutation eliminated most operands inside one outlined lemma. Iteration 45 recorded this as a backlog item for a 1,200-operand case. The work serves milestone 2 of the plan, the kernel-checked Boolean slice. It also serves the plan's top priority, the regression matrix, which needs large inputs to check without timeouts.

What changed

Think of a book with 600 pages and no page numbers. To read page 500, you count from page 1 every time. The PR adds a bookmark every 32 pages. Now you count from the nearest bookmark.

  • Reconstructor: an and-elim of an operand at position 32 or later now projects from the nearest tail, so it never walks more than 32 levels.
  • Reconstructor: each outlined lemma, and the main theorem when nothing is outlined, binds the tails it needs right after the premise that proves the conjunction.
  • Reconstructor: a premise that depends on a hypothesis keeps the old direct projection, because its proof cannot be shared this way.
  • Tests: three new Lean-checked tests cover the outlined 600-operand case, an inline 150-operand case, and an 80-operand case whose conjunction proof sits inside the eliminating lemma.
  • Plan document: a dated note in doc/lean-proof-plan.md records the problem, the fix, and the timings.

Worked example

The input is the 600-operand implication chain from the PR's new outlined test. It was run through the old and the new pipeline for this report.

(a) The input

The real file has four lines. The two long lines are cut here with "...".

; 600-operand implication chain: p0, p0 => p1, ..., p597 => p598, not p598
(declare-const p0 Bool) (declare-const p1 Bool) ... (declare-const p598 Bool)
(assert (and p0 (=> p0 p1) (=> p1 p2) ... (=> p597 p598) (not p598)))
(check-sat)

p0 is true, each pi implies the next, and the last one is false. That is a contradiction, and finding it needs every operand.

Minor, untested path. The reviewer looked for the case where the conjunction's proof sits inside the same outlined lemma as its and-elim. Then the tails must follow that proof inside the lemma. The code was correct, and the reviewer confirmed it by hand. But no test guarded it. A later reordering could break it and CI would stay green. The fix added an 80-operand test that forces outlining and checks the tail order in Lean.

Nit, a test pattern that never matched. The test checked that no projection is longer than 32 steps. Its regular expression stopped at the underscore in names like _tail_895_128. So it only checked projections from the start, never from a tail. An off-by-one could have slipped through as a slowdown. The fix matches tails and operand projections separately and bounds each.

Nit, wording. The plan note said every conjunction of 600 or more failed. In fact only refutations that eliminate most operands failed. The note also pointed to a case by a name the section never used. Both were corrected and the text was rewrapped.

Suggestion, not done. A conjunction eliminated only once still gets the full tail chain. The reviewer measured that this costs the same number of steps as a direct projection. So it was left as is.

Risks and open questions

  • The Lean text changes for every and-elim at position 32 or later. This includes older wide tests and clause-log certificates. The full suite passes.
  • Each outlined lemma rebinds the tails it needs. That adds about one let per 32 operands per lemma.
  • Many lets in one declaration slow Lean more than linearly. Chunks stay at 500 steps, which avoids this, but it limits how far the chunk size can grow.
  • Premises that take hypotheses still project from the start. No input has shown this case yet, so its cost is unknown.

What comes next

  • The prover, the def-axiom lemmas, and the EUF terms build their own And.left and And.right chains. These are quadratic in the same way. They may explain a kernel memory blowup on the tta_startup benchmark.
  • Still open from iteration 45: tta_startup does not verify, and FISCHER inputs have quadratic assume equivalence checks.

Glossary

and-elim
The proof rule that takes a proof of a conjunction and returns one of its operands. From A ∧ B, conclude A.
axiom
A statement accepted without proof. A trusted certificate should add none of its own.
Boolean
The sort of truth values, true and false. In SMT-LIB it is Bool.
certificate
The proof data Z3 exports so that another tool can check the result.
clause log
A newer proof format that records the clauses the solver learned, step by step.
conjunction
A formula joined by "and", such as (and p q r). It is true only when every operand is true.
heartbeat
Lean's unit of work. When a declaration uses more than its limit, Lean stops with a timeout.
hypothesis
A temporary assumption inside a proof that is discharged later.
implication
A formula "if A then B", written (=> A B) in SMT-LIB.
legacy proof object
Z3's older proof format, a tree of named proof rules such as and-elim.
lemma
A small proven statement used as a step toward a larger theorem.
let binding
A way to give a value a name once and reuse it, such as let t := x.2.
operand
One of the parts joined by a connective. In (and p q), p and q are operands.
outlining
Splitting a large proof into separate lemmas so that Lean checks smaller pieces.
premise
A fact a proof step uses as input. For and-elim, the premise is the proof of the conjunction.
projection
Taking one part out of a pair. In Lean, h.1 is the left part of h : A ∧ B and h.2 is the right part.
quadratic
Growing with the square of the size. Doubling the width makes the work about four times larger.
reconstructor
The script that turns a certificate into a Lean file for Lean to check.
refutation
A proof that a set of assertions leads to False.
right-nested
A shape where each "and" holds one operand and the rest: A ∧ (B ∧ (C ∧ D)).
sort
The type of a value, such as Int, Real, or Bool.
sorry
A Lean placeholder that skips a proof. A checked certificate must not contain it.
tail
The rest of a right-nested conjunction after its first k operands. Here, a named tail is bound every 32 operands.
theorem
The final proven statement. Here, that the asserted formulas imply False.
timeout
Stopping a check because it used more time or work than allowed.
