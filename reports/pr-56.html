Prove normalized rewrites over reshaped ite terms and wide flattenings

Pull request levnach/z3#56 · OPEN · 2026-10-31T06:57:29Z · loop iteration 56

This pull request is open and not merged. The change commit is d91a1b0f5.

In one paragraph

Z3's rewrite step often reshapes if-then-else terms over sort Real before solving. The reconstructor must then prove, as a lemma, that the original assertion and the reshaped one are equivalent. This PR proves such lemmas when the two sides hold differently shaped ite terms with the same values. It also handles a wide disjunction that one side nests and the other side flattens, with proof size growing linearly instead of quadratically. Three QF_LRA benchmarks that failed the Lean check before now pass it. Every new step is checked by the Lean kernel, so nothing new is trusted.

Background

Before this PR, the reconstructor had a fast path for rewrites, the normalized rewrite. It proves one small lemma per atom, then one propositional lemma that ties the two sides together. Any ite term kept a rewrite off that path. The fallback was the tactic grind over the whole rewrite, and on two spider benchmarks it ran out of heartbeats. On a clock benchmark, a 250-way disjunction made the propositional lemma too large, and grind failed too. This work serves milestone 3, equality and linear arithmetic, and the plan's priority of fixing rescan failures.

What changed

All code changes are in the Python reconstructor proof_to_lean.py. There is no C++ change.

  • Ite value tables. Rewrites whose sides hold reshaped but equal-valued ites can now be proved, since each ite is matched to its partner by its values in every case.
  • Atom lemma fallback. When grind fails on two matched ites, as with an iff or xor condition, the lemma now does a case split on every ite.
  • Links. The propositional prover first proves that matching pieces of the two sides are equivalent, so it stops re-walking long disjunctions.
  • Linear refutation. Refuting each operand of a false disjunction with more than 32 operands now takes a bounded number of steps.
  • Tests and docs. New tests cover the spider shape, its iff and xor variants, and a 16-clock flattening, and the plan gained a dated section.

Think of two lamps wired differently that light up in exactly the same switch positions. A value table lists every switch position, so the two wirings visibly agree. It only picks which term is written. A wrong match would fail the Lean check.

Review

The reviewer approved, with no blocker and no major finding. They forced a deliberately wrong ite match, and Lean rejected the output. So a bad table match cannot sneak in a false claim.

  • Minor, fixed. The reviewer changed the inner ite condition to = or xor. The tables still matched correctly, but a bare grind could not prove the ites equal. The base commit failed these inputs too, so it was a gap, not a regression. The split fallback fixed it, and both variants became a regression test.
  • Nit, fixed. A comment wrongly implied that abs ites get no table. It now gives the real reason they still go to grind.
  • Nit, partly fixed. The size budget now counts one header line it missed. An unproved link still leaves an unused binding, which the author kept because a safe removal needs a larger change.

Risks and open questions

  • The faster refutation affects every prover use, but only for false disjunctions over 32 operands.
  • Linked proofs are larger per step. A much wider rewrite than the 16-clock test could exceed the size budget and fall back to grind.
  • A value table grows exponentially with its condition leaves, so it is capped.
  • The split fallback grows exponentially with the ites in one atom, but it only runs after grind fails.

What comes next

  • Carpark2-ausgabe-6 still fails. Its rewriter evaluates atoms over ites inside other ites' conditions, which the table does not see.
  • The main search partly repeats the top link. Reusing that link would roughly halve the proof text.

Glossary

assertion
A formula given to the solver with assert, claimed to be true.
atom
A formula with no Boolean connective inside, such as (< x 3) or a Boolean variable b.
Boolean
The sort of truth values, true and false.
case split
Proving a goal separately for each possibility, such as once with c true and once with c false.
clause
A disjunction of literals. A unit clause has a single literal, like (< z0 3).
congruence
The rule that equal inputs give equal outputs: if a = b, then f a = f b.
contradiction, proof by
Assume the opposite of the goal and derive False.
disjunction
An “or” of formulas, true when at least one of them is true. Each formula is an operand.
double negation
“Not not p”, which classically means the same as p.
flattening
Rewriting (or (or a b) c) as (or a b c). Nothing changes in meaning, only in shape.
grind
A general-purpose Lean tactic that combines case splits, congruence, and arithmetic.
heartbeat
Lean's unit of work. A proof that uses more than the limit is stopped with a timeout error.
iff
“If and only if”: both sides are true or both are false. Written <-> in Lean.
if-then-else term (ite)
A term (ite c a b) whose value is a when c holds and b otherwise.
kernel
The small core of Lean that checks every proof step. It is the only part that must be trusted.
lemma
A helper theorem proved on the way to the main theorem.
linear arithmetic
Arithmetic with sums of variables times constants, such as 2x + y ≤ 3, and no products of variables.
literal
An atom or the negation of an atom.
normalized rewrite
The reconstructor's way to prove a rewrite: put each atom into one canonical linear form, then prove the remaining propositional equivalence.
propositional
About how atoms are combined with and, or, not, and iff, ignoring what the atoms mean.
QF_LRA
The SMT-LIB logic of quantifier-free linear real arithmetic.
refutation
A proof that a set of assertions implies False.
rewrite
A step where Z3 simplifies a formula and claims the new form is equivalent to the old one.
sort
The type of a value, such as Int, Real, or Bool.
tactic
A Lean command that builds part of a proof automatically.
xor
“Exclusive or”: true when exactly one of two formulas is true.
