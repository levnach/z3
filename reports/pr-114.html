Name hypotheses by binders and close resolutions with resolve_right

Pull request levnach/z3#114 · OPEN · 2026-11-11T04:32:50Z · loop iteration 113

This PR is open and not merged. The change it proposes is commit eaf5bf8.

In one paragraph

This PR makes the Lean text that the reconstructor writes for a proof certificate smaller, without changing what it proves. Two kinds of redundant text go away. First, a hypothesis is no longer bound as its own proof step. The steps that use it now name its binder directly. Second, a unit resolution that keeps one literal and eliminates every literal after it now uses Or.resolve_right instead of a case split. The theorem and lemma statements stay the same, and Lean still checks every term. This matters because Lean's memory during elaboration grows with the text. Large refutations are close to, or over, the 8 GB cap of the checker.

Background

Before this PR, the pipeline already verified the QF_IDL logic benchmark plan-21 under the 8 GB cap, with little room to spare. Larger refutations, such as the QF_IDL benchmark DTP_k2_n35_c245_s9, still ran out of memory. The previous iteration had moved each proof step under hypotheses into the one step that uses it. Its notes said that what remained in DTP was mostly shared steps and Or.elim resolution terms. This PR removes part of that text. It serves milestone 3 of the plan, equality and linear arithmetic, by keeping large arithmetic refutations checkable.

What changed

  • Reconstructor. A proof step that uses a hypothesis now refers to the hypothesis's binder, so no extra let binding and no one-line lemma fun _hypN => _hypN is written for it.
  • Reconstructor. When every literal after the last kept one in a clause is eliminated or false, the resolution now concludes that literal in one step, with no case split.
  • Reconstructor. The one exception is the premise of a lemma step, which keeps its own step because the lemma discharges the hypothesis there.
  • Tests. New Lean-checked tests now pin nine clause shapes for the new resolution form and the lemma-premise exception, and the size limits on a DTP-style test are tighter.
  • Docs. The plan document and the examples README now describe both changes and the new file sizes.

An analogy for the second change: once every suspect but one is ruled out, you name that suspect directly instead of reopening each case.

Worked example

This PR shrinks the text for inputs that already worked, so no input was rejected before and accepted now. The example is a small input that the old and new code both certify, from real runs of both versions. The certificate was identical, and only the Lean text changed.

(a) The input

(set-logic QF_LRA)
(declare-const p Bool) (declare-const q Bool)
(declare-const x Real) (declare-const y Real) (declare-const z Real)
(assert (or p q))
(assert (not q))
(assert (or (not p) (< x y) (< y z)))
(assert (or (>= x y) (< z x)))
(assert (or (>= y z) (< z x)))
(assert (<= x z))
(check-sat)

From p ∨ q and ¬q we get p, so x < y or y < z. Either way z < x follows, which contradicts x ≤ z.

(b) Before: what the base code generated

The old reconstructor did not reject this input. It wrote a longer file that Lean accepted. These are its lines for the two steps shown below:

  let _step_41 : (formula_11 _atoms _vars) :=
    (Or.elim _step_33 (fun _literal => _literal) (fun _tail => (False.elim (_tail _step_39))))
...
  let _step_44 (_hyp4 : (formula_4 _atoms _vars)) : (formula_43 _atoms _vars) :=
    let _step_40 : (formula_4 _atoms _vars) :=
    _hyp4
    (False.elim (_step_18 (_step_17.resolve_left _step_40)))

The first step opens a case split with two branches. The second step copies the hypothesis _hyp4 into a new name, _step_40, only to use it once.

(c) After: what the reconstructor generates now

...
def formula_4 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := (Not (formula_0 _atoms _vars))
...

...
def formula_16 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := ((term_5 _atoms _vars) <= (term_8 _atoms _vars))
...
def formula_29 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := (Not (formula_16 _atoms _vars))
def formula_30 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := (Or (formula_11 _atoms _vars) (formula_29 _atoms _vars))
...
def formula_43 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := False

Each formula becomes a Lean definition: formula_0 is p, formula_11 is x ≥ y, and formula_30 is the clause x ≥ y ∨ ¬(x ≤ z).

theorem unsat (_atoms : Nat -> Prop) (_vars : Nat -> Rat)
    (_h0 : (formula_2 _atoms _vars))
    (_h1 : (formula_3 _atoms _vars))
    ...
    (_h5 : (formula_16 _atoms _vars))
    : False :=

The theorem says that for every value of the Boolean atoms and the variables, the six assertions together imply False.

  let _step_41 : (formula_11 _atoms _vars) :=
    (_step_33.resolve_right (fun _literal => _literal _step_39))

The clause x ≥ y ∨ ¬(x ≤ z) and the assertion x ≤ z now give x ≥ y in one step, with no case split.

  let _step_44 (_hyp4 : (formula_4 _atoms _vars)) : (formula_43 _atoms _vars) :=
    (False.elim (_step_18 (_step_17.resolve_left _hyp4)))
...

Under the hypothesis ¬p, the clause p ∨ q gives q, which contradicts ¬q, and the step now names the hypothesis by its binder _hyp4.

Review

The reviewer approved the PR. There were no blockers, no major findings, and no minor findings.

  • Nit: stale figures. The slow plan-21 test's comments still said 25 MB and 7.5 GB. Someone tuning the memory cap could trust these old numbers. They now say 23.4 MB and 7.0 GB.
  • Nit: awkward wording. The README and two docstrings said a hypothesis "is no step". It now says "not bound as a step".
  • Suggestion: pin the exception. The reviewer tried a hypothesis that is a lemma's premise and is also used by another step. It passed, but no committed test covered this path. The integrator added a Lean-checked test for it.
  • Suggestion: avoid the text rewrite. The new code finds hypothesis references with a regular expression over generated text. The reviewer suggested resolving them while building each term. This is a follow-up. It is safe today because every name there is generated, and a wrong reference fails the Lean check.

The reviewer also checked four edge cases in Lean, including a conjunction used as a hypothesis. All passed.

Risks and open questions

  • Soundness should be unchanged. The statements are the same, and an out-of-scope binder is a Lean error.
  • The text rewrite depends on how generated steps are named. A naming change could break it, though Lean would catch the error.
  • DTP and the swap benchmark still exceed the 8 GB cap, and plan-21 passes close to it.
  • The local gate and CI results were unknown when this page was written.

What comes next

  • Merge each import of a shared step under hypotheses with its one re-application. The PR estimates about 1 MB of DTP.
  • Shrink the chains of hypotheses in the lemma statements, which the PR measures at 4.66 MB of DTP.
  • Resolve hypothesis references while building terms, instead of rewriting the text afterwards.

Glossary

atom
A formula with no Boolean connective inside it, such as p or x < y.
binder
A name introduced for a value inside a term, such as h in fun h => .... It can only be used inside that term, which is its scope.
Boolean
The sort with two values, true and false. In the example, p and q are Boolean atoms.
case split
Proving a goal from A ∨ B by proving it once assuming A and once assuming B. In Lean this is Or.elim.
clause
A disjunction of literals, such as p ∨ ¬q ∨ r. It is true when at least one literal is true.
conjunction
An "and" of formulas, such as A ∧ B.
discharge
To remove a hypothesis from a proof by turning it into the premise of a statement. From a proof of False under A, the lemma rule concludes ¬A with no hypothesis left.
disjunction
An "or" of formulas, such as A ∨ B.
elaboration
The phase in which Lean turns the source text of a proof into fully typed terms before checking them.
hypothesis
A formula assumed temporarily inside a proof, so that a later step can show it leads to a contradiction.
lemma
A proven statement used as a building block. In Z3's proofs, the lemma rule also discharges hypotheses. The reconstructor checks large shared steps as separate Lean lemmas.
let binding
A Lean line let name : type := value that gives a proved fact a name so later steps can use it.
literal
An atom or its negation, such as p or ¬(x ≤ z).
logic (SMT-LIB)
A named fragment of formulas a benchmark uses. QF_LRA is quantifier-free linear real arithmetic. QF_IDL is quantifier-free integer difference logic, with constraints like x - y ≤ 3.
proof certificate
A file of proof steps that Z3 exports for an unsat result, so another tool can check them.
proof step
One inference in a proof, with its premises and its conclusion.
refutation
A proof that a set of assertions leads to False.
sort
The type of a value, such as Int, Real, or Bool.
unit resolution
An inference that removes literals from a clause using facts that refute them. From p ∨ q and ¬q it concludes p.
