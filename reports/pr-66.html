Certify uninterpreted functions next to Int and Real (qf_uflira)

Pull request #66 on levnach/z3 · state OPEN · 2026-11-03T19:06:02Z · loop iteration 66

This pull request is open and not merged. The change it proposes is commit aafcbbb65. The PR contains two commits on top of base 0bac76fe1: the feature itself and a fix found in review.

In one paragraph

Z3 inputs that mix uninterpreted functions with both the Int and the Real sort can now be certified in Lean. Before this PR the exporter stopped at the first such input. Now these inputs form a new fragment called qf_uflira. The Lean theorem gets one valuation per number sort, and its interpretation gets one injection per number sort. A function application now counts as a single atom. So a Farkas lemma or congruence step over (f n) is no longer mistaken for mixed-sort arithmetic. Every lemma is still checked by the Lean kernel, so the trust boundary does not move.

Background

The previous three PRs (#62 to #64) certified qf_lira, where Int and Real terms sit side by side, linked by to_real, to_int, and is_int. Uninterpreted functions were also certified, but only next to one number sort at a time (qf_uflia or qf_uflra). An input with a function such as f : Int -> Real, or a predicate over both sorts, was rejected. The Lean encoding had room for only one numeric injection and one function family. This PR serves milestone 3, "Equality and linear arithmetic", whose rule is to finish each fragment end to end before adding another.

What changed

  • The exporter now labels inputs with uninterpreted sorts or functions next to both Int and Real as qf_uflira instead of rejecting them, and the fragment is opt-in like the other integer fragments.
  • Both proof cores, the clause log and the legacy proof object, can now be turned into Lean for this fragment.
  • Each function argument enters the shared carrier through the injection of its own sort, and each result is valued by the function family of its own sort.
  • Arithmetic lemmas treat (f n) as one atom whatever its argument sorts are. Think of a sealed envelope: arithmetic sees the envelope, not the letter inside.
  • Helpers that equate two function arguments now group them by sort, so an Int if-then-else term is never equated with a Real one.
  • A new test file covers five documented inputs, a random generator, and checks that run without Lean.

Review

Major: an ill-sorted helper. The reviewer wrote an input where f takes an Int and g takes a Real. Both were applied to the same condition, as (ite c 1 0) and (ite c 1.0 0.0). The two arguments share one linear form, so the reconstructor grouped them and wrote a helper claiming an Int equals a Real. Lean could not prove that helper, and the check failed on both cores. This was fail-closed, so nothing false was certified, but a simple input could not be certified at all. The fix adds the sort to the grouping key. The reviewer's input became a test, next to a check that no helper equates terms of two sorts.

Nit: an incomplete error message. A message listed only qf_lia and qf_uflia as Int fragments. It now also names qf_lira and qf_uflira.

Nit: README drift. The legacy-core paragraph listed two opt-in integer fragments instead of four. It now lists all four.

Risks and open questions

  • A known gap, shared with qf_lira: an Int if-then-else term whose condition compares Reals, or the reverse, still gets its theory step rejected. This is fail-closed and was not introduced here.
  • Most random inputs are refuted by preprocessing and congruence, so wider arithmetic shapes are untested.
  • No z3test regression file is in this fragment, so the proof matrix does not exercise it.
  • Nothing states that the Int and Real injections have disjoint images. The PR argues that nothing needs it.

What comes next

  • Treat if-then-else conditions as their own sort when classifying a step, to close the known gap.
  • Write a QF_UFLIRA generator that needs more theory reasoning.
  • Handle other operators that are still rejected, such as ^ of numerals, enumeration datatypes, and unary + in the clause log.

Glossary

atom
The smallest unit an arithmetic step reasons about, such as a variable x or an application (f n).
carrier
The set of values an interpretation works over. Here it is the Lean type _m.U.
clause
A disjunction of literals, such as a or not b or c.
clause log
One of Z3's two proof cores. It records each clause the solver learns, with a hint about why it holds.
congruence
The rule that equal arguments give equal results. If n = 3, then (f n) = (f 3).
cut
An Int step that uses the fact that integers have no values between them. Example: from 2k = 1 conclude False.
fail-closed
A failure that rejects a valid proof rather than accepting a false one. It costs coverage, not soundness.
Farkas lemma
A proof that some linear inequalities contradict each other. Multiply each by a nonnegative number and add them to get 0 < 0.
fragment
A family of inputs defined by which sorts and operators they use, such as qf_lira or qf_uflira.
if-then-else term
A term whose value depends on a condition. (ite c 1 0) is 1 when c holds and 0 otherwise.
injection
A map that sends different values to different values. Here it turns an Int or Real argument into a carrier value.
interpretation
A choice of meaning for every uninterpreted sort, function, and predicate. In the Lean file it is the structure _m.
kernel
The small core of Lean that checks every proof step. Tactics only suggest steps, and the kernel accepts or rejects them.
lemma
A helper fact proved separately and then used in a larger proof.
linear form
A sum of atoms times numbers, such as 2x + 3y - 1.
literal
An atom or its negation, such as (= n 3) or (not (= n 3)).
predicate
An uninterpreted function whose result sort is Bool, the sort of true and false.
proof object
The legacy proof core of Z3. It builds a tree of named rules such as mp, th-lemma, and unit-resolution.
refutation
A proof that a set of assertions implies False.
sort
The type of a value, such as Int, Real, Bool, or a declared sort U.
tactic
A Lean command that searches for a proof, such as omega or grind.
theory lemma
A clause justified by a theory such as arithmetic or equality, not by Boolean reasoning alone.
trust boundary
The line between what must be trusted and what is checked. Here only the Lean kernel and the input encoding are trusted.
uninterpreted function
A function with a declared signature but no definition, such as (declare-fun f (Int) Real). Only congruence is known about it.
uninterpreted sort
A sort declared with no structure, such as (declare-sort U 0).
valuation
An assignment of a value to every variable. Here _vars values Real variables and _ivars values Int ones.
