Omit redundant mod bounds from re-derived Int Farkas lemmas in Lean

Pull request levnach/z3#31 into master · OPEN · opened 2026-10-22T16:33:50Z · loop iteration 31

This pull request is open and not merged. The change under review ends at commit 62bf7fc9f. It contains two commits: the main change and a follow-up that answers the review.

In one paragraph

When the Lean reconstructor proves an Int theory lemma over mod terms, it treats each atom as an opaque variable and calls the omega tactic. Before this PR it first stated two bounds for every mod atom, such as 0 ≤ (x mod 3) < 3. For a Farkas lemma that carries its coefficients, those bounds are useless. Python has already checked that the coefficients form a linear combination that reaches a contradiction over the bare atoms. The bounds only made omega do extra case analysis. This PR drops them for such lemmas, and keeps them for cuts and the other cases that need them. On one large QF_UFLIA certificate, Lean's check time fell from 48 s to 22 s. That matters because a lemma twice as wide could have run out of heartbeats, so a correct refutation would have gone uncertified.

Background

Before this PR, the pipeline already certified Int theory lemmas over div, mod and abs atoms. It did this by generalizing the atoms and calling omega, with the mod bounds always in context. A stress run at twice the usual instance size found no rejected input. It did find one input that Z3 solves in seconds but that spent most of its Lean time on a single 33-literal Farkas lemma over 26 atoms. The pipeline was therefore sound on that input but close to a completeness gap. The work serves milestone 3 of the project plan, "Equality and linear arithmetic".

What changed

  • A Farkas or bound theory lemma with coefficients now reaches omega without any mod bounds, so wide lemmas check much faster.
  • Cuts, lemmas without coefficients, and theory rewrites still get the bounds, because nothing else justifies them.
  • A new test runs a large random instance (seed 75) through Z3, the certificate exporter and the Lean kernel, then checks the shape of every generalized lemma.
  • The README and the project plan now say exactly when the bounds are stated, with timings measured on an idle machine.

The reconstructor change is small. A new helper, _combination_certified, recognizes the steps that Python has already re-derived. For those steps, the lemma builder skips the bound facts. Think of a teacher who has already checked a student's sum line by line. Handing the grader a list of extra hints about each number only slows the grader down. No Lean files and no C++ code changed.

Worked example

This PR is a speed-up, not a new capability. The old code also accepts every small input, including this one. So "Before" below shows the lemma the old code generated, not an error. The real slowdown only shows up on large inputs like seed 75; see the timing table under "How it was verified".

(a) The input

(declare-const x Int)
(declare-const y Int)
(assert (>= (mod x 3) 1))
(assert (>= (mod y 3) 1))
(assert (<= (+ (mod x 3) (mod y 3)) 1))
(check-sat)

Two mod terms are each at least 1, yet their sum is at most 1, so the assertions are contradictory.

Z3 explains the contradiction with a theory lemma recorded as th-lemma farkas 1 1 1. The three ones are the coefficients: add the three inequalities once each and you get 2 ≤ 1.

(b) Before: the lemma the pre-PR reconstructor generated

  unfold formula_48 formula_47 formula_46 formula_45 formula_41 formula_36 formula_22 term_8 term_3
  first
    | (have _m0_0 : ((0 : Int)) <= (term_6 _atoms _vars) := by unfold term_6 term_5 term_1; exact Int.emod_nonneg _ (by decide)

       have _m1_0 : ((0 : Int)) <= (term_2 _atoms _vars) := by unfold term_2 term_1 term_0; exact Int.emod_nonneg _ (by decide)
       have _m1_1 : (term_2 _atoms _vars) < ((3 : Int)) := by unfold term_2 term_1 term_0; exact Int.emod_lt_of_pos _ (by decide)

The four have lines state 0 ≤ m < 3 for both mod atoms before omega runs, although the proof never needs them.

Lean accepted this old file too. Running the pre-PR reconstructor on the input produced no error.

(c) After: what the reconstructor generates now

def term_2 (_atoms : Nat -> Prop) (_vars : Nat -> Int) : Int := ((term_0 _atoms _vars) % (term_1 _atoms _vars))
...
def term_6 (_atoms : Nat -> Prop) (_vars : Nat -> Int) : Int := ((term_5 _atoms _vars) % (term_1 _atoms _vars))
...
def formula_48 (_atoms : Nat -> Prop) (_vars : Nat -> Int) : Prop := (Or (formula_45 _atoms _vars) (Or (formula_46 _atoms _vars) (formula_47 _atoms _vars)))

The two mod atoms become term_2 and term_6, and formula_48 is the lemma's clause of three negated literals.

private theorem th_lemma_49 (_atoms : Nat -> Prop) (_vars : Nat -> Int)
    : (formula_48 _atoms _vars) := by
  unfold formula_48 formula_47 formula_46 formula_45 formula_41 formula_36 formula_22 term_8 term_3
  first
    | (generalize (term_6 _atoms _vars) = _o0
       generalize (term_2 _atoms _vars) = _o1
       omega)
    | (unfold term_6 term_5 term_2 term_1 term_0
       first | omega | grind (splits := 64))

Review

The reviewer approved the PR. There were no blocker or major findings.

  • Minor, fixed. The reviewer read the README while checking the change. It still said the mod bounds are stated before omega on every step. A maintainer chasing a slow lemma would have been misled. The paragraph now says the bounds appear only on the grind path, that is, for cuts and lemmas without coefficients.
  • Nit, fixed. The new test reused the constant name WIDE_DIVISION_SEED, which another test file uses for a different seed. Someone searching for it after a failure could land in the wrong place. It is now WIDE_FARKAS_SEED.
  • Nit, fixed. The reviewer re-timed the seed-75 file and could not reproduce the headline "140 s". That number was measured while the stress run loaded the machine. The plan note, docstring and test comment now give the idle figures and label the loaded ones.
  • Nit, kept on purpose. The test pins details of Z3's explanation on one seed, such as at least 14 mod atoms in the widest lemma. An unrelated Z3 change could break it. The author kept it because it proves the test really exercises the wide case, as earlier seed-pinned tests do.

Risks and open questions

  • Soundness is not at risk. Only ordinary have lines were removed, and missing facts can make a proof fail, never succeed wrongly. Nothing new is trusted.
  • If Python's re-derivation and Lean's generalized goal ever disagreed, the fast attempt would fail. The unchanged fallback, which unfolds the atoms, would then run.
  • The new test depends on Z3's explanation shape for one random seed, as discussed under Review.
  • The Lean CI step becomes about 50 s longer.

What comes next

  • Build a direct Farkas proof term from the coefficients, so these lemmas no longer depend on omega's heuristics.
  • Profile the other slow stress-run certificates (lia-ite79, lia-ite88, legacy lia-ite86). Their timings were inflated by load.
  • Widen the SMT-LIB frontend for get-value after check-sat and for commands after exit.

Glossary

atom
A term the arithmetic reasoning treats as one unknown, such as (mod x 3) or f(y).
bound
A fact limiting a value's range, such as 0 ≤ (x mod 3) < 3. In Z3 hints, "bound" also names a lemma kind that combines bounds.
case analysis
Proving a goal by splitting into cases and handling each one, for example one case per possible value of a bounded variable.
certificate
The proof data Z3 exports, which the reconstructor turns into a Lean file.
clause
A disjunction of literals, read as "at least one of these holds". Example: ¬a ∨ ¬b ∨ c.
coefficient
A number that multiplies a term or inequality. In 2x + 3y, the coefficients are 2 and 3.
completeness
The property that every correct proof can be checked. A timeout on a valid lemma is a completeness gap.
cut
An integer step that rounds a bound. Example: from 2x ≤ 3 over integers, conclude x ≤ 1.
Farkas lemma
A theory lemma showing linear inequalities are contradictory. Adding them with suitable non-negative coefficients gives a false statement such as 0 < 0.
generalize
A Lean tactic that replaces a term by a fresh variable, forgetting what the term was.
grind
A general-purpose Lean tactic that combines congruence closure, case splits and arithmetic.
heartbeat
Lean's unit of work. A proof that exceeds the maxHeartbeats limit is stopped and fails.
linear combination
A sum of terms each multiplied by a constant, such as 1·a + 1·b + 1·c.
literal
An atomic formula or its negation, such as x ≥ 1 or ¬(x ≥ 1).
mod
The remainder of integer division. In SMT-LIB, (mod 7 3) is 1, and the result is always between 0 and the divisor's absolute value minus one.
omega
A Lean tactic that decides linear integer arithmetic goals.
QF_UFLIA
The SMT-LIB logic of quantifier-free formulas with uninterpreted functions and linear integer arithmetic.
refutation
A proof that a set of assertions leads to False.
soundness
The property that the checker never accepts a wrong proof.
tactic
A Lean command that builds part of a proof automatically, such as omega or grind.
theory lemma
A clause that holds because of a background theory such as integer arithmetic, not because of Boolean logic alone.
uninterpreted function
A function symbol with no fixed meaning, only that equal inputs give equal outputs. The "UF" in QF_UFLIA.
