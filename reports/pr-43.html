Check euf and tseitin steps over Boolean constants natively

Pull request levnach/z3 #43 · State: OPEN · Date: 2026-10-29T00:45:57Z · Loop iteration 43

This pull request is open and not merged. The change under review is commit 64e6e8c3f on top of master at c95b61cb0.

In one paragraph

Z3 can write a clause log and later replay it with its own native checkers. Two of those checkers gave up on common steps and passed them to the slower SMT fallback. The euf checker could not see congruence through a negated Boolean argument of an uninterpreted function. The tseitin checker did not know the values of the constants true and false inside a gate clause. It also missed clauses that are tautologies, and a trivial if-then-else term whose two branches are the same. Now both checkers verify these steps themselves, and on 692 test logs these fallbacks drop to zero. Lean certificates do not change, because Lean already checked these steps. The gain is a more complete native certificate and a cleaner regression signal.

Background

Before this PR, Python export and Lean reconstruction already handled these inputs. Z3's native replay did not. It marked 28 euf steps and 700 tseitin steps, in 165 of 692 logs, as verified-smt. The regression matrix counts such steps as unverified fallbacks, so they hid real gaps among the noise. The euf gap was a backlog item from iteration 42. The work serves milestone 3, equality and uninterpreted functions, and the regression methodology that gates it. It strengthens the C++ checker that the plan keeps for diagnostics.

What changed

  • Euf checker: it now accepts (pb (not q)) = (pb true) when the hint fixes q to false, reading through any number of negations.
  • Tseitin checker, constants: it now treats true, false and (not true) as fixed values inside every gate rule, so a constant needs no literal of its own.
  • Tseitin checker, tautologies: it now accepts any clause that holds a literal and its negation, or a literal that is always true.
  • Tseitin checker, if-then-else: it now accepts (= (ite c a a) a), where both branches equal the right-hand side.
  • Tests and notes: new C++ and Python regression tests fail on the old build and pass on the new one, and the project plan has a dated note.

An analogy for the constants rule: a gate with an input wired straight to power always sees "on". The old checker wanted a label on that wire before it would trust it. The new checker reads the wire directly.

Worked example

This PR changes native checkers, not Lean reconstruction. So the example shows a real clause log, replayed by the old and new Z3 builds. The input is the first case of the new Python test.

(a) The input

(declare-const q Bool)
(declare-fun pb (Bool) Bool)
(assert (not q))
(assert (pb true))
(assert (not (pb (not q))))
(check-sat)

Since q is false, (not q) is true, so (pb (not q)) and (pb true) must agree. The assertions say they do not.

The new Z3 build wrote this euf step in the clause log, shown here unchanged:

(define-const $7 Bool (pb true))
(define-const $6 Bool (not q))
...
(define-const $8 Bool (pb $6))
...
(define-const $11 Bool (= $7 $8))
(define-const $12 Proof (cc $11))
(define-const $9 Bool (not $8))
(define-const $13 Proof (euf $7 $9 $6 $12))
(infer (not $7) $8 (not $6) $13)

The step claims the clause "not (pb true), or (pb (not q)), or q". Its hint gives one congruence step, (pb true) = (pb (not q)).

(b) Before: replay with the base build

(proofs +tseitin 1)
(proofs +tseitin 1 -euf 1)
(verified-smt
(euf (pb true) (not (pb (not q))) (not q) (cc (= (pb true) (pb #23))))
 (not (pb true))
 (pb (not q))
 (not (not q)))
(proofs +tseitin 1 +rup 1 -euf 1)
not congruent (cc (= (pb true) (pb (not q))))

The euf checker rejected the congruence step as "not congruent", so the step went to the SMT fallback and was counted as -euf 1.

(c) After: replay with this PR

(proofs +tseitin 1)
(proofs +tseitin 1 +euf 1)
(proofs +tseitin 1 +euf 1 +rup 1)

Every step, including the euf step, now verifies natively, and there is no verified-smt line.

The new C++ regression test replays a log of the same shape, with the negation on the other side:

"(assume s)(assume $2)(assume (not $3))"
...
"(infer $1 $3 (not $2) (euf $2 s (not $3) (cc (= $2 $3))))"
...
"(declare-fun rup () Proof)(infer rup)"), "euf 1");

Here $2 is (pb (not s)) and $3 is (pb false), and the test requires native verification.

The Lean path is unchanged. For this input, the current reconstructor wrote a Lean file that check_lean.sh accepted: "Lean checks passed." I could not rerun the base-commit Python scripts here, but the PR does not touch them.

Review

The reviewer approved with no blocker, major, minor or nit findings.

The reviewer's main worry was soundness. Giving constants a value changes two helper tests that every tseitin gate rule reads. So the reviewer walked through each rule for and, or, =, ite, => and xor. They checked that no term can look both true and false at once. The new first pass returns early in every such case, so the rules always see a consistent assignment.

Next, the reviewer tried to fool the checker with 15 false look-alikes, such as (= (ite p a b) b). The new build rejected all 15 and accepted 5 valid shapes. The new Python test failed on the base binary, as it should.

Two suggestions left the code unchanged. The Python test runs only in one CI job, but the C++ tests run everywhere and were judged enough. An older debug print in the tseitin checker is noisy. It predates this PR and is a follow-up.

Risks and open questions

  • The native checkers accept more steps. A wrong acceptance would be a soundness bug in Z3's certificates, but not in Lean's.
  • The constant values apply to every tseitin gate rule at once.
  • The Python test depends on how Z3 clausifies four inputs today. If that changes, the test fails loudly.
  • Only UF-family generators were scanned. LRA and LIA ite generators and the SMT-LIB sample may show other tseitin shapes.
  • CI results for this PR are not known to this report.

What comes next

Glossary

Boolean
The sort with exactly two values, true and false. In SMT-LIB it is written Bool.
certificate
A record of a proof that a separate checker can verify step by step.
clause
An "or" of literals. It holds when at least one of its literals is true. Example: q or not p.
clause log
A file in which Z3 writes each clause it learns, together with a hint saying why the clause holds.
congruence
The rule that equal arguments give equal results. If a = b, then f(a) = f(b).
constant
A fixed value such as true, false or 3. A declared name like q is also called a constant in SMT-LIB, but here the word means a fixed value.
cut
A step in integer arithmetic that rounds a bound to the nearest integer, such as going from 2x ≤ 3 to x ≤ 1.
euf
Equality with uninterpreted functions. It is the theory, and the Z3 checker, that reasons about equalities and congruence.
gate clause
A clause that ties a compound formula, such as (or a b), to its parts. Example: "not a, or (or a b)".
hint
The justification attached to a step in a clause log. It tells the checker which rule and which facts to use.
if-then-else term
A term (ite c a b) that equals a when c is true and b otherwise.
literal
A Boolean atom or its negation, such as q or (not q).
native checker
A checker written in C++ inside Z3 that verifies one kind of step, such as euf or tseitin steps, without calling the solver.
reconstruction
Turning a Z3 proof into a Lean proof that Lean then checks on its own.
replay
Reading a clause log back and checking each step in order.
SMT fallback
When no native checker accepts a step, Z3 proves the step by running its solver again. Z3 marks such steps verified-smt. This works, but it trusts the solver.
sort
The type of a value, such as Int, Real or Bool.
soundness
A checker is sound if it never accepts a false step.
tautology
A formula that is true under every assignment. Example: q or not q.
tseitin
The Tseitin encoding turns a formula into clauses by naming each compound part and adding gate clauses for it. In Z3 it is also the name of the checker for those gate clauses.
uninterpreted function
A function symbol with no fixed meaning. The solver only knows that it gives equal results for equal arguments. Example: pb in the worked example.
