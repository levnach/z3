In one paragraph

Z3 can now hand Lean a checked refutation for inputs that use arrays whose element sort is an enumeration datatype, such as (Array Int Color). Before this PR, the exporter rejected every such input. Z3's datatype solver makes a case split on a select from such an array: the value is red, green, or blue. Lean must also know that fact, or it cannot check the theory lemmas in the clause log. The PR adds two kinds of field to the Lean interpretation and two small prelude theorems. For each read that a lemma needs, the exporter now builds a proof term that the kernel checks. No sorry, no new axiom, and no .lean file was added.

Background

Iteration 80 taught the pipeline about enumeration datatypes. Lean then knew the possible constructors of constants and of uninterpreted function applications. It knew nothing about reads from arrays, so any array sort that mentioned an enumeration was still rejected. That gap was on the backlog as "Arrays and maps over enumerations". This PR closes the main part of it. It serves milestone 4 of the plan, "Broader theories and integration", where arrays are one of the named extensions.

What changed

  • You can now certify inputs over (Array I Color) with Int, Real, Bool, uninterpreted, or array indices, using constants, functions into and over such arrays, store, ite, select, equality, and extensionality.
  • The Lean interpretation now promises, for each array constant and each function into such arrays, that every read is one of the constructors.
  • Two new prelude theorems let the exporter carry that promise through stores and ite terms, down to the read a lemma actually uses.
  • The clause-log replay now learns an enumeration's constructors from an array's element sort, even when no plain constant of that sort appears.
  • Inputs still out of scope get their own clear rejection message: arrays indexed by an enumeration, nested arrays of one, constant arrays, default values, and maps over them.

An analogy for the new fields: think of a warehouse where every box carries a label saying "contains red, green, or blue". A store swaps one box's contents for another color. The prelude theorem _cases_store says the label stays true after the swap.

Worked example

This input is the read_of_a_store case from the PR's new tests. It reads one cell of an array after a store and says the cell is not red, not green, and not blue. That is impossible, so Z3 reports unsat.

(a) The input

(declare-datatypes ((Color 0)) (((red) (green) (blue))))
(declare-const a (Array Int Color))
(declare-const i Int)
(declare-const j Int)
(declare-const c Color)
(assert (not (= (select (store a i c) j) red)))
(assert (not (= (select (store a i c) j) green)))
(assert (not (= (select (store a i c) j) blue)))
(check-sat)

The exporter from the PR's base commit stopped at once:

These declarations encode (store a i c) and the read (select (store a i c) j).

private theorem _cases_store {I E : Type} (P : E -> Prop) (a : I -> E) (i : I) (v : E) (j : I)
    (ha : P (_select a j)) (hv : P v) : P (_select (_store a i v) j) := by
  rw [_store_apply]
  split <;> assumption

If the old array's read and the stored value both satisfy P, the read after the store does too.

private theorem th_lemma_24 (_atoms : Nat -> Prop) (_vars : Nat -> Int) (_m : Interpretation)

  unfold formula_23 formula_13 term_12 formula_10 term_9 formula_7 term_6 term_5 term_4

Review

The reviewer approved the change with no blocker and no major finding. Three smaller findings came up.

  • Minor: deep store chains crashed. The reviewer fed in a read through 1,100 nested stores. The new read walk called itself once per store and hit Python's recursion limit. The user got a raw traceback instead of a certificate or a clean rejection. The deep-input tests promise that nesting depth never breaks the exporter. The fix rewrote the walk with an explicit stack and added a 1,100-level regression test. That test checks reconstruction only, because Lean hits its heartbeat limit on 1,100 enumeration constants. A 200-level chain passes Lean.
  • Minor: "all verify" was too strong. The reviewer swept a deeper random configuration with uninterpreted indices. About 1 in 10 unsat seeds failed Lean with a grind error. The cause is older than this PR: a read through an ite over a store gets no store fact. The same failure appears for (Array Int Int) with the base commit. It is not a soundness problem, because Lean rejects rather than accepting something false. The plan now names the failing seeds and records the fix as backlog.
  • Nit: README wording. One sentence was badly wrapped and the list of operations left out two items. Both were fixed.

Risks and open questions

  • The new fields are sound only because of how a model's arrays are embedded in Lean. Outside the index sort, every array takes one fixed constructor. The reviewer checked this argument and found no problem.
  • The ite-over-store gap still makes some inputs fail Lean. This affects every element sort, not just enumerations.
  • An input with about 1,000 enumeration constants exceeds Lean's heartbeat limit. That limit comes from iteration 80's per-constant fields.
  • Each read gets its own proof term, linear in its store chain, with no sharing. Large inputs were not measured.
  • The random generator rarely needs the new read facts. Only 1 of 14 seeds with datatype hints failed without them.

What comes next

  • Walk ite branches in the shared array helpers, with seed 219 as the regression input.
  • Arrays indexed by an enumeration. These need a Lean index type with exactly the constructors.
  • Constant arrays, default values, and maps over arrays of an enumeration.
  • Arrays of an enumeration nested inside other arrays.
  • A random generator that compares reads only with reads and constructors, to test the new walk harder.

Glossary

array
A total map from an index sort to an element sort. (Array Int Color) gives a color for every integer.
case split
Reasoning by trying each possible value in turn. "x is red, or green, or blue" splits into three cases.
clause
A disjunction of literals, such as p or not q.
clause log
The record of clauses Z3 learns or uses while solving, each with a hint saying why it holds.
constructor
One of the named values of a datatype. red, green, and blue are the constructors of Color.
enumeration datatype
A datatype whose constructors take no arguments, so it has a fixed finite list of values.
extensionality
Two arrays are equal exactly when they agree at every index.
heartbeat limit
Lean's cap on how much work one declaration may take before it gives up.
if-then-else term (ite)
A term that takes one of two values depending on a Boolean condition, such as (ite p a b).
interpretation
An assignment of meanings to the input's symbols. Here it is a Lean structure, and the final theorem holds for every interpretation.
kernel
Lean's small trusted core that checks every proof term.
literal
An atomic formula or its negation, such as x = red or not (x = red).
model
An interpretation that makes all assertions true.
proof term
A proof written as an explicit expression that the kernel checks directly, without search.
refutation
A proof that a set of assertions leads to False.
select
Reading an array at an index. (select a j) is the value of a at j.
sort
The type of a value, such as Int, Bool, or Color.
soundness
The checker never accepts a false claim.
store
Writing a value into an array. (store a i c) is a with index i changed to c.
tactic
A Lean command that searches for a proof, such as grind or omega.
theory lemma
A clause that holds because of a theory, such as arrays or datatypes, rather than by pure Boolean logic.
uninterpreted function
A function symbol with no fixed meaning, only that equal arguments give equal results.
uninterpreted sort
A sort declared with no fixed values, such as (declare-sort U 0).
