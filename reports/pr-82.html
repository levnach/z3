Certify arrays of enumerations in Lean through the clause log

Pull request levnach/z3 #82 · state OPEN · 2026-11-07T02:08:13Z · loop iteration 82

This pull request is open and not merged. The change under review is commit 2216463fc, the last of three commits in the PR.

In one paragraph

Inputs that use an array whose element sort is an enumeration, such as (Array Int Color), can now be certified in Lean through the clause log. Z3 proves such inputs with a case split on each select: the read is red, green, or blue. Lean must therefore know that every read is one of the constructors. The interpretation now states this for each array constant. For reads through a store or an if-then-else term, the reconstructor builds a small proof term that the kernel checks. No sorry or new axiom is added, so each accepted refutation stays fully checked.

Background

Iteration 80 added enumeration datatypes to the clause-log path. It still rejected every array sort with an enumeration in it. Lean knew the cases of enumeration constants and of uninterpreted function applications, but not of array reads. So simply letting these inputs through the front end would only have produced Lean files that fail. This PR closes the backlog item “Arrays and maps over enumerations” for element sorts. It serves milestone 4 of the project plan, “Broader theories and integration”, which lists arrays as a separate extension.

What changed

  • You can now give the exporter an array of an enumeration over Int, Real, Bool, uninterpreted, or array indices, and get a certificate.
  • Lean now knows that every read of an array constant, or of a function’s array value, is a constructor.
  • A read through any chain of stores and if-then-else terms now gets its cases as a kernel-checked proof term, built from two new prelude theorems for stores and if-then-else terms.
  • The clause-log replay now learns an enumeration’s constructors and recognizers from an array’s element sort, even when no plain enumeration term appears.
  • Arrays indexed by an enumeration, nested arrays of an enumeration, constant arrays, default values, and maps of them are still rejected, each with its own message.
  • A read through 1,100 nested stores no longer crashes the reconstructor, because the walk now uses an explicit stack.

Worked example

This is the input read_of_a_store from the PR’s new tests. A read of a after a store at another index is neither red, green, nor blue. That is impossible, because the read is either the stored value c or an old read of a.

(a) The input

(declare-datatypes ((Color 0)) (((red) (green) (blue))))
(declare-const a (Array Int Color))
(declare-const i Int)
(declare-const j Int)
(declare-const c Color)
(assert (not (= (select (store a i c) j) red)))
(assert (not (= (select (store a i c) j) green)))
(assert (not (= (select (store a i c) j) blue)))
(check-sat)

Review

The reviewer approved, with no blocker or major findings. They also tried tampered certificates, and each one was rejected.

  1. Minor: a deep store chain crashed the reconstructor. The reviewer built a read through 1,100 nested stores. The new read walk called itself once per store, and Python ran out of stack. The user got a raw traceback instead of a certificate or a clean rejection. This mattered because the repository promises that deep inputs are handled like any other. The fix walks the chain with an explicit stack, like a to-do list instead of nested phone calls. A new test reconstructs the 1,100-level chain. That test skips Lean: 1,100 constants make an interpretation too large to check, a limit from iteration 80.
  2. Minor: the plan said “all verify”, but some inputs fail. The reviewer ran a deeper random configuration. About 1 in 10 unsatisfiable seeds failed Lean with a grind error. The cause is older than this PR: a read through an if-then-else term over a store gets no value fact. The same gap hits (Array Int Int) with the base commit’s code. It is not a soundness problem, because Lean rejects and nothing false is accepted. The plan now names the failing seeds and records the fix as backlog.
  3. Nit: README wording. A sentence was badly wrapped, and the list of supported operations was incomplete. Both were fixed.

Risks and open questions

  • The new fields are sound only if the embedding of a model’s arrays gives a constructor outside the index sort. The PR argues this, and the reviewer agreed.
  • Reads through an if-then-else term over a store still fail Lean, for every element sort. Seed 219 is the recorded regression input.
  • Around 1,000 enumeration constants make the interpretation too large for Lean’s time budget.
  • Each read’s proof term grows with its store chain, and terms are not shared across lemmas. This was not measured beyond depth 3 in sweeps.
  • The random generator rarely needs the read facts: only 1 of 14 hint seeds failed without them.

What comes next

  • Walk if-then-else branches in the array helpers, which fixes the gap for all element sorts.
  • Support arrays indexed by an enumeration. This needs a Lean index type with exactly the constructors.
  • Support constant arrays, default values, maps, and nested arrays of an enumeration.
  • Write a generator that compares reads only with reads and constructors, to stress the new walk.

Glossary

array
A total map from an index sort to an element sort. (Array Int Color) gives a color for every integer.
case split
Reasoning by trying each possibility in turn. “The read is red, or green, or blue.”
clause log
A record of every clause the solver learned, with a hint for why each one holds. The reconstructor replays it.
constructor
One of the named values of a datatype. red, green, and blue are the constructors of Color.
embedding
A one-to-one way to represent one structure inside another. Here, a model’s arrays become Lean functions.
enumeration
A datatype whose constructors take no arguments, so it has exactly that many distinct values.
extensionality
The rule that two arrays are equal if they agree at every index.
if-then-else term (ite)
A term that picks one of two values by a Boolean condition. (ite p a b) is a when p holds, else b.
interpretation
An assignment of meanings to every symbol of the input. In the Lean file, it is a structure whose fields are facts every model satisfies.
kernel
The small trusted core of Lean that checks every proof term.
lemma (theory lemma)
A clause justified by a theory, such as arrays or datatypes, rather than by Boolean reasoning alone.
model
An interpretation that makes all assertions true.
proof term
A proof written as an explicit expression that the kernel can check step by step.
recognizer
A Boolean test for a constructor. ((_ is red) x) is true when x is red.
refutation
A proof that a set of assertions leads to a contradiction, that is, to False.
rewrite
A step that replaces a term with an equal, simpler term.
select
The array read. (select a i) is the value of a at index i.
sort
The type of a value, such as Int, Bool, or Color.
soundness
The guarantee that a checker never accepts a false claim.
store
The array write. (store a i v) is a with the value at i replaced by v.
tactic
A Lean command that searches for a proof automatically. grind and omega are tactics.
uninterpreted function
A function symbol with no fixed meaning, only that equal arguments give equal results.
uninterpreted sort
A sort with no fixed values, declared with declare-sort.
