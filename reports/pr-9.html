Certify Bool-only predicates from the legacy proof object in Lean

Pull request: levnach/z3 #9 Merge commit: e268600 Merged: 2026-10-14T20:04:46Z Loop iteration: 9

In one paragraph

This PR lets the pipeline certify inputs it used to reject: problems whose only special symbols are uninterpreted predicates over Booleans. A predicate is a function whose result is a Boolean, a true-or-false value. An uninterpreted function is a function symbol with no fixed meaning, only the rule that equal inputs give equal outputs. Before, such a predicate was accepted only if the input also used an uninterpreted sort, a user-declared type of values with no built-in structure. Now no sort is needed, which closes a gap between what Z3 proves and what Lean confirms. Only Python scripts, tests, and documentation changed.

Background

The pipeline already certified three fragments, named subsets of the input language: propositional input (Boolean variables and connectives only), QF_UF (quantifier-free formulas with uninterpreted functions over a declared sort), and QF_LRA (quantifier-free linear real arithmetic). Proof evidence comes from two sources. The legacy proof object is a proof tree built by Z3's older solver core. The clause log is a record of learned clauses from the newer core, where a clause is an or-list of literals, each a Boolean atom or its negation. Bool-only predicates fell through both paths, because the newer core applies Ackermannization, replacing each predicate application by a fresh variable that cannot be tied back to the input. The gap, noted in iteration 6, belongs to milestone 3 of the plan.

What changed

  • Classification. The exporter now files a Bool-only predicate input under QF_UF instead of raising an error. Mixing such predicates with arithmetic is still rejected.
  • Automatic routing. With the default --core auto setting, these inputs go to the legacy proof object.
  • Clear rejection on the other path. Asking for the clause log on such an input now fails up front with a message pointing at the legacy core.
  • Lean encoding without a sort. The reconstructor no longer assumes a QF_UF certificate declares a sort, so the same Lean shape works when only Booleans are present.
  • Tests and docs. Five documented inputs, a random problem generator, pinned seeds, tampering tests, and updated READMEs and plan notes.

Worked example

The example is the smallest of the PR's five documented test inputs, bp_congruence. It rests on congruence, the rule that equal arguments give the same predicate value, like a vending machine that must give the same snack for the same button. Here the two arguments are equal, yet the predicate holds on one and fails on the other. So a refutation exists, a proof that the assertions lead to a contradiction.

(a) The input

(declare-fun r (Bool) Bool)
(declare-const p Bool)
(declare-const q Bool)
(assert (= p q))
(assert (r p))
(assert (not (r q)))
(check-sat)

This is an SMT-LIB file. SMT-LIB is the standard text format for solver inputs.

(b) Before the PR

The exporter from the parent commit rejected the input in both its default and legacy modes. No certificate was produced, so Lean never ran.

proof_certificate.py: error: uninterpreted functions over Bool alone are not supported without an uninterpreted sort: r

(c) After the PR

The exporter now produces a QF_UF certificate with one monotonicity step, Z3's name for a congruence step. The reconstructor wrote the Lean file below, and the check script reported Lean checks passed.

These declarations encode (r p) and (r q). Each Boolean argument is wrapped by _bool so it can live in the single carrier type.

theorem unsat (_atoms : Nat -> Prop) (_U : Type) (_elems : Nat -> _U) (_funs : Nat -> List _U -> _U) (_preds : Nat -> List _U -> Prop) (_bool : Prop -> _U)

The theorem says that for any carrier type, predicates, and Boolean injection, the three assertions imply False.

  let _step_9 : (formula_8 _atoms _U _elems _funs _preds _bool) :=

This is the congruence step. From the equality Lean derives that the two applications are equivalent, which contradicts the third assertion.

Review

The verdict was APPROVE with no blocker, major, or minor findings. Three nits needed no code change.

  1. A misleading table row. The change summary implied the regression matrix had covered the new inputs. The reviewer checked the output and found only the existing propositional files. This mattered because the separate z3test harness still reports "unsupported" for Bool-predicate files. The integrator confirmed it and worded the PR body accurately. Extending the harness is a follow-up.
  2. A slower failure in the harness. The z3test clause-log producer still uses the older parser, so a Bool-only input runs the solver before failing. The outcome is still "unsupported", so only time is lost. Noted as a follow-up in that repository.
  3. A changed error message. A hand-built certificate with an uninterpreted function over reals is now rejected by a different check. Both checks reject, and the exporter never produces such a certificate, so no change was made.

Risks and open questions

  • A wider classification. The exporter now labels inputs as QF_UF that it used to refuse. Every consumer re-checks, and the reconstructor binds each certificate to the original input.
  • A changed consistency test. The reconstructor's fragment check now also counts uninterpreted symbols with arguments. Existing suites were unaffected.
  • Unused binders. The Lean theorem quantifies over element and function families that nothing applies. This is harmless.
  • Open question. Supporting these inputs through the clause log needs either a C++ change or fresh Boolean atoms in the certificate. The second raises a trust question tracked in the backlog.

What comes next

  • Bool-only predicates mixed with arithmetic remain rejected, since the arithmetic encoding has no predicate family yet.
  • Teach the z3test harness to accept QF_UF on the legacy path so the regression matrix can exercise this fragment.
  • The clause-log route for Bool-only predicates stays on the backlog pending the trust decision.
  • Widening the accepted set-option commands was measured at two trivial corpus files and deferred.

Glossary

Ackermannization
Replacing each application of an uninterpreted function by a fresh variable, plus constraints that keep equal inputs giving equal outputs.
Boolean
A value that is either true or false.
Clause
An or-list of literals.
Clause log
A record of the clauses Z3's newer solver core learns while solving, used as proof evidence.
Congruence
The rule that a function or predicate gives the same result on equal arguments. Z3 calls this step monotonicity.
Fragment
A named subset of the input language, such as propositional, QF_UF, or QF_LRA.
If-then-else term
A term written ite in SMT-LIB that picks one of two values based on a condition.
Legacy proof object
The proof tree Z3's older solver core builds while it works, used as proof evidence.
Literal
A Boolean atom or its negation.
Predicate
A function whose result is a Boolean.
Propositional
Input built only from Boolean variables and connectives such as and, or, not.
QF_LRA
Quantifier-free linear real arithmetic.
QF_UF
Quantifier-free formulas with uninterpreted functions and equality.
Refutation
A proof that a set of assertions leads to a contradiction.
SMT-LIB
The standard text format for solver inputs.
Sort
The type of a value. An uninterpreted sort is a user-declared type with no built-in structure.
Uninterpreted function
A function symbol with no fixed meaning, only the rule that equal inputs give equal outputs.
