Certify uninterpreted functions into arrays in Lean via the clause log

Pull request #72 on levnach/z3 · state OPEN · not merged · opened 2026-11-04T16:46:25Z · loop iteration 72
Change commit: 29b5008c9 (the PR has two commits on top of base fff41c909).

In one paragraph

This PR lets the pipeline certify inputs that declare an uninterpreted function whose result sort is an array, such as (declare-fun h (Index) (Array Index Element)). Before, the certificate exporter and the Lean reconstructor both rejected such declarations. Now the clause log for these inputs becomes a Lean refutation that the Lean kernel checks. Each Lean array type gets one new universally quantified field in the interpretation, standing for every function into that type. Each application also gets a small fact proved by rfl. That fact lets the grind tactic use congruence: equal arguments give equal arrays. No axiom or sorry is added, so nothing new is trusted. For every input without such functions, the generated Lean is byte-for-byte unchanged.

Background

Earlier iterations certified arrays over uninterpreted sorts, Int, and Real. That work covered select, store, extensionality, and constant arrays. Functions that take arrays as arguments have been certified since iteration 69. A function that returns an array was still rejected, and the backlog listed this gap as "functions into arrays". This PR serves milestone 4, broader theories, where arrays are one of the named extensions. It builds on the uninterpreted function support from milestone 3.

What changed

  • The exporter now turns an input with a function into a supported array sort into a certificate, where it used to stop with an error.
  • The reconstructor accepts these functions and gives each Lean array type one family of them. Think of a filing cabinet per array type: each function has a numbered drawer, and the argument list picks the folder.
  • Each application of such a function gets an rfl fact, so grind can conclude h i = h j from i = j by congruence closure.
  • Certificates that swap, rename, or relabel these functions are rejected, because they no longer match the original input.
  • Eleven new test inputs are each checked in Lean. They cover store, extensionality, ite, constant arrays, nested applications, and Int and Real sorts under Farkas lemma steps.

Arrays with Boolean elements and arrays of arrays are still rejected, both as arguments and as results.

Worked example

This input is the test input function_into_arrays from the PR. Since i = j, congruence gives (h i) = (h j). So (h j) equals a store of e into itself at i, and reading it at i must give e. The third assertion says it does not, so the input is unsat.

(a) The input

(set-logic QF_AUF)
(declare-sort Index 0)
(declare-sort Element 0)
(declare-fun h (Index) (Array Index Element))
(declare-fun i () Index)
(declare-fun j () Index)
(declare-fun e () Element)
(assert (= (h i) (store (h j) i e)))
(assert (= i j))
(assert (not (= (select (h j) i) e)))
(check-sat)

(b) Before

The exporter from the PR's base commit rejected the input:

(c) After

The new exporter and reconstructor produced a Lean file. The project's Lean check accepted it with "Lean checks passed."

structure Interpretation where
  U : Type
  elems : Nat -> U
  ...
  arrs : Nat -> U -> U
  arrs_funs : Nat -> List U -> U -> U

The last field is new: one family for all functions into this array type, indexed by a number and fed a list of arguments.

def term_1 (_atoms : Nat -> Prop) (_m : Interpretation) : (_m.U -> _m.U) := _m.arrs_funs 0 [(term_0 _atoms _m)]
...
def term_3 (_atoms : Nat -> Prop) (_m : Interpretation) : (_m.U -> _m.U) := _m.arrs_funs 0 [(term_2 _atoms _m)]

These are (h i) and (h j): function number 0 of the family, applied to i and to j.

theorem unsat (_atoms : Nat -> Prop) (_m : Interpretation)
    (_h0 : (formula_6 _atoms _m))
    (_h1 : (formula_7 _atoms _m))
    (_h2 : (formula_10 _atoms _m))
    : False :=
  ...

For every interpretation, the three assertions together imply False.

private theorem th_lemma_21 (_atoms : Nat -> Prop) (_m : Interpretation)
    : (formula_20 _atoms _m) := by
  unfold formula_20 formula_19 formula_18 formula_17 formula_15 term_14 formula_9 term_8 formula_7 formula_6 term_4 term_2 term_0
  have _t1 : (term_1 _atoms _m) = _m.arrs_funs 0 [(_m.elems 0)] := rfl
  have _t3 : (term_3 _atoms _m) = _m.arrs_funs 0 [(_m.elems 1)] := rfl
  have _t5 : (term_5 _atoms _m) = (_store ((term_3 _atoms _m)) (_m.elems 0) (_m.elems 2)) := rfl
  have _s14 := _store_apply ((term_3 _atoms _m)) (_m.elems 0) (_m.elems 2) (_m.elems 0)
  grind (splits := 64)

This lemma proves one clause of four literals from the clause log. The new _t1 and _t3 facts expose the two applications, so grind can see that i = j makes them equal.

Review

The reviewer approved the change with no blockers and no major findings.

  • Minor: a missing tamper test. The reviewer read the tests that feed the checker forged certificates. They caught wrong declaration shapes, but none swapped two functions with the same signature. If someone later loosened the binding check, a forged certificate swapping f and g could slip past every test. Today's code already rejects it, so this was a coverage gap, not a bug. The fix added an input where f and g play different roles. The tamper test now swaps them and renames g, and both forgeries are rejected as not matching the input.
  • Nit: an unused loop variable in the exporter's signature check. It was removed.
  • Nit: a stale docstring. Its first line did not mention arrays. It was fixed.
  • Nit: a wrong claim in the implementer's notes. The notes said the symbol tables were "numbered together". In fact each table counts from zero, which is safe because each maps to its own family. The code and docs never made the claim, so only the notes were wrong. No code change was needed.

Risks and open questions

  • Soundness relies on an argument written in the PR, not proved in Lean. A model's function into arrays returns model arrays. These embed into the Lean array type by the same map as array constants, and that map respects select and store.
  • No z3test input becomes newly certified. The two fuzzsmt regressions with such functions are satisfiable, so all coverage comes from synthetic inputs.
  • An unused constant-array field is still emitted when an array sort appears only as a function result. The reviewer judged this harmless.
  • The legacy proof core does not inject array arguments in one congruence step. This cannot be reached while that core rejects arrays.
  • CI results and the local gate outcome were unknown at the time of writing.

What comes next

  • Arrays with Boolean elements, also called sets, are the next array candidate. The backlog plans a Prop element type for them.
  • Arrays of arrays remain rejected.
  • Optionally, the unused constant-array field could be trimmed to keep the interpretation minimal.

Glossary

array
A value that maps every index to an element, like a total function. (Array Int Real) maps integers to reals.
axiom
A statement Lean accepts without proof. A certificate that needs a new axiom trusts something extra.
Boolean
The sort with two values, true and false, written Bool.
clause
A disjunction of literals: at least one of them must be true. Example: x = 1 or not p.
clause log
The record of clauses the solver derived on its way to a contradiction, used here as the proof certificate.
congruence
The rule that equal arguments give equal results: if i = j then h i = h j.
congruence closure
A procedure that finds all equalities that follow from given ones by congruence.
constant array
An array with the same element at every index, written ((as const (Array Int Int)) 0).
extensionality
The rule that two arrays are equal if they agree at every index.
Farkas lemma
A way to show linear inequalities have no solution: a positive combination of them sums to something false, like 0 < 0.
grind
A Lean tactic that combines congruence closure, case splits, and arithmetic to close a goal.
if-then-else term (ite)
A term that picks one of two values by a condition: (ite p a b) is a when p holds, else b.
interpretation
A choice of meaning for every symbol: which set a sort is, which function a function symbol is, and so on.
kernel
The small core of Lean that checks every proof step. A proof is trusted only once the kernel accepts it.
literal
An atomic formula or its negation, such as i = j or not (i = j).
model
An interpretation that makes all the assertions true.
refutation
A proof that a set of assertions leads to False, so no model exists.
rfl
Lean's proof that a term equals itself. It also proves equalities that hold just by unfolding definitions.
satisfiable
Having at least one model. A satisfiable input has no refutation to certify.
select
Reading an array: (select a i) is the element of a at index i.
sort
The type of a value, such as Int, Real, Bool, or an array sort.
store
Writing an array: (store a i v) is a with index i changed to v.
tactic
A Lean command that builds part of a proof automatically.
uninterpreted function
A function symbol with no fixed meaning. Only its sorts are known, and congruence holds. Example: (declare-fun h (Index) (Array Index Element)).
uninterpreted sort
A sort with no fixed meaning, declared with declare-sort, such as Index above.
universally quantified
Stated "for all" values. The Lean theorem holds for every interpretation, so it covers every possible model.
