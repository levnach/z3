In one paragraph

Z3's legacy core sometimes ends an integer proof with a theory lemma labelled unsupported. The label means the solver found a conflict but could not produce Farkas coefficients for it. That is what a lattice conflict looks like from inside the solver. Before this PR the exporter rejected every proof carrying that label, so some integer problems Z3 solved could not be certified. Now, over the sort Int, the exporter keeps the step as a coefficient-free Farkas step. Its premises are the held literals and its conclusion is false. The reconstructor already handles that shape and lets a Lean tactic prove the refutation from the premises alone. Nothing new is trusted. The change is Python and documentation only.

Background

The pipeline has two certified proof sources, the legacy core and the clause log. For linear integer arithmetic, the exporter already accepted a Farkas step whose coefficients it could not re-derive. It stripped the coefficients and left the step to Lean, which uses omega and then grind, as it does for cut steps. But a step labelled unsupported was a hard rejection, even though it has the same shape. The iteration 27 stress run hit this on five inputs. This PR serves milestone 3 of the plan, equality and linear arithmetic, by closing that gap in the integer fragment.

What changed

  • Integer conflicts the solver could not explain are now certified. A step labelled unsupported over Int is exported as a coefficient-free Farkas step, so Lean can prove it from its premises.
  • The step must still look right. It is accepted only if it has at least one premise and concludes false.
  • Real arithmetic is unchanged. Over Real the label is still rejected, because a Farkas step Z3 could not check over the rationals is suspect. The nonlinear variant stays rejected too.
  • Nothing changed in what Lean trusts. The reconstructor gained only a comment. Its shape check and tactic are the same as before.
  • New tests pin the behaviour. Two documented inputs run through both proof sources, and a tampered variant with made-up coefficients is rejected before Lean runs.

Farkas coefficients are a recipe for mixing the constraints until they add up to a contradiction. A lattice conflict has no such recipe, because every rational mix is fine. Before, the exporter threw the whole proof away at that point. Now it hands that one step to Lean, which proves it directly.

Review

The reviewer approved the change with no blocking or major findings. They verified that the mapping only fires over Int with at least one premise and a false conclusion, and that Real and nonlinear labels stay rejected. They also duplicated a premise in a certificate. Python let it through, and Lean rejected it. Three smaller points were raised.

  • Minor: the tests pin solver behaviour. Two tests assert that Z3 still emits the unsupported label on the new inputs. A future C++ change that emits real evidence instead would fail both tests even though every certificate still verifies. The reviewer accepted this as deliberate pinning. The fix was to rewrite the assertion messages so they tell a future maintainer to drop the label assertions and keep the certificate checks.
  • Nit: a duplicated test input. The lattice input appears verbatim in two test files because the import direction forces the copy. A comment now names the twin so the two do not drift apart.
  • Nit: a misleading parameter name. A check read like a test on a list, but the value is a count. The parameter was renamed premise_count throughout.

The integrator checked the trust argument in the C++ source. The label is produced only on the conflict path, so it always concludes false. Mixed Int and Real inputs are rejected earlier, so a coefficient-free Farkas step over Real cannot reach the Lean-only branch.

Risks and open questions

  • The label carries no evidence. The whole refutation rests on Lean's tactics within the heartbeat budget. A conflict Lean cannot prove is rejected, not trusted. The known inputs are small, but a large one could time out.
  • Real arithmetic is deliberately untouched. If Z3 ever emits this label over Real, that calls for a solver-side investigation, not a wider mapping.
  • The change is additive. No previously accepted certificate changes shape.
  • CI status is unknown at report time. The CI jobs had not reported when this page was written.

What comes next

  • Emit real evidence from the solver. The backlog item is to make Z3's integer solver produce lattice or tightening steps instead of unsupported, so consumers without Lean can replay these conflicts. The two pinned tests then need their label assertions dropped.
  • One stress input still times out. The div and mod input from iteration 27 verifies through the legacy core, but its clause-log certificate still exceeds the heartbeat budget.

Glossary

clause log
The second proof source in this project. Z3's newer solver core records each learned clause with a hint saying how it was derived.
conflict
A set of constraints the solver has found to be jointly impossible. Example: x > 2 together with x < 1.
cut
An inequality that is true for every integer solution but cuts off some rational ones. Example: from 2x < 3 an integer solver derives x <= 1.
exporter
The Python script that turns a Z3 proof into a JSON certificate. It rejects proof shapes it does not understand.
Farkas lemma, Farkas coefficients
A theorem saying that if linear inequalities have no solution, some positive combination of them adds up to an obvious contradiction such as 0 < 0. The multipliers in that combination are the Farkas coefficients.
fragment
A named subset of SMT-LIB, such as QF_LIA or QF_LRA, that fixes which sorts and operations an input may use.
grind
A general-purpose Lean tactic that combines case splitting, rewriting, and arithmetic. It is the fallback when omega fails.
lattice conflict
A set of linear constraints that has rational solutions but no integer solution. Example: 2y = 3 is fine over the rationals and impossible over the integers.
legacy core
Z3's older solver core, which builds an explicit proof object. One of the two certified proof sources in this project.
literal
An atomic formula or its negation, such as x <= 5 or not (x = y).
omega
A Lean tactic that decides linear arithmetic over integers and natural numbers. It handles the integer rounding that Farkas coefficients cannot express.
premise
A fact a proof step assumes. The step's conclusion must follow from its premises.
linear integer arithmetic (QF_LIA)
Formulas over integer variables with addition, multiplication by constants, comparisons, and Boolean connectives, but no quantifiers.
reconstructor
The Python script that turns a JSON certificate into Lean source and runs the Lean check on it.
refutation
A proof that a set of assertions implies false. In Lean it is a theorem whose hypotheses are the assertions and whose conclusion is False.
sort
The type of a value in SMT-LIB, such as Int, Real, or Bool.
tactic
A Lean command that searches for a proof automatically instead of the user writing it by hand. Examples: omega, grind.
theory lemma
A proof step justified by a theory solver rather than by Boolean reasoning. In Z3's legacy proofs it is labelled th-lemma with a hint such as farkas or unsupported.
