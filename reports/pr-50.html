In one paragraph

The certificate exporter now stops on time in its last two unbounded stages. The first is the solve that builds a proof object for propositional input. The second is the replay of the clause log. Both now obey the exporter's time limit, and the first also obeys its memory limit. A hit ends the export with an error that names the limit. This matters for certifying refutations in Lean across large benchmark sweeps. One hard input can no longer stall a whole run. What Lean checks is unchanged. A certificate produced within the limits is the same as before.

Background

The previous pull request, #49, put limits on every run of the z3 executable in a clause-log export. Two stages ran inside the Python process and stayed unbounded. A pigeonhole formula with eleven holes ran for ever on the proof-object path, even with a one-second limit. A difference logic benchmark took 622 seconds to export under a 60-second limit, because the replay had no deadline. This work serves the regression methodology, which the project plan calls its current top priority. That methodology runs a matrix of benchmarks, and every stage must finish in bounded time.

What changed

  • Legacy exporter: you can now pass --timeout to a propositional export, and it stops at that limit instead of running for ever.
  • Legacy exporter: you can now pass --memory to a propositional export, and z3 stops its search once its memory in the process passes that limit.
  • Error messages: you can now tell a time limit, a memory limit, and an outside interrupt apart, because each gives its own message.
  • Clause-log replay: you can now rely on the replay to stop near its time limit, because it checks a deadline before each log command and each solver call.
  • Tests and docs: two new tests cover both limits, and the README and the plan describe them.

The memory limit uses a z3 setting called the memory high watermark. It is a global setting, shared by everything in the process. So the exporter sets it just for the check and puts the old value back afterwards. Think of a shared office thermostat: you change it for your meeting and reset it when you leave.

Worked example

This pull request makes no new input certifiable. Its effect is that a hard input now stops with a clear error, while easy inputs certify as before. So the example has two inputs from the same family, both run for this report on the merged code. The hard one is the pigeonhole formula with 11 holes and 12 pigeons, as built by the new test. It has 738 clauses, too many to show. The small one below has 2 holes and 3 pigeons.

(a) The input

(declare-const p0_0 Bool) (declare-const p0_1 Bool) (declare-const p1_0 Bool) (declare-const p1_1 Bool) (declare-const p2_0 Bool) (declare-const p2_1 Bool)
(assert (or p0_0 p0_1))
(assert (or p1_0 p1_1))
(assert (or p2_0 p2_1))
(assert (or (not p0_0) (not p1_0)))
(assert (or (not p0_0) (not p2_0)))
(assert (or (not p1_0) (not p2_0)))
(assert (or (not p0_1) (not p1_1)))
(assert (or (not p0_1) (not p2_1)))
(assert (or (not p1_1) (not p2_1)))
(check-sat)

The Boolean variable p1_0 means pigeon 1 sits in hole 0. The first three clauses put each pigeon in some hole. The other six keep two pigeons out of the same hole.

(b) Before

On the 11-hole input, the old exporter ignored the one-second limit. It was still solving after 60 seconds, when the report's script killed it.

$ python3 proof_certificate.py --timeout 1 php11.smt2
(no output, still running after 60 s, killed)

On the small input, the old exporter succeeded. Its certificate is byte-for-byte identical to the new one.

(c) After

On the 11-hole input, the new exporter stops after 1.2 seconds with exit code 2.

$ python3 examples/python/proof_certificate.py --timeout 1 php11.smt2
proof_certificate.py: error: the legacy solver run exceeded the time limit of 1 s

The error names the limit, so a batch run can record why it skipped this input.

On the small input, the exporter still produces a certificate. The reconstructor turns it into the Lean file below. This pull request does not change any Lean lemma, so the excerpt shows the ordinary proof shape.

-- Atom 0: "p0_0"
-- Atom 1: "p0_1"
...
def formula_0 (_atoms : Nat -> Prop) : Prop := _atoms 0
def formula_1 (_atoms : Nat -> Prop) : Prop := _atoms 1
def formula_2 (_atoms : Nat -> Prop) : Prop := (Or (formula_0 _atoms) (formula_1 _atoms))
...
def formula_34 (_atoms : Nat -> Prop) : Prop := False

Each SMT-LIB variable becomes a numbered atom, and each subformula becomes one Lean definition.

theorem unsat (_atoms : Nat -> Prop)
    (_h0 : (formula_2 _atoms))
    (_h1 : (formula_5 _atoms))
    ...
    (_h8 : (formula_20 _atoms))
    : False :=

The theorem says that the nine assertions together imply False.

  let _step_27 (_hyp7 : (formula_7 _atoms)) : (formula_7 _atoms) :=
    _hyp7
  ...
  let _step_36 : (formula_18 _atoms) :=
    _step_35
  ...
  let _step_43 : (formula_34 _atoms) :=
    (False.elim ((_step_21.resolve_left (fun _literal => _literal _step_42)) _step_39))
  _step_43

The proof assumes p2_1 as a hypothesis, reaches False, concludes not p2_1, and then finishes with resolution steps on each clause.

Lean accepted this file. The check script reported "Lean checks passed."

Review

The reviewer approved the change, with no blocker or major findings.

  • Minor, fixed. The reviewer exported the trivial input (assert false) with a 1 MB memory limit. It failed at once, blaming "the legacy solver run". The watermark compares all of z3's memory in the process, not just this solve. So a long-running caller could see easy inputs rejected with a misleading message. The message and the help text now say "z3's memory in this process".
  • Nit, fixed. z3 reports both its timer and an outside interrupt as "canceled". The first version called every "canceled" a time-limit hit. Now it says "time limit" only when the check really lasted that long. An early cancel stays "unknown: canceled", and a new subtest covers it.
  • Suggestion, adopted. The memory subtest relied on z3 already using about 20 MB. It now also has a 5-second time limit, so a future failure shows up fast.
  • Suggestion, not adopted. The z3test matrix could pass its own time limit to the replay. That code lives outside this repository, so it is a follow-up.

Risks and open questions

  • The memory watermark is process-global. A caller holding other large z3 contexts reaches it sooner, and another thread would also see it.
  • A replay that truly needs more than its limit now fails, where it used to finish. The default is 600 seconds.
  • The deadline is checked only between steps. One very slow step can still overrun it.
  • The Python work after the legacy solve, which builds the certificate, has no time limit.

What comes next

  • z3test's scripts should pass their own time and memory limits through to the exporter.
  • The same iteration logged a new backlog item: Lean memory on large QF_UF certificates. One benchmark ran out of kernel memory, and fewer declarations are the main lever.

Glossary

atom
A formula with no Boolean connective inside, such as the variable p0_0.
Boolean
The sort with exactly two values, true and false. In SMT-LIB it is written Bool.
certificate
A file of proof steps that a separate checker can verify without trusting the solver.
clause
A disjunction of literals, such as (or (not p0_0) (not p1_0)).
clause log
A record of every clause the solver added or deleted during its search, with hints on why each one holds.
difference logic
Constraints of the form x - y <= c over integers. Its SMT-LIB logic name is QF_IDL.
hypothesis
A formula assumed for part of a proof. The assumption is later discharged, often by proving its negation.
literal
An atom or its negation, such as p1_0 or (not p1_0).
pigeonhole formula
The claim that n+1 pigeons fit in n holes, one per hole. It is unsatisfiable, and hard for clause-based solvers as n grows.
proof object
A tree of inference steps that z3 builds while solving with proofs enabled. The older solver core uses it.
propositional
Built only from Boolean variables and connectives such as and, or, and not, with no arithmetic or functions.
refutation
A proof that a set of assertions implies False, so they cannot all hold.
replay
Reading a log step by step and rebuilding each step as an explicit proof step.
resolution
The rule that combines (or A x) and (or B (not x)) into (or A B).
theorem
A statement that Lean has proved. Here it states that the input's assertions imply False.
