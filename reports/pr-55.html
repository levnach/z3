Read integer numerals coerced to Real as Real numerals in certificates

This pull request is open and not merged. The change it proposes ends at commit 6291d878a. It contains two commits: 8a0092fd1 makes the change, and 6291d878a adds documentation and one test after review.

In one paragraph

Without a set-logic, Z3 reads an integer numeral in a Real position, like the 2 in (* 2 x), as an Int under a to_real coercion. The certificate exporter refused every to_real, so these common inputs could not be certified. This PR rewrites to_real of a pure numeral expression into the same expression over Real numerals, before anything reads the assertions. The result is exactly what Z3 reads under the logic QF_LRA. Both the clause log and the legacy proof object now yield a refutation that Lean checks. The binding to the input uses the same rewritten assertions, so a changed numeral is still caught. This closes a completeness gap without adding trust.

Background

Before this PR, the pipeline already certified linear real arithmetic when the input said (set-logic QF_LRA). The same text without that line failed with "unsupported arithmetic operator: to_real". Even a two-line input such as (assert (> x 1)) over a Real x was refused. Mixing the sorts Int and Real stays outside the supported fragment, and that boundary does not move. The work serves milestone 3 of the plan, "Equality and linear arithmetic".

What changed

  • You can now certify a Real input that uses integer numerals and has no set-logic, or uses (set-logic ALL).
  • An explicit (to_real (+ 2 1)) is read as (+ 2.0 1.0) under any logic, including QF_LIRA.
  • The exporter and the Lean reconstructor's input check now share one parsed copy of the assertions, built by the new function _parse_snapshot.
  • to_real of anything that is not a pure numeral expression is still rejected, for example an Int variable, an application of an uninterpreted function, div, or an Int if-then-else term.
  • New tests pin all of this down, and the README and plan document describe the new exception to the rejection list.

An analogy: a form asks for a price, and someone writes "2" instead of "2.00". Z3 tags the 2 with "convert to decimal", and the old exporter threw the form away. Now it peels the tag off and writes "2.00", which means the same thing. The rewrite never computes, so (- 5 1) becomes (- 5.0 1.0), not 4.0.

Worked example

This input, a smaller version of the PR's test input numerals_without_logic, was run for this report at the PR head and at the PR base.

(a) The input

(declare-const x Real)
(assert (<= (* 2 x) 1))
(assert (> x 1))
(check-sat)

If 2x is at most 1, then x is at most one half, so x cannot also be greater than 1.

(b) Before: the pipeline at the PR base

proof_certificate.py: error: unsupported arithmetic operator: to_real

The old exporter stopped here, so the old Lean reconstructor had nothing to read.

(c) After: the Lean file the reconstructor now generates

def term_0 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Rat := ((2 : Rat))
def term_1 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Rat := _vars 0
def term_2 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Rat := ((term_0 _atoms _vars) * (term_1 _atoms _vars))

The numeral 2 appears directly as a Real number, with no Int and no coercion around it. The file encodes Real values as Lean's rationals, Rat.

    (_h1 : (formula_5 _atoms _vars))

The theorem says that the two input assertions, 2x ≤ 1 and x > 1, together imply False.

private theorem rewrite_10 (_atoms : Nat -> Prop) (_vars : Nat -> Rat)
    : (formula_9 _atoms _vars) := by
  unfold formula_9 formula_8 term_7 formula_4 term_3 term_2 term_1 term_0
  have _s8 : ((_vars 0) <= (((((1 : Rat))) / (((2 : Rat)))))) -> (((2 : Rat)) * _vars 0 + ((-1 : Rat)) <= ((0 : Rat))) := by grind
  grind (splits := 64)
...

This rewrite step proves that 2x ≤ 1 is equivalent to x ≤ 1/2, using Real numerals on both sides and the tactic grind.

A theory lemma and a unit resolution then reach False. Lean accepted the file: the reconstructor reported "Lean checked the refutation", and check_lean.sh printed "Lean checks passed."

Nit1

Nit: the documentation was narrower than the code. The reviewer wrote an input under (set-logic QF_LIRA) with an explicit (to_real 2). The new code accepted it, and Lean verified it. That is correct, because to_real of 2 is the Real number 2.0. But the README still said to_real is "rejected explicitly". This mattered because readers use that list to learn what the pipeline certifies. Commit 6291d878a fixed the README, the code comment, and the plan document. It also added a test: (to_real (+ 2 1)) must read as (+ 2.0 1.0).

The reviewer also probed soundness with edge cases and tampered certificates, and found no problem.

Risks and open questions

  • Lean proves the rewritten statement: the input says (* 2 x), the theorem says 2.0 * x. This is Z3's own QF_LRA reading, and it happens in the trusted Python front end.
  • Two parsing functions now return a Python list instead of a Z3 vector. An outside caller using vector-only methods would break. All known callers pass.
  • CI results and the final local gate result are unknown at the time of writing.

What comes next

  • An Int if-then-else term in a Real position, such as (= x (ite p 1 2)), is still rejected. Supporting it needs more work in the clause-log replay.
  • A rescan of QF_LRA benchmarks found four new Lean failures, now in the backlog. They hit grind step limits or time out on Real theory lemmas over ite terms.

Glossary

assertion
A formula the input states as true, written (assert ...).
axiom
A statement a proof checker accepts without proof. A certificate is trustworthy only if it uses the checker's standard axioms and nothing extra.
binding (of a certificate to its input)
The check that the formulas inside a certificate are exactly the assertions of the original input, so a certificate for a different problem is rejected.
certificate
A file that records a proof so that a separate checker can confirm it.
clause
A disjunction of literals: at least one of them must be true. Example: (or (not a) b).
clause log
A record of the clauses a solver learned while searching, which a checker can replay step by step.
coercion
A conversion of a value from one sort to another. In SMT-LIB, to_real turns an Int into the same number as a Real.
completeness
How many correct inputs a tool can handle. A completeness gap is a correct input that the tool refuses.
fragment
A restricted part of logic that a tool supports, such as linear real arithmetic without quantifiers.
if-then-else term
A term whose value depends on a condition, written (ite c a b): it equals a when c holds, otherwise b.
legacy proof object
Z3's older proof format: one large proof term built during solving, as opposed to the clause log.
linear real arithmetic (QF_LRA)
Formulas over Real variables using sums, differences, and multiplication by constants. QF_LRA is its quantifier-free SMT-LIB logic. QF_LIRA allows Int and Real together.
literal
An atomic formula or its negation, such as x > 1 or (not p).
logic (SMT-LIB)
A named setting, chosen with set-logic, that fixes which sorts and operations an input may use. ALL allows everything.
numeral
A number written literally in the input. 2 is an Int numeral, and 2.0 is a Real numeral.
refutation
A proof that a set of assertions leads to False, so they cannot all hold.
rewrite step
A proof step that replaces a formula by an equivalent one, such as 2x ≤ 1 by x ≤ 1/2.
sort
The type of a value, such as Int, Real, or Bool.
soundness
The guarantee that a checker never accepts a false claim.
tactic
A Lean command that builds part of a proof automatically. grind is one such tactic.
theory lemma
A clause that is true because of the rules of a theory such as arithmetic, not because of Boolean reasoning alone.
uninterpreted function
A function symbol with no fixed meaning. The only rule is that equal arguments give equal results. Example: (declare-fun f (Real) Real).
unit resolution
A proof step that takes a clause and facts contradicting all but one of its literals, and concludes the remaining literal.
