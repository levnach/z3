In one paragraph

Many people write a Real problem with plain integer numerals, such as (* 2 x), and give no logic. In that case Z3 parses each such numeral as an Int term wrapped in a to_real coercion. The exporter refused every such assertion with “unsupported arithmetic operator: to_real”. This PR rewrites those coercions into Real numerals before anything else reads the input. The result is exactly how Z3 reads the same text under QF_LRA. The exporter, both proof cores, and the step that binds the certificate to the input all share that one rewritten snapshot. So a whole class of everyday inputs now gets a refutation that Lean checks. The change is Python, tests, and docs only. No Lean rule, C++ code, or trusted axiom changed.

Background

Before this PR, the pipeline certified QF_LRA inputs only when every Real numeral was written as a decimal, or when the file declared (set-logic QF_LRA). Without that line, even (assert (> x 1)) over a Real x was rejected, because the parser had inserted a to_real coercion. Mixing the Int and Real sorts stays out of scope, so the exporter rejected the whole input. The PR body calls this a completeness gap on inputs Z3 already solves. The work serves milestone 3 of the project plan, “Equality and linear arithmetic”, which asks to complete each fragment end to end.

What changed

  • You can now certify a Real problem written with integer numerals and no set-logic, or under (set-logic ALL).
  • An explicit to_real of a numeral expression, such as (to_real (+ 2 1)), is now read as (+ 2.0 1.0) under any logic.
  • The certificate and the Lean statement show the same Real numerals that QF_LRA would show, with the input's structure kept and nothing folded.
  • A certificate whose numeral was edited, for example 2 changed to 5, is still caught and rejected before Lean runs.
  • to_real of anything else stays rejected, such as an Int variable, a function application, div, mod, abs, or an Int if-then-else term.

The rewrite lives in one new function, _parse_snapshot. Think of it as a translator at the door. Every later reader sees the same translated text, so the exporter and the binding check can never disagree about what the input said. The two parsing helpers now return a Python list instead of a Z3 vector.

Worked example

This example was produced by running the real pipeline for this report, on the old and the new code.

(a) The input

(declare-const x Real)
(assert (<= (* 2 x) 1))
(assert (> x 1))
(check-sat)

A Real x with 2x ≤ 1 and x > 1 cannot exist. The numerals 2 and 1 are written as integers, and there is no set-logic line.

(b) Before: the exporter at the PR's base commit

proof_certificate.py: error: unsupported arithmetic operator: to_real

The old exporter saw (* (to_real 2) x) and stopped. No certificate and no Lean file were produced.

(c) After: the Lean file the reconstructor now generates

def term_0 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Rat := ((2 : Rat))
def term_1 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Rat := _vars 0
def term_2 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Rat := ((term_0 _atoms _vars) * (term_1 _atoms _vars))
def term_3 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Rat := ((1 : Rat))
def formula_4 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := ((term_2 _atoms _vars) <= (term_3 _atoms _vars))
def formula_5 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := ((term_1 _atoms _vars) > (term_3 _atoms _vars))
...

The numerals 2 and 1 now appear directly as rational constants, with no to_real anywhere, and formula_4 is the first assertion 2·x ≤ 1.

theorem unsat (_atoms : Nat -> Prop) (_vars : Nat -> Rat)
    (_h0 : (formula_4 _atoms _vars))
    (_h1 : (formula_5 _atoms _vars))
    : False :=
  ...

The theorem says that the two input assertions together imply False.

private theorem rewrite_10 (_atoms : Nat -> Prop) (_vars : Nat -> Rat)
    : (formula_9 _atoms _vars) := by
  unfold formula_9 formula_8 term_7 formula_4 term_3 term_2 term_1 term_0
  have _s8 : ((_vars 0) <= (((((1 : Rat))) / (((2 : Rat)))))) -> (((2 : Rat)) * _vars 0 + ((-1 : Rat)) <= ((0 : Rat))) := by grind
  grind (splits := 64)

This lemma proves Z3's rewrite of 2·x ≤ 1 into x ≤ 1/2, working on the same Real constant 2 that the input statement uses.

Review

The reviewer approved the PR. There were no blocker, major, or minor findings. There was one nit.

SeverityFindingResolution
nitThe README and the docstring described the rewrite more narrowly than the code behaves.Fixed: docs widened and a test added.

The reviewer wrote an input under (set-logic QF_LIRA) with an explicit (to_real 2). The new code accepted it as QF_LRA and Lean verified it on both cores. That behaviour is correct, because to_real of 2 is simply 2.0. But the README still said to_real is “rejected explicitly”, and it only mentioned the parser's hidden coercion. A reader trusting the docs would have a wrong picture of what is certified. The implementer extended the README, the docstring, and the plan note to cover an explicit to_real in any logic. They also added a test that pins (to_real (+ 2 1)) to (+ 2.0 1.0). The reviewer found no soundness problem. No Lean files changed and no new trust was added.

Risks and open questions

  • Lean proves the rewritten statement. Where the text says (* 2 x), Lean states (* 2.0 x). This matches Z3's own QF_LRA reading, and a test compares the two. The rewrite runs in the trusted Python front end.
  • The two parsing helpers now return a list instead of a Z3 vector. An outside caller that relies on vector-only methods would break. All in-repo callers and z3test pass.
  • Whether GitHub CI on master passed with this change is not recorded in the inputs.

What comes next

  • An Int if-then-else term of numerals in a Real position, such as (= x (ite p 1 2)), is still rejected. The clause log keeps that coercion over an Int ite, so support needs the replay to read part of QF_LIRA.
  • A rescan of QF_LRA benchmarks found new Lean failures, now in the backlog. One hits the step limit of the tactic grind. Three others time out in fallback proofs of theory lemmas over ite terms.

Glossary

assertion
A formula the input states as true, written (assert …) in SMT-LIB.
axiom
A statement Lean accepts without proof. The project allows only Lean's standard axioms in a certified proof.
certificate
The file the exporter writes. It holds the input's terms and Z3's proof steps, so that Lean can recheck them.
clause
A disjunction of literals, such as (or (not a) b). A clause log records the clauses Z3 derives.
coercion
An automatic conversion of a value from one sort to another, such as an Int 2 used where a Real is expected.
core (proof core)
One of the two Z3 proof sources the exporter can read: the clause log or the legacy proof object.
if-then-else term
A term that picks one of two values by a Boolean condition, written (ite p 1 2).
lemma
A small proved statement used as a step inside a bigger proof.
literal
An atomic formula or its negation, such as (> x 1) or (not (> x 1)).
logic (SMT-LIB logic)
The fragment an input declares with set-logic, such as QF_LRA or ALL. It tells the parser which sorts and operators to expect.
numeral
A constant number written in the input, such as 2 (an Int numeral) or 2.0 (a Real numeral).
QF_LRA
Quantifier-free linear real arithmetic: Real variables, sums, and products by constants, with no quantifiers.
refutation
A proof that a set of assertions leads to False, so they cannot all hold.
rewrite
A proof step that replaces a formula by an equivalent one, such as 2·x ≤ 1 by x ≤ 1/2.
snapshot (assertion snapshot)
The list of assertions parsed from the input at the query, which the exporter and the reconstructor both read.
sort
The type of a value, such as Int, Real, or Bool.
soundness
The property that a checker never accepts a false claim.
tactic
A Lean command that builds part of a proof automatically, such as grind.
theorem
A statement with a proof that Lean has checked.
theory lemma
A clause that holds by the rules of a theory such as arithmetic, written th-lemma in Z3 proofs.
to_real
The SMT-LIB function that maps an integer to the same real number. For example, (to_real 2) is 2.0.
