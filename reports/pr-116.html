Infer resolution step types and apply re-applications in place in Lean

Pull request levnach/z3#116 into master · State: OPEN · Opened 2026-11-11T08:03:52Z · Loop iteration 115

This pull request is open and not merged. The change under review is commit fdf5c43. It contains two commits on top of the base.

In one paragraph

The Lean files that certify Z3's refutations got smaller. Two kinds of text were dropped because Lean can work them out itself. First, a unit resolution step no longer states its type. Lean's type inference recovers it from the clause being resolved. Second, when a step is applied to a hypothesis and the result is used only once, the application is written at that use. It no longer gets its own let binding. This matters because Lean's memory grows with the text it must elaborate. The largest integer difference logic benchmark the project checks was at 7.86 of the 8 GB limit. It now peaks at 7.45 GB, which leaves more room before it fails. The theorem statement does not change, and Lean still checks every proof term.

Background

Before this PR, the reconstructor already handled the QF_IDL benchmark DTP_k2_n35_c245_s9. It verified for the first time in the previous iteration, PR #115, at 7.86 GB of the 8 GB cap. That margin was thin, so any growth in the text could push it out of memory. Most of its proof was resolution steps under hypotheses, each with a stated type and an extra let binding. This work serves milestone 3 of the project plan, equality and linear arithmetic. The plan files it under its "Boolean and EUF proof infrastructure" section.

What changed

  • A step that resolves a clause down to one kept literal is now written without a stated type, and Lean infers it.
  • Every other kind of step, such as a case split or a proof by contradiction, still states its type, because Lean needs it there.
  • A step applied to its hypotheses and used once on the next line is now written directly at that use.
  • That rewrite only accepts hypotheses and decidability witnesses as arguments, so it can never move a reference to another pending step.
  • New tests check both rewrites, and the size limits on the two large slow benchmarks are tighter.

An analogy for the second change: writing a phone number on a sticky note just to read it once on the next line. The PR dials the number directly instead.

All code changes are in the Lean reconstructor, proof_to_lean.py. No C++ code changed.

Worked example

This PR does not make any new input pass. It shrinks the Lean text for inputs that already passed. So the example below shows the same input before and after. Both versions were accepted. The input is a small QF_IDL problem, written for this report in the style of the PR's DTP tests. All three pieces come from real runs of the old and new scripts.

(a) The input

(set-logic QF_IDL)
(declare-const x Int)
(declare-const y Int)
(declare-const z Int)
(assert (or (>= (- x y) 1) (>= (- y x) 1)))
(assert (or (not (>= (- x y) 1)) (>= (- y z) 1)))
(assert (or (not (>= (- y z) 1)) (>= (- z x) 0)))
(assert (or (not (>= (- y x) 1)) (>= (- x z) 0)))
(assert (or (not (>= (- x z) 0)) (>= (- z y) 1)))
(check-sat)

Either x > y or y > x. Each choice leads, through the other clauses, to a cycle of strict inequalities, which is impossible.

Review

The reviewer's verdict was approve. There were no blocker, major, or minor findings.

  • Nit, fixed. The reviewer read the new paragraphs in the README and the plan. They were not wrapped to the same width as their neighbours, so they looked ragged. Nothing broke, but docs are read often. Both paragraphs were reflowed in the second commit.
  • Suggestion, fixed. The reviewer noticed that the re-application pattern accepted any name as an argument. In theory, one pending step could then name another pending step. Substituting them in place would make the order of substitution matter. The pattern now accepts only hypotheses and witnesses, and a unit test covers a step-named argument. The Lean text of all four measured inputs stayed the same.
  • Suggestion, deferred. The reviewer pointed out that CI never runs the large DTP test. A cheap size-only check in the default tier would catch growth earlier. This is left as a follow-up. The default tier already bounds DTP seed 1 below 505,000 characters.

The reviewer also checked soundness. Only proof terms change, and Lean checks each one. A wrong inferred type would make Lean reject the file. It could never make Lean accept a false claim. A scan of eight inputs found every untyped step was a plain unit resolution.

Risks and open questions

  • Both rewrites match on the generated text. A future step kind that looks like a resolution would fail loudly in Lean. It would not pass silently.
  • DTP_k2_n35_c245_s9 still uses 7.45 of 8 GB, and its test runs only in the slow tier.
  • The QF_AUFLIA benchmark swap_t1_pp_sf_ai_00010_008 still runs out of memory. The excess is in its theory lemmas, not its proof steps.
  • CI results and the local gate record were not available when this page was written.

What comes next

  • Add a size-only check for DTP_k2_n35 or plan-21 to the default test tier.
  • Profile the theory lemmas of swap_t1_pp_sf_ai_00010_008.
  • Look at the 3,579 steps in DTP that still state a type, and at the hypothesis chains in lemma statements.

Glossary

case split
Proving a goal by handling each side of a disjunction separately. Example: assume x > y, then assume y > x.
clause
A disjunction of literals, such as p or not q or r.
elaboration
Lean's step of turning written text into fully typed internal terms. It is where most of the memory goes.
hypothesis
A fact assumed for part of a proof. A step proved under a hypothesis holds only while that assumption is in force.
integer difference logic (QF_IDL)
Constraints of the form x − y ≥ c over integers, with no quantifiers.
let binding
Giving a name to a value so later lines can refer to it. Example: let a := f x.
literal
A Boolean atom or its negation, such as p or not p.
proof by contradiction
Proving a statement by assuming its negation and deriving False.
proof term
A program-like expression whose type is the statement it proves. Lean checks it like code.
refutation
A proof that a set of assertions leads to False, so they cannot all hold at once.
resolution
An inference rule. From A or p and B or not p, conclude A or B.
theorem
The final checked statement. Here: the input assertions imply False.
theory lemma
A clause that holds by the rules of a theory such as arithmetic, not by Boolean logic alone.
type
In Lean, the statement a proof proves. A proof of p or q has type p or q.
type inference
Lean working out a term's type by itself, so the text does not need to state it.
unit resolution
Resolution against single literals. From p or q and not p, conclude q.
