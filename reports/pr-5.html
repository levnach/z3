In one paragraph

The certificate pipeline for unknown functions and equality used to accept inputs over only one kind of value. This PR certifies inputs with any number of kinds. The certificate keeps every kind's name, Python checks that no step mixes kinds, and Lean sees all kinds as one type. This matters because hardware-derived benchmarks declare one kind per bit width, so they were all out of reach. A reviewer found that the first version could certify a satisfiable input when one name was reused for two symbols. That hole was closed before the merge.

Background

Iterations 2 and 4 built the path for unknown functions: Z3's clause log becomes a certificate, a Python reconstructor turns it into a Lean file, and Lean checks it. That path handled unknown constants, functions, predicates, if-then-else terms, and "all different", but only over one declared kind of value. Z3 already solved many-kind inputs, and its clause log already declared every kind, so nothing new was needed from the solver. The work serves milestone 3 of the plan, "Equality and linear arithmetic", which asks for equality reasoning to be completed end to end before new theories are added.

What changed

  • Several kinds of value are accepted. You can now certify an input that declares two or more kinds, with functions mapping one kind to another.
  • The certificate stays faithful. Every exported declaration keeps the kind names from the input.
  • Python checks that kinds are never mixed. The reconstructor refuses a certificate where a function gets the wrong kind, an equality compares two kinds, or a declared kind is never used.
  • Lean sees one type for all kinds. Think of marbles of several colours in one box: if nobody ever compares a red marble with a blue one, a proof about the box is a proof about each colour.
  • Reused names are rejected. Z3 allows one name to be declared twice with different kinds. The pipeline now refuses such inputs at the front door, because its argument needs each name to mean one thing.
  • Binding checks full signatures. Matching certificate symbols to input symbols now compares argument kinds and result kind, not just the name.

Worked example

The input declares two kinds, A and B. The function f maps an A value to a B value, and p is a yes/no question about B values. Since a1 equals a2, the question cannot have different answers for them. The example was cut down from the PR's two-kind tests.

(a) The input

(set-logic QF_UF)
(declare-sort A 0)
(declare-sort B 0)
(declare-fun a1 () A)
(declare-fun a2 () A)
(declare-fun f (A) B)
(declare-fun p (B) Bool)
(assert (= a1 a2))
(assert (p (f a1)))
(assert (not (p (f a2))))

Review

The reviewer requested changes: one blocker and two minor findings. All three were fixed before the PR was opened.

Blocker: a certificate could be rebound to a satisfiable input

The reconstructor matched certificate symbols to input symbols by name alone, while Z3 allows one name to be declared twice with different kinds. The reviewer took the honest certificate of a one-kind unsat input and swapped in a satisfiable two-kind input whose assertions print identically. With one unused declaration added, the reconstructor accepted it and Lean verified False for a satisfiable problem. This broke the trust boundary the project rests on. The fix rejects reused names at the front door, checks full signatures when binding, and tags terms with their kind. The exploit is now a regression test.

Minor: an unused declaration could pad the set of kinds

The exploit needed the padding because the set of kinds was computed from all declarations, used or not. The reconstructor now rejects a declaration over a kind that no proof step references.

Minor: the README claimed more than the code did

The README said reused names were rejected, but only the binder did so, and only when both copies reached the proof graph. The rejection now happens at classification, and the README states the precondition the soundness argument relies on.

Risks and open questions

  • The one-type argument is not formalised. Lean checks the collapsed theorem, but the step back to many kinds is a documented paper argument, like treating reals as rationals.
  • Reused names are now rejected everywhere. This also affects Boolean and arithmetic inputs, but no input that previously certified is lost.
  • One error message changed. Renaming a kind inside a certificate now fails with wrong argument sort.
  • Still rejected. Unknown functions taking or returning true/false values, unknown functions mixed with arithmetic, integer arithmetic, and harmless set-option commands.

What comes next

True/false arguments and results of unknown functions are now the most common remaining rejection in hardware-derived benchmarks. A set of many-kind inputs in the separate z3test repository would put this fragment into the CI matrix directly.

Glossary

Kind of value (sort)
A declared category of values, such as A or B, with no built-in meaning.
Unknown function (uninterpreted function)
A function with a declared signature but no definition; only equal inputs are guaranteed equal outputs.
Carrier
The Lean type that stands in for a kind of value. This PR uses one carrier, _U, for every kind.
Well-sorted
Every function receives arguments of the kinds it was declared for, and equalities compare one kind only.
Overloading
Declaring one name twice with different signatures. Z3 allows it; the pipeline now rejects it.
Signature
The list of argument kinds and the result kind of a declared symbol.
Binder
The reconstructor step that matches each certificate symbol to a symbol parsed from the original input.
Congruence
The rule that equal arguments give equal function results, used by Lean's grind tactic here.
Standard axioms
The three axioms Lean's library relies on; the generated proofs depend on nothing else.
