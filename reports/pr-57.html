Evaluate comparisons of numeral-valued ites in ite value tables

Pull request levnach/z3#57 · state OPEN · opened 2026-10-31T08:52:45Z · loop iteration 57

This pull request is open and not merged. It contains two commits. The change commit is 43d90c864, on top of base c4658bdcd.

In one paragraph

This PR lets the Lean reconstructor certify a rewrite step in which Z3's rewriter has already decided comparisons like (= s 2). Here s is an if-then-else term whose branches are all numerals. Before, each such comparison was an independent atom in the value table, so the two sides looked different. The step fell back to one large grind call, which ran out of heartbeats. Now the table evaluates those comparisons, and the two sides match. Each matching pair gets its own small lemma, proved by a case split on the Boolean variables. This closes the last of four known QF_LRA rewrite failures, the benchmark Carpark2-ausgabe-6. The Lean kernel still checks every lemma, so nothing new is trusted.

Background

The reconstructor could already prove large rewrite steps one atom at a time, on a normalized path. PR #56 extended that path to ite terms that Z3 reshapes, by pairing ites with equal value tables. It still failed on the sal/carpark benchmarks. There, a rate ite tests a selector ite, as in (= s 4), and Z3's rewriter turns those tests into disjunctions of conjunctions of flags. This PR serves Milestone 3 of the plan, equality and linear arithmetic.

What changed

  • The reconstructor now sees that (ite (= s 2) 20 …) and the ite Z3 rewrote it into, (ite a 20 …), take the same value under every assignment of the flags.
  • The lemma that relates such a pair can now be proved by trying every true/false combination of the flags, then simplifying, then running grind.
  • A Lean warning about unused simp arguments is now silenced only on lemmas that use this new split, not on every lemma over ites.
  • New tests generate inputs with the carpark shape and check both proof cores in Lean.
  • The plan document records the change and marks the old open item as done.

Think of two price lists. One says “if the dial reads 2, charge 20”. The other says “if switch a is on, charge 20”. The dial is wired to the switches. Listing the price for every switch setting shows the lists agree. The value table now does exactly that.

Review

The reviewer approved with two nits and two suggestions, and no blocker, major, or minor findings. They reran the benchmark and the ablations and found no axiom beyond the standard three.

Nit 1, fixed. Reading the generated Lean, the reviewer saw a linter switch on every lemma over ites, even lemmas with no simp call. It silenced nothing, and it could later hide a real warning. Now it is printed only with the new split, and the test checks that the counts match.

Nit 2, fixed. A 97-character line in the plan document was rewrapped. This was cosmetic.

Suggestion 1, not applied. A heartbeat timeout in one alternative is not caught by the next, so a slow failing split could starve the old fallback. No such case appeared, and the current order was faster. It is a follow-up.

Suggestion 2, not applied. Table evaluation could cache shared parts. The reviewer measured the same slowdown on deep nesting with the old code. It is a follow-up.

Risks and open questions

  • More ites now share a table. If a lemma cannot prove an equality the table claims, Lean fails where grind once ran. No such case appeared.
  • The split is exponential in the number of flags. It is capped at 8 flags, so at most 256 cases per lemma.
  • CI and local gate results were not available for this page.

What comes next

  • Comparisons of ites with a variable branch, such as (= (ite c x 4) 4), are still independent atoms.
  • The split could also case on arithmetic conditions, not only on Boolean variables.
  • Caching in the table evaluation, and trying the split later when no comparison was evaluated.
  • Work on the tta_startup benchmark is unchanged and remains in the backlog.

Glossary

ablation
An experiment that removes one part of a change to see whether that part is needed.
atom
A formula with no Boolean connective inside, such as a0 or (< z0 3).
axiom
A statement accepted without proof. A Lean proof here may use only the three standard ones: propext, Classical.choice, Quot.sound.
Boolean variable
A constant of sort Bool, true or false. In the example, a0 and b0 are Boolean variables, also called flags.
case split
Proving a goal separately for each possibility, for example once with a0 true and once with it false. Lean's by_cases tactic does this.
clause log
A record of the clauses Z3 derived while solving. It is one of the two proof sources, or cores, the exporter can use. The other is the legacy proof object.
conjunction
An “and” of formulas, written (and p q).
disjunction
An “or” of formulas, written (or p q).
grind
A Lean tactic that searches for a proof automatically, using case splits, equalities, and linear arithmetic.
heartbeat
Lean's unit of work. Each declaration may use a fixed budget, here 1,000,000. Exceeding it is a timeout error.
if-then-else term (ite)
A term (ite c t e) whose value is t when condition c holds and e otherwise.
kernel
The small core of Lean that checks every proof. It is the only part that must be trusted.
lemma
A small proved statement used as a step in a larger proof.
linter
A checker that warns about suspicious but valid code. The checks here treat warnings as errors.
normal form
A fixed way of writing a formula, so that equal formulas look the same. For example, (< x 3) and (not (<= 3 x)) get one normal form.
numeral
A constant number written in the input, such as 2 or 20.
QF_LRA
The SMT-LIB logic of quantifier-free linear real arithmetic: Boolean structure over sums of real variables times numerals.
refutation
A proof that a set of assertions implies False.
rewrite step
A proof step where Z3's rewriter replaces a formula with an equivalent, simpler one. The certificate must show the two are equivalent.
simp
A Lean tactic that rewrites a goal with a given list of equations, such as ite_true, until it is simpler.
sort
The type of a value, such as Int, Real, or Bool.
tactic
A Lean command that builds part of a proof, such as grind, simp, or by_cases.
value table
The reconstructor's list of an ite's value under every true/false assignment of its condition atoms. Two ites with the same table are treated as equal, and a lemma must then prove it.
