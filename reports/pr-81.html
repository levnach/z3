Tell maps of different functions apart in the clause-log replay keys

This pull request is open and not merged. The change commit is 0a834da3c. The pull request has two commits: the fix 293ffa2db and a review follow-up 0a834da3c.

In one paragraph

The clause-log replay matches each clause that the clause log assumes to an input conjunct. It does this by comparing structural keys. Before this PR, the key of an array map ignored which function was mapped. So ((_ map and) a b) and ((_ map or) a b) got the same key. Maps of two uninterpreted functions, and maps of + and -, collided the same way. After preprocessing split a conjunction, the replay could pick the wrong conjunct. It then emitted a rewrite step that the tactic grind could not prove, and Lean rejected the whole certificate. Now a map's key names its function by its signature, and a constant array's key names its sort. Such refutations now pass Lean. No Lean file, axiom, or trust setting changed.

Background

Recent iterations taught the pipeline to certify arrays, array maps, sets, and enumeration datatypes through the clause log. Iteration 80 noticed that map keys collide, but it found no input that failed because of it. This iteration found three. Each one exported and reconstructed, and then Lean rejected it. That was a completeness gap, not a soundness hole, because Lean caught the bad step. The work serves milestone 4 of the plan, "Broader theories and integration", where arrays are one of the listed extensions.

What changed

Think of a coat check that writes only "black coat" on each ticket. Two guests with black coats can get each other's coats back. The fix writes the owner's name on the ticket too.

  • The replay can now tell ((_ map and) a b) from ((_ map or) a b), because a map's key includes its function's signature.
  • Maps of two different uninterpreted functions, or of two built-in operators such as + and -, now get different keys as well.
  • Constant arrays of different sorts, such as (Array Int Bool) and (Array Real Bool), no longer share a key.
  • Three small inputs that Lean used to reject are now tests that check in Lean on every run of the suite.
  • The plan document records the fix and lists the operators that will need the same treatment later.

Risks and open questions

  • Fewer key matches. The same map written two ways might now miss its key. A miss falls back to a slower solver-based equivalence check, which is still sound. The reviewer tried nested maps and two constant arrays, and both verified.
  • Text keys. Keys use the signature text Z3 prints. That text is stable within one context.
  • Numerals of different sorts. 0 and 0.0 still share a key as arguments of built-in operators.

What comes next

  • Key numerals by sort as well as value.
  • Key accessors, bit-vector operators, and as-array once the exporter supports them.
  • Turn the random map sweep into a pinned-seed test.

Glossary

array
A total map from an index sort to an element sort, read with select and updated with store. Example: (Array Int Bool).
array map
An array built by applying one function at every index of other arrays. ((_ map and) a b) holds "a[i] and b[i]" at each index i.
axiom
A statement that Lean accepts without proof. Adding one widens what must be trusted.
certificate
The evidence Z3 exports for an unsat result, which the reconstructor turns into a Lean proof.
clause
A disjunction of literals, such as p ∨ ¬q. A literal is a Boolean atom or its negation.
clause log
The record of clauses Z3's solver assumed and derived while it searched for a refutation.
clause-log replay
The exporter's pass that walks the clause log and justifies each step against the original input.
completeness
The checker accepts every correct proof. A completeness gap means some valid results are rejected.
conjunct
One part of a conjunction. In (and q r), q and r are the conjuncts.
constant array
An array with the same value at every index, written ((as const (Array Int Bool)) p).
preprocessing
Simplifications Z3 applies before the main search, such as splitting a conjunction into separate assertions.
refutation
A proof that a set of assertions implies False.
rewrite step
A proof step claiming that one formula equals or follows from another after rewriting.
signature
A function's name with its argument sorts and result sort, such as (declare-fun f (Int) Int).
sort
The type of a value in SMT-LIB, such as Int, Bool, or (Array Int Bool).
soundness
The checker accepts only correct proofs. A soundness hole would let a false claim through.
structural key
A value computed from a formula's shape, used to find matching formulas quickly. Two formulas should share a key only if they mean the same thing.
tactic
A Lean command that builds part of a proof automatically. grind and omega are tactics.
theory lemma
A clause that holds because of a theory, here arrays, rather than by Boolean logic alone.
uninterpreted function
A function symbol with no fixed meaning. The only thing known is that equal arguments give equal results. Example: f in (declare-fun f (Int) Int).
