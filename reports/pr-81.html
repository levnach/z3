In one paragraph

The clause log replay matches each clause the log assumes to an input conjunct by a structural key. That key ignored the parameters of built-in heads. So array maps of and and of or over the same arrays got one key, and so did maps of two uninterpreted functions. After preprocessing split a conjunction, the replay derived one map's conjunct from the other's. Lean then rejected that rewrite step, because the tactic grind could not prove it. Now a map's key names its function by signature, and a constant array's key names its sort. This closes a completeness gap, so these inputs now get a Lean-checked refutation. It was never a soundness hole, because Lean caught every wrong step.

Background

Earlier iterations taught the clause-log path to certify arrays, constant arrays, and array maps of Boolean operators, arithmetic, and uninterpreted functions. Iteration 80 noticed that two different maps could share a replay key, but found no failing input. This PR found three. Each has two guarded conjunctions with different maps over the same arrays. The work serves milestone 4 of the plan, "Broader theories and integration", where arrays are one of the listed extensions.

What changed

  • The replay can now tell ((_ map and) a b) from ((_ map or) a b), so it matches each split conjunct to the input assertion it really came from.
  • Maps of two declared functions, such as f and g, and maps of + and - over the same arrays now get different keys too.
  • Two constant arrays that differ only in their index sort, such as (Array Int Bool) and (Array Real Bool), no longer share a key.
  • Three small inputs that Lean used to reject are now regression tests that Lean checks in CI.
  • The plan document records which other parameterized heads still key without their parameters, so the same gap is not reopened later.

Think of the key as a label on a filing drawer. Before, the label said only "map", so the and map and the or map shared a drawer, and the replay pulled out the wrong file. Now the label also names the function. The helper that writes it is _parameter_names. No .lean file, axiom, or trust setting changed.

Worked example

This input is the PR's new test conjuncts_map_and_or. Both "before" and "after" below come from real runs made for this report.

(a) The input

(declare-fun a () (Array Int Bool))
(declare-fun b () (Array Int Bool))
(declare-fun c () (Array Int Bool))
(declare-fun d () (Array Int Bool))
(declare-fun q () Bool)
(declare-fun r () Bool)
(assert (and q (= c ((_ map and) a b))))
(assert (and r (= c ((_ map or) a b)) (= c d)))
(assert (select a 0))
(assert (not (select b 0)))
(check-sat)

At index 0, a holds and b does not. So the and map is false there and the or map is true there. But c must equal both maps, which is impossible.

(b) Before: the pre-PR scripts

The old exporter produced a certificate, and the old reconstructor produced a Lean file. Then the Lean check failed, so no proof was published. The failing step tried to prove that the and conjunct is equivalent to the or conjunct: 

def formula_24 ... : Prop := (Iff (formula_5 _atoms _vars _m) (formula_9 _atoms _vars _m))
...
private theorem rewrite_25 (_atoms : Nat -> Prop) (_vars : Nat -> Int) (_m : Interpretation)
    : (formula_24 _atoms _vars _m) := by
  unfold formula_24 formula_9 formula_5
  ...
  first | omega | grind (splits := 64)
z3_proof_….lean:235:18: error: `grind` failed
...
Lean checking failed; no proof was published.

Here formula_5 is c = map and a b and formula_9 is c = map or a b. They are not equivalent, so no tactic could prove this step.

(c) After: the generated Lean

The declarations for the two maps and the conjuncts that use them:

def term_4 ... : (Int -> Prop) := (_map2 And (term_2 _atoms _vars _m) (term_3 _atoms _vars _m))
def formula_5 ... : Prop := ((term_1 _atoms _vars _m) = (term_4 _atoms _vars _m))
def formula_6 ... : Prop := (And (formula_0 _atoms _vars _m) (formula_5 _atoms _vars _m))
...
def term_8 ... : (Int -> Prop) := (_map2 Or (term_2 _atoms _vars _m) (term_3 _atoms _vars _m))
def formula_9 ... : Prop := ((term_1 _atoms _vars _m) = (term_8 _atoms _vars _m))
...
def formula_12 ... : Prop := (And (formula_7 _atoms _vars _m) (And (formula_9 _atoms _vars _m) (formula_11 _atoms _vars _m)))

Arrays become Lean functions from Int to Prop, and _map2 And and _map2 Or are the two maps.

The theorem statement:

theorem unsat (_atoms : Nat -> Prop) (_vars : Nat -> Int) (_m : Interpretation)
    (_h0 : (formula_6 _atoms _vars _m))
    (_h1 : (formula_12 _atoms _vars _m))
    (_h2 : (formula_14 _atoms _vars _m))
    (_h3 : (formula_16 _atoms _vars _m))
    : False :=
  ...

The four hypotheses are the four input assertions, and the theorem says that together they prove False.

The steps that embody the fix:

  let _step_22 : (formula_12 _atoms _vars _m) :=
    _h1
  let _step_23 : (formula_7 _atoms _vars _m) :=
    _step_22.1
  let _step_24 : (formula_9 _atoms _vars _m) :=
    _step_22.2.1
  ...

The or conjunct is now taken straight out of the second assertion, and the bad rewrite_25 step is gone.

The scratch path. The reviewer tried to rerun the random sweep that the plan cited as evidence. The plan pointed to a script outside the repository, so no maintainer could rerun it. The fix describes the sweep without the path or the seed numbers. The three documented inputs now pin the failure in CI instead.

Other parameterized heads. The reviewer noted that datatype accessors, bit-vector extract, and as-array could collide the same way. The author checked that the export rejects all of them today, so no input can fail through them. The plan now says to key them once they are supported. A short allow-list was kept on purpose, because keying every head could split keys that should be shared.

Sentence fragments. Two test comments did not read as whole sentences. They were rewritten.

Risks and open questions

  • Keys can now miss where they used to match, for example the same map written two ways. A miss only sends the replay to its slower solver-based equivalence check, which is still sound. The new test shows that maps the clause log builds key the same as the input's.
  • The keys use printed signature text, which is stable within one context.
  • An Int numeral and a Real numeral with the same value still share a key.
  • The random sweep is not part of CI. Only the three documented inputs guard this failure there.

What comes next

  • Key numerals by sort as well as value, so 0 and 0.0 differ.
  • Key accessors, bit-vector heads, and as-array by their parameters once the export supports them.
  • Turn the random map sweep into a test with pinned seeds.

Glossary

array
A total map from an index sort to an element sort. (Array Int Bool) gives a Boolean for every integer. Lean models it as a function.
assertion
One (assert …) line of the input. Together the assertions must be shown contradictory.
Boolean
The sort of truth values, true and false. Written Bool in SMT-LIB.
clause
A disjunction of literals, such as "p or not q". A literal is an atom or its negation.
clause log
The record Z3 writes as it solves: each clause it assumes, derives, or deletes, with hints on why.
completeness
The checker accepts every correct proof. A completeness gap means a true result gets rejected.
conjunct, conjunction
A conjunction is an "and" of formulas. Each of those formulas is a conjunct. In (and q r), q and r are conjuncts.
constant array
An array with the same value at every index. Written ((as const (Array Int Bool)) p).
grind
A Lean tactic that tries to close a goal automatically by congruence, case splits, and arithmetic. "grind failed" means it found no proof.
map (array map)
An array built by applying a function at every index. ((_ map or) a b) holds at index i when a or b holds there.
parameter (of a declaration)
Extra data fixed inside an operator's name. In (_ map or) the parameter is the function or.
preprocessing
Simplification Z3 does before the main search, such as splitting (and q r) into two separate facts.
refutation
A proof that the assertions together imply False.
replay
Walking through the clause log step by step and turning each step into Lean.
rewrite step
A proof step showing that two formulas are equivalent, so one can replace the other.
signature
A function's name with its argument sorts and result sort, such as (declare-fun f (Int) Int).
sort
The type of a value, such as Int, Real, Bool, or (Array Int Bool).
soundness
The checker never accepts a false claim. A soundness hole would let a wrong result through.
structural key (replay key)
A summary of a formula's shape used to find matching formulas quickly. Two formulas with equal keys are treated as the same.
tactic
A Lean command that builds part of a proof for you, such as omega or grind.
uninterpreted function
A declared function with no fixed meaning. The only rule is congruence: equal arguments give equal results. Example: (declare-fun f (Int) Int).
