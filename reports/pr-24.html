Check alldiff gate clauses natively and log root distinct as input

This pull request is not merged. The report describes the change as of commit 8b7344c27, which holds both commits of the PR on top of base commit 9c2b87b9d.

In one paragraph

Z3's clause log labels each derived clause with a hint naming the rule that justifies it. The alldiff hint covers clauses that come from a distinct constraint. Before this PR the native checker accepted every alldiff hint without reading it, so a forged log could pass the native replay. Now Z3 logs the clauses of a distinct constraint asserted at the root as input clauses. The native checker verifies the one remaining alldiff shape: the two gate clauses that tie a distinct literal below the root to the disjunction of its pairwise equalities. Both are tautologies. Any other alldiff hint is rejected and sent to the SMT fallback check, which refutes a forged log with a countermodel. The Lean refutation is unchanged, because the exporter already tied these clauses to the original assertions.

Background

Before this PR the Lean pipeline already certified distinct constraints over an uninterpreted sort and in linear real arithmetic. It treated every alldiff clause as a consequence of the original assertions, the way it handles an unsat core. The native C++ checker, kept as a diagnostic tool, could not tell a genuine gate clause from a forged one. The PR serves milestone 3, equality with uninterpreted functions and linear arithmetic, where congruence over an uninterpreted function meets the Boolean core.

What changed

  • Proof production. A root distinct constraint is now logged as input clauses, so the log no longer claims a theory lemma no hint could justify.
  • Native checker. The alldiff plugin accepts only two literals of one polarity that form a gate clause, matching equalities up to symmetry.
  • Rejection path. Every other alldiff hint now fails with a countermodel instead of being accepted.
  • Tests. A C++ unit test pins accepted and rejected shapes, and a live-solver Python test checks the new log shapes.
  • Documentation. Exporter comments, the README, and a dated plan note describe which clauses carry alldiff.

Analogy: the old plugin waved through anyone wearing an alldiff badge. The new one checks the badge against exactly two faces.

Worked example

The example is the below-root case from the PR's new Python test: two clauses force the distinct constraint whatever p is, and a third assertion contradicts it. All outputs are from real runs on 2026-10-20, "After" on the PR head and "Before" on a z3 built from the base commit.

(a) The input

(declare-sort U 0)
(declare-const a U)
(declare-const b U)
(declare-const c U)
(declare-const p Bool)
(assert (or p (distinct a b c)))
(assert (or (not p) (distinct a b c)))
(assert (= a c))
(check-sat)

(b) Before

The forged log below invents the three pairwise equalities as one clause with nothing behind it, then refutes them with three assumed disequalities. The old checker accepted it. 

; forged log: infer the pairwise equalities out of nothing, under an alldiff label
(infer $15 $13 $16 (alldiff $15 $13 $16))
(assume (not $15))(assume (not $13))(assume (not $16))
(infer rup)

; pre-PR checker verdict
(proofs +alldiff 1)
(proofs +alldiff 1 +rup 1)

A gate clause missing one pair was accepted the same way. The pre-PR solver also logged a root distinct constraint as an inference, though the clause is just the assertion in clause form.

; pre-PR log of a root (not (distinct a b c))
(infer $10 $12 $14 $16)          ; $16 = (alldiff $10 $12 $14)

The pre-PR Python exporter accepted the input too, and its certificate is byte for byte the current one.

(c) After

Z3's log for the input now carries exactly two alldiff hints, one per gate clause, and the native checker verifies both.

(define-const $9 Bool (distinct a b c))
(define-const $14 Bool (or $15 $13 $16))      ; $15 = (= a b), $13 = (= a c), $16 = (= b c)
...
(infer (not $9) (not $14) $26)                ; $26 = (alldiff (not $9) (not $14))
(infer $9 $14 $27)                            ; $27 = (alldiff $9 $14)
(assume p $9)
(assume (not p) $9)
(assume $13)
...
(infer rup)

; checker verdict on the genuine gate pair
(proofs +tseitin 4 +alldiff 2 +rup 4)

The forged log is now rejected, and the fallback prints a countermodel in which all three equalities are false.

Review

The reviewer approved the change with no blockers and no major findings.

  • Minor, pre-existing, filed as follow-up. The reviewer fed the checker a valid gate hint whose logged clause dropped a literal that RUP could not recover. The plugin rejected it, but the SMT fallback accepted it, because the fallback proves the hint clause together with the logged clause, and a tautological hint leaves nothing to prove. The flaw is in the shared checker framework, untouched here, and the same log passed outright before the PR.
  • Minor, fixed. The new live-solver test lacked the guard its siblings carry, so without a z3 executable it would error instead of skipping. The second commit adds the guard.
  • Nit, fixed. The plan note sat under the arithmetic heading. The second commit moves it, with the xor note, under "Boolean and EUF proof infrastructure".
  • Suggestion, filed as follow-up. A single-argument distinct constraint fails in Lean on both export paths, a pre-existing reconstructor gap.

The reviewer also ran eight distinct-constraint sources through Lean, all passing.

Risks and open questions

  • Consumers of the clause log now see root distinct clauses as input clauses rather than alldiff inferences. The exporter handled both identically, and the pinned old-style logs still replay.
  • Distinct constraints with more than 32 arguments use an equisatisfiable encoding over fresh symbols, now labelled input. The exporter rejected them before as well.
  • The checker is stricter than necessary on shapes Z3 never emits. Rejection costs only a fallback check.
  • The fallback flaw remains open, so a valid gate hint with a tampered logged clause can still pass. CI results are unknown at the time of this report.

What comes next

  • Fix the fallback to check the logged clause alone, with a replay regression for a dropped non-RUP literal.
  • Give the gate clauses a def-axiom shape in the exporter so they stop going through the unsat-core fallback.
  • Handle a single-argument distinct constraint in the Lean reconstructor.
  • A root distinct constraint over a finite sort with too few elements still emits an empty clause with an empty Tseitin status that nothing can verify.

Glossary

Boolean
A value or variable that is either true or false. In SMT-LIB the sort is written Bool.
clause
A disjunction of literals, such as "p or not q or r". It is satisfied when at least one literal is true.
clause log
The text Z3 writes while solving, one line per clause it assumed or derived, with a hint saying why each derived clause holds.
congruence
The rule that equal arguments give equal results: if a = b then f(a) = f(b). It is the heart of equality reasoning.
countermodel
An assignment of values that makes a supposedly unsatisfiable set of formulas true, proving the claim wrong.
def-axiom
A proof step whose clause is a tautology about a connective, such as "not (a or b), or a, or b". It needs no hypotheses.
disjunction
An "or" of several formulas, written (or x y z) in SMT-LIB. It is true when any part is true.
distinct constraint
The SMT-LIB formula (distinct a b c), true when no two arguments are equal. It is shorthand for a conjunction of disequalities.
equality with uninterpreted functions (EUF)
The logic of equality, uninterpreted functions, and uninterpreted sorts, with no arithmetic. Its rules are reflexivity, symmetry, transitivity, and congruence.
equisatisfiable
Two formulas that are both satisfiable or both unsatisfiable without being equivalent. Encodings with fresh symbols are usually only equisatisfiable.
gate clause
A clause that defines a fresh Boolean literal in terms of a compound formula. For a distinct constraint d and its pairwise equalities e, the two gates are "not d or not e" and "d or e".
hint
The label on a derived clause in the clause log, such as alldiff, tseitin, or rup, naming the rule a checker should use.
input clause
A clause taken directly from the user's assertions, written (assume ...) in the log. Also called an assumption.
linear real arithmetic
Formulas over real-valued variables with addition, multiplication by constants, and comparisons such as x + 2y <= 3.
literal
An atomic formula or its negation, such as p or (not (= a b)).
polarity
Whether a literal is positive (the atom itself) or negative (its negation). The two gate clauses have opposite polarity.
refutation
A proof that a set of formulas cannot all be true, ending in the empty clause or in False.
root
The top level of the input: a formula asserted directly rather than nested inside another formula. A root distinct constraint has no literal of its own.
RUP (reverse unit propagation)
A clause check: assume all its literals false and run unit propagation. A contradiction means the clause follows from the current clauses.
SMT fallback check
What Z3's checker does when no native plugin accepts a hint: it asks a fresh solver whether the negated clause is satisfiable and rejects the step if so.
sort
The type of a value, such as Int, Real, Bool, or a user-declared sort.
tactic
A Lean command that builds part of a proof automatically, such as grind or unfold.
tautology
A formula true under every assignment, such as "p or not p". It can be checked without hypotheses.
theory lemma
A clause valid in a background theory, such as arithmetic or equality, rather than by Boolean reasoning alone.
Tseitin encoding
The standard way to turn a nested Boolean formula into clauses by naming each subformula with a fresh literal and adding its gate clauses.
uninterpreted function
A function symbol with no fixed meaning, only a name and sorts. Any interpretation respecting congruence is allowed.
uninterpreted sort
A sort with no fixed set of elements, declared with (declare-sort U 0). Its values are only known to be equal or different.
unit propagation
Repeatedly finding a clause with all literals but one false and setting the remaining literal true.
unsat core
A subset of the assertions that is already unsatisfiable on its own.
