Bound every z3 run of the clause-log export by time and memory

In one paragraph

To build a certificate for a linear real arithmetic or EUF problem, the exporter starts the z3 executable twice. One run writes a clause log, and the other performs proof trimming on it. Before, neither run had a memory limit, and the solver had a time limit only on request. Now both runs always carry both limits, by default 600 seconds and 8192 MB. When a run hits a limit, the export stops with an error that names the limit. A limit can only end an export early, so the set of refutations Lean accepts is unchanged. What it buys is safety: benchmark sweeps can no longer leave runaway solver processes behind.

Background

On 2026-10-30 a sweep exported certificates without a timeout. Its own deadlines killed the Python workers, but eleven z3 processes kept running. Together they used 220 GB of memory, and the machine crashed. Also, a trimmer stopped at a limit looked like an unusable clause log, so the exporter silently fell back to the untrimmed log. The PR serves the regression matrix, which the plan names as the current top priority. That matrix runs the exporter over many benchmarks, so every run must be bounded.

What changed

  • Every z3 run of the clause-log export now stops by itself after 600 seconds or 8192 MB, unless the caller sets other limits.
  • A caller can now set a memory limit with the new --memory option.
  • Hitting a limit now gives an error that names the run and the limit.
  • A trimmer that hits a limit no longer silently falls back to the untrimmed replay.
  • Limits too large for z3 or Python to hold now get a clear usage error instead of a crash.

Think of circuit breakers: each run now has its own, and its label tells you which one tripped. As a backstop, Python kills a run that outlives its time limit by 30 seconds. The PR has two commits: the first adds the limits, and the second rejects limits z3 cannot hold.

Worked example

This PR makes no new input certifiable, so the example has two parts, both from real runs. Part 1 shows a hard input hitting a limit. Part 2 shows a small input certified exactly as before. Paths in the outputs are shortened to file names.

Part 1: a hard input hits the limits

(a) The pigeonhole formula for 11 holes, generated by the PR's test helper. Only a few of its 870 lines are shown.

(declare-const p0_0 Bool)
(declare-const p0_1 Bool)
...
(assert (or p0_0 p0_1 p0_2 p0_3 p0_4 p0_5 p0_6 p0_7 p0_8 p0_9 p0_10))
...
(assert (or (not p0_0) (not p1_0)))
...
(assert (or (not p10_10) (not p11_10)))

Each Boolean variable pP_H means "pigeon P sits in hole H". The first kind of clause puts every pigeon in some hole. The second kind forbids two pigeons from sharing a hole.

(b) Before, with the base commit's exporter and --core clause-log --timeout 1:

proof_certificate.py: error: the solver did not report unsat: timeout

The run stopped, but the message does not name the limit. A memory limit could not be requested at all:

proof_certificate.py: error: unrecognized arguments: --memory hard.smt2

(c) After, with the same timeout, and then with --timeout 60 --memory 20:

proof_certificate.py: error: the clause-log solver run exceeded the time limit of 1 s
proof_certificate.py: error: the clause-log solver run exceeded the memory limit of 20 MB

Each run ended in about one second. A limit that is too large is now refused before z3 starts:

proof_certificate.py: error: --timeout must be a positive number of seconds, at most 1000000

Part 2: certification is unchanged

(a) A small linear real arithmetic input, taken from the PR's existing tests:

(set-logic QF_LRA)
(declare-const x Real)
(declare-const y Real)
(declare-const z Real)
(assert (>= (+ (* 2.0 x) y) 5.0))
(assert (<= (+ x (* 3.0 z)) 1.0))
(assert (<= (- y (* 6.0 z)) 2.0))
(assert (<= x 0.0))
(check-sat)

(b) Before: the old exporter accepted this input too, and wrote a byte-for-byte identical certificate.

(c) After: the generated Lean file, trimmed. The Lean check accepted it and printed "Lean checks passed."

def term_1 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Rat := _vars 0
...
def formula_6 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := ((term_4 _atoms _vars) >= (term_5 _atoms _vars))
...

Each input term becomes a small definition. Here formula_6 is the first assertion, 2x + y ≥ 5.

private theorem th_lemma_46 (_atoms : Nat -> Prop) (_vars : Nat -> Rat)
    : (formula_45 _atoms _vars) := by
  unfold formula_45 formula_44 formula_43 ...
  grind (splits := 64)

This theory lemma says three of the bounds cannot all hold, and the tactic grind proves it.

theorem unsat (_atoms : Nat -> Prop) (_vars : Nat -> Rat)
    (_h0 : (formula_6 _atoms _vars))
    (_h1 : (formula_12 _atoms _vars))
    (_h2 : (formula_16 _atoms _vars))
    (_h3 : (formula_18 _atoms _vars))
    : False :=
  ...

The main theorem takes the four assertions as hypotheses and derives False.

Review

The reviewer approved, with no blockers or major findings. All three smaller findings were fixed in the second commit.

  1. Minor: huge timeouts crashed. The reviewer passed a timeout of 107 seconds, and Python crashed with an OverflowError. Before the PR, a huge timeout was the usual way to say "no limit", so this mattered. The timeout is now capped at 106 seconds, and larger values get a usage error.
  2. Nit: huge memory values confused z3. A memory limit of 240 MB gave a confusing z3 parameter error. The fix uncovered a worse case: 4294967295 MB makes z3 report "out of memory" at once, which looks like a real limit hit. Memory is now capped at 222 MB, about 4 TB.
  3. Nit: some number types were refused. The first commit refused values such as a Fraction, which the old code took. Validation now accepts any real timeout and any integer memory value, except True and False.

Risks and open questions

  • An export that truly needs more than 600 seconds or 8 GB per run now fails, unless the caller raises the limits.
  • Detecting a limit hit relies on how z3 reports it. Those messages were checked on this build only.
  • In z3test, a trimmer that runs out of memory is now reported as "unsupported", not as a separate memory-out status.
  • CI results and the local gate result were unknown when this page was written.

What comes next

The legacy Boolean core still solves inside Python with no limit, and the Python replay has no time budget. The PR lists bounding both as follow-ups, along with letting z3test pass its own memory limit.

Glossary

Boolean
A value that is either true or false. In SMT-LIB its sort is Bool.
certificate
A file that records the steps of a proof, so that an independent checker can confirm it without trusting the solver.
clause
A disjunction of literals, true when at least one literal is true. Example: (or (not p0_0) (not p1_0)).
clause log
A file in which the solver writes every clause it assumes, derives, or deletes while it searches, with hints for theory steps.
EUF
The theory of equality with uninterpreted functions: functions whose only known property is that equal inputs give equal outputs.
hypothesis
A statement a theorem assumes. Here, each input assertion becomes one hypothesis of the final theorem.
linear real arithmetic
Constraints that add and compare real-valued variables and multiply them only by constants, such as 2x + y ≥ 5. In SMT-LIB the logic is called QF_LRA.
literal
An atomic formula or its negation, such as p0_0 or (not p0_0).
pigeonhole formula
A classic unsatisfiable set of clauses saying n + 1 pigeons fit into n holes, one pigeon per hole. It is famously hard for resolution, so it makes a good stress test.
proof trimming
Removing the steps of a clause log that the final contradiction does not depend on, so the checker has less to replay.
refutation
A proof that a set of assertions cannot all be true, ending in False.
regression matrix
The project's table of benchmark inputs and export settings, run regularly to catch any input that stops being certified.
sort
The type of a value in SMT-LIB, such as Int, Real, or Bool.
tactic
A command in a Lean proof that builds part of the proof automatically. grind is one such tactic.
theorem
A statement together with a proof that Lean has checked.
theory lemma
A clause that holds because of a background theory such as arithmetic, not because of Boolean logic alone. Example: x ≤ 0 and x ≥ 1 cannot both hold.
