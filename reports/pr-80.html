Certify enumeration datatypes in Lean through the clause log

Pull request levnach/z3#80 · state OPEN · opened 2026-11-06T20:37:23Z · loop iteration 80

This pull request is open and not merged. The change it proposes ends at commit b3054dc30.

In one paragraph

Inputs that declare an enumeration datatype can now be certified in Lean. Before this PR, the frontend rejected every datatype declaration. Now a sort whose constructors all take no arguments is accepted. Its constructors and recognizers become ordinary terms in the Lean theorem. The Lean statement gains facts, read only from the input: the constructors differ, and every value equals one of them. The datatype hints in the clause log become theory lemmas that Lean proves from those facts. A small C++ change was also needed. A distinct over more terms than the sort has values used to be refuted by an empty clause with an empty hint, which certified nothing. With proofs on, Z3 now adds the pairwise disequalities, so the refutation can be checked step by step.

Background

Before this PR, the pipeline handled uninterpreted sorts, uninterpreted functions, linear arithmetic, arrays, sets, and maps. Any declare-datatype or declare-datatypes command stopped the export at once. An earlier attempt, fork PR #67, was never merged, and later work rewrote much of its base. This PR redoes it on the current master. It serves milestone 4 of the project plan, "Broader theories and integration", which treats each new theory as its own extension.

What changed

  • You can now certify inputs that declare an enumeration, such as a Color sort with values red, green, and blue.
  • You can now use recognizers, in both the (_ is red) form and the older is-red form.
  • You can now certify a distinct that has more terms than the sort has values, which is a pigeonhole argument.
  • The clause-log replay now tells (= x red) and (= x blue) apart, which it previously could have confused.
  • Unsupported shapes are rejected with a clear message: datatypes with fields and their accessors, parametric datatypes, arrays over an enumeration, and pigeonholes too large for Lean.

Think of an enumeration as a traffic light. It has exactly three colors, no two colors are the same, and the light always shows one of them. The new Lean facts say exactly those two things, and nothing more.

Worked example

This is the pigeonhole input from the PR's new tests. Four constants must all differ, but Color has only three values. I ran it through the old and the new scripts for this page.

(a) The input

(declare-datatypes ((Color 0)) (((red) (green) (blue))))
(declare-const a Color)
(declare-const b Color)
(declare-const c Color)
(declare-const d Color)
(assert (distinct a b c d))
(check-sat)

(b) Before

(c) After

The new scripts produced a 750-line Lean file. scripts/check_lean.sh accepted it: "Lean checks passed." The excerpts below are trimmed.

-- Enumeration "Color" is part of _m.U with constructors "red", "green", "blue", _m.ctors 0 to 2 (enum_distinct, enum_cases_*, enum_fcases_*).

structure Interpretation where
  U : Type
  elems : Nat -> U
  ...
  ctors : Nat -> U
  enum_distinct : (And (Not (ctors 0 = ctors 1)) (And (Not (ctors 0 = ctors 2)) (Not (ctors 1 = ctors 2))))
  enum_cases_0 : (Or (elems 0 = ctors 0) (Or (elems 0 = ctors 1) (elems 0 = ctors 2)))
  ...
  enum_cases_3 : (Or (elems 3 = ctors 0) (Or (elems 3 = ctors 1) (elems 3 = ctors 2)))

The interpretation now carries the three colors as ctors 0 to ctors 2, states that they differ, and states that each constant a to d is one of them.

    : False :=
  ...

The theorem says: in any interpretation where a, b, c, and d are pairwise different, we reach False.

private theorem th_lemma_12 (_atoms : Nat -> Prop) (_m : Interpretation)
    : (formula_11 _atoms _m) := by
  unfold formula_11 formula_10 term_9 formula_8 term_7 formula_6 term_5 term_2
  have _ed := _m.enum_distinct
  have _ec2 := _m.enum_cases_2
  grind (splits := 64)

This lemma is one of Z3's datatype case splits, a clause of three literals: c is blue, red, or green, and Lean's grind tactic proves it from the two new facts.

Review

The reviewer approved the PR with three findings and no blockers.

  • Minor: the pigeonhole limit was too generous. The reviewer built a distinct of 8 terms over 7 constructors. The exporter accepted it, but Lean ran out of memory on the result. That matters because users were promised a clean rejection, not a late Lean failure. New measurements showed that the number of terms matters too. The limit is now 5 constructors and 16 terms, and a slow test checks the largest accepted case.
  • Minor: proofs can now be slow for large pigeonholes. With proofs on, Z3 now searches the pigeonhole instead of answering instantly, and timed out at 11 constructors. This was accepted and documented, because the old fast answer certified nothing. Runs without proofs are unchanged.
  • Nit: a crash was described as current. On this build the exporter rejects the old empty hint rather than Z3 crashing. The wording now credits the crash to iteration 67's build.

Risks and open questions

  • Large pigeonholes with proofs on are now an exponential search in Z3. A counting lemma would fix this properly.
  • Wide distinct terms are costly in Lean, which is why the term limit is 16.
  • Only about 6% of the random seeds produce a datatype hint, so the hand-written tests carry most of the coverage.
  • A related replay-key defect remains for maps: (_ map and) and (_ map or) can share a key. It is listed in the backlog.

What comes next

The PR lists these follow-ups: a counting lemma for the distinct shortcut, arrays and maps over enumerations, datatypes with fields, and enumerations on the legacy core.

Glossary

accessor
A function that reads a field of a datatype value, such as head of a list. Enumerations have none.
case split
Reasoning by trying each possible value in turn, such as "c is red, green, or blue".
clause
A disjunction of literals, such as a = red ∨ a = blue.
clause log
The file Z3 writes while solving, listing each clause it learns and a hint for why it holds.
constructor
A function that builds a datatype value. In an enumeration every constructor is nullary, a fixed value such as red.
datatype hint
The hint Z3's datatype solver attaches to a clause, such as a case split over constructors or a clash between two of them.
disequality
A statement that two terms differ, such as a ≠ b.
distinct
The SMT-LIB operator saying all its arguments are pairwise different. (distinct a b c) means a≠b, a≠c, and b≠c.
enumeration datatype
A datatype whose constructors all take no arguments and which has no type parameters, such as Color with red, green, blue.
hint
The justification attached to a clause in the clause log, telling the checker which reasoning step produced it.
literal
An atomic formula or its negation, such as a = red or ¬(a = red).
parametric datatype
A datatype with a type parameter, such as a list of T. Not supported here.
pigeonhole principle
If more items than boxes go into boxes, two items share a box. Four distinct constants cannot fit in three colors.
recognizer
A predicate that tests which constructor built a value. ((_ is red) x) is true exactly when x is red.
refutation
A proof that the assertions lead to a contradiction, so they cannot all hold.
sort
The type of a value in SMT-LIB, such as Int, Bool, or Color.
tactic
A Lean command that builds part of a proof automatically. grind is a tactic that combines case splits and equality reasoning.
theory lemma
A clause that holds because of a theory's meaning, not because of the input, such as "a Color is red, green, or blue".
uninterpreted function
A function symbol with no fixed meaning, only the rule that equal arguments give equal results.
uninterpreted sort
A sort with no fixed values, declared with declare-sort.
unit propagation
Deriving a literal from a clause whose other literals are all false. The replay uses it to check each logged clause.
