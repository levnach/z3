Ignore harmless front matter in the proof exporters

Pull request #15 Merge commit cc51040 Merged 2026-10-16T05:19:16Z Loop iteration 15

In one paragraph

The exporter used to reject any SMT-LIB file whose front matter did not match one exact shape. It accepted a single option and only three queries. This PR teaches it to skip options that only configure output, models, resource limits, or search. It also accepts tactics in check-sat-using, named assertions, and the output queries for models and unsat cores. Nothing new is trusted. The skipped commands never reach the solver run, the certificate records the input verbatim, and the refutation is still a theorem about the parsed assertions alone. Five z3test regression files now export and verify in Lean.

Background

Before this PR the pipeline certified propositional inputs, uninterpreted functions with equality, and linear arithmetic over Int and Real. Those are the fragments that milestones 2 and 3 cover. Yet most z3test regression files were turned away at the frontend for a set-option line or a get-model query. Widening the frontend serves the regression methodology that the plan treats as its top priority and that gates milestones 3 to 5.

What changed

Exporter frontend

  • Harmless options are skipped. You can now export a file that sets produce-models, a timeout, a random seed, or a search setting.
  • Any tactic is accepted as the one query. A check-sat-using with a tactic counts as the check, since the exporter runs its own solver anyway.
  • Output queries no longer block export. You can leave get-model or get-unsat-core after the check, and echo or get-info anywhere.
  • Dangerous options are still rejected, now with a reason. Options that change how the input is read, such as numeral-as-real, fail with a message saying so. Everything not on the allowlist is rejected too, so an omission can only reject more.

Think of a letter with a stamp and a note saying "please reply by fax". None of that changes what the letter says, and the exporter now reads past the envelope.

Tests and documentation

  • Five z3test regressions are kept verbatim as test inputs and run through both the legacy proof object and the clause log. The README and the plan document list which options are ignored and which are refused.

Worked example

This input was built from the shapes in the PR's new test fixture. It has two skipped options, two named assertions, a tactic in the check, and an unsat-core query. The assertions say that x is below 1 and above 2 at once.

(a) The input

(set-logic QF_LRA)
(set-option :auto-config true)
(set-option :produce-unsat-cores true)
(declare-const x Real)
(assert (! (< x 1.0) :named low))
(assert (! (> x 2.0) :named high))
(check-sat-using (par-or smt smt))
(get-unsat-core)
(exit)

(b) Before

The exporter from the parent commit stopped at the first option line and exited with status 2.

The current exporter produced a certificate for the qf_lra fragment, and the reconstructor wrote the Lean file below. The Lean check accepted it with "Lean checks passed."

This theory lemma is the arithmetic heart of the proof: for any rational x, either 1 ≤ x or 2 ≥ x.

private theorem th_lemma_18 (_atoms : Nat -> Prop) (_vars : Nat -> Rat)
    : (formula_17 _atoms _vars) := by
  unfold formula_17 formula_12 formula_6 term_3 term_1 term_0
  grind (splits := 64)

The theorem takes the two parsed assertions as hypotheses and derives False. The named labels and the ignored front matter are not part of the statement.

Review

The reviewer requested changes with one finding, rated major, and nothing else.

Major: one allowlisted option changed how the input is read

The reviewer checked Z3's source for every option on the allowlist and found that smtlib2_compliant did not belong there. With it set, Z3's scanner reads -1.0 as a symbol instead of a negative numeral, and Int to Real coercions are off. The reviewer wrote a six-line file that declares a constant literally named |-1.0| and sets that option. Z3, honouring the option, answered sat. Both exporters ignored the option, read -1.0 as a number, and emitted an unsat certificate that Lean checked. That certificate was about a different reading of the file than Z3's, which is exactly what the allowlist was meant to prevent.

The integrator reproduced the divergence and moved the option to the rejected group. They also added Z3's int-real-coercions option, which uses the same handler. The reviewer's file joined the rejection test, and the corpus counts dropped by one. It mattered because soundness here means the theorem is about the input as Z3 reads it.

Two reviewer suggestions were not taken. The output-channel options stay rejected, because a file redirect should not be dropped silently, and moving the corpus scan script into the repository is a follow-up.

Risks and open questions

  • The allowlist is a judgment. The review caught one wrong entry, and the integrator re-checked the rest against Z3's source. A future wrong entry would repeat the same failure.
  • Tactics are not validated. A malformed tactic that Z3 would refuse is accepted. The result is still Lean-checked.
  • Error messages changed. Setting produce-proofs to false now fails with the generic message. The z3test harness checks status only and still passes.

Glossary

assertion
A formula the input declares to be true, written (assert ...). The refutation shows that all assertions together cannot hold.
Boolean
Having the sort Bool, that is, being either true or false.
clause log
A record of the clauses the solver learned while searching, used as proof evidence for arithmetic inputs.
coercion
An automatic conversion of a value from one sort to another, such as reading the Int 1 as the Real 1.0.
Farkas lemma
A result from linear arithmetic: if a set of linear inequalities has no solution, some weighted sum of them gives an obvious contradiction such as 0 < 0. Arithmetic theory lemmas are usually justified this way.
fragment
A restricted class of formulas, such as propositional logic or linear real arithmetic (QF_LRA). The checker supports one fragment at a time.
front matter
The commands in an SMT-LIB file that configure the solver or ask for output, as opposed to the declarations and assertions that define the problem.
hypothesis
An assumption a theorem is allowed to use. Here each parsed assertion becomes one hypothesis of the Lean theorem.
linear arithmetic
Arithmetic with addition and multiplication by constants only, such as 2x + 3y ≤ 7, over integers or reals.
model
An assignment of values to the variables that makes every assertion true. A model exists only when the problem is satisfiable.
named assertion
An assertion with a label, written (assert (! t :named a)). The label is used when reporting an unsat core and does not change the formula.
numeral
A literal number in the input, such as 1 or 2.0.
option
A solver setting given with (set-option :name value), such as a timeout or a request to produce models.
proof certificate
The JSON file the exporter writes. It holds the input verbatim, the parsed assertions, and the proof evidence that the reconstructor turns into Lean.
propositional
Built only from Boolean variables and the connectives and, or, not, and so on, with no arithmetic or functions.
query
A command that asks the solver for a result, such as check-sat, get-model, or get-unsat-core.
refutation
A proof that a set of assertions leads to False, that is, that they cannot all be true at once.
scanner
The part of a parser that cuts the input text into tokens such as numbers, symbols, and parentheses.
SMT-LIB
The standard text format for solver inputs. Its commands are written in parentheses, like (declare-const x Real).
sort
The type of a value, such as Int, Real, or Bool.
soundness
The property that a certified result is actually true of the input. Here it means the Lean theorem is about the input exactly as Z3 reads it.
tactic
A recipe that tells a solver or proof assistant how to attack a problem, such as "try these five strategies in parallel". In SMT-LIB a tactic is passed with check-sat-using.
theory lemma
A fact that is true by the rules of a theory such as arithmetic, independent of the input. Example: for every rational x, either 1 ≤ x or 2 ≥ x. See also Farkas lemma.
uninterpreted function
A function symbol with a known signature but no fixed meaning, such as f : Int → Int. The only rule is that equal inputs give equal outputs.
unsat core
A subset of the named assertions that is already unsatisfiable on its own, reported by get-unsat-core.
