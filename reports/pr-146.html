Keep the literals of a wide unit resolution in place, not case-split

Pull request levnach/z3 #146 · state OPEN · opened 2026-11-17T19:09:28Z · loop iteration 145

This pull request is open and not merged. Its change commit is 5135dacdc.

In one paragraph

A refutation from Z3 often contains a unit resolution that removes one literal from a long clause and keeps all the others. The Lean exporter used to write that step as one case split per kept literal. Each split rebuilt the literal's position in the conclusion, so the text grew with the square of the clause width. At 400 kept literals, Lean ran out of heartbeats on that one step and rejected the whole file. Now, when more than eight literals are kept in the same order, the exporter writes a short term that moves no literal. Its size is linear in the clause. The same 400-literal input now gets a Lean certificate. The kernel still checks every step, and no axiom is added.

Background

Before this PR, every sample file that exports verified in Lean, except one failure and five files never checked for time. But the pipeline still had costs that grew faster than the input. One of them was the unit resolution described above. It appears when Z3 logs a clause it has simplified under a unit and ties it back to its source. Wide clauses of that kind were rejected by Lean on generated inputs with a few hundred literals, even though the step is trivial. The resolution rule belongs to the Boolean slice of milestone 2 in the plan. The inputs it helps here are linear-arithmetic files, part of milestone 3. The change is about scale, not about new kinds of input.

What changed

  • A unit resolution that keeps more than eight literals of its clause, in order, now gives Lean a term whose size is linear in the clause.
  • Generated inputs with 400 and 800 kept literals, which Lean rejected before, now verify.
  • Cuts after a kept literal use two new small helper theorems, resolve_first and resolve_rest, which Lean proves without axioms.
  • Narrower or reordered resolutions are written exactly as before, so 146 of 152 sample texts are byte-for-byte unchanged.
  • New tests pin the exact terms, check them in Lean, and check that seven tampered versions are rejected.
  • The plan document gains a section with the measurements, and the examples README describes the new form.

An analogy: the old exporter copied a long list by taking each item out and putting it back where it was, one item at a time. The new exporter crosses out the removed items and leaves the rest of the list where it is.

Worked example

This change is about size, so a tiny input is accepted both before and after. The example below is ten bounds from the PR's own test family. It shows the shape of the change. The rejection under "Before" comes from the 400-bound member of the same family. It was produced by the test generator wide_clause_under_a_unit(400). All outputs below come from real runs made for this page.

(a) The input

(set-logic QF_LRA)
(declare-const b Bool)
(declare-const x0 Real) (declare-const x1 Real) (declare-const x2 Real) (declare-const x3 Real) (declare-const x4 Real)
(declare-const x5 Real) (declare-const x6 Real) (declare-const x7 Real) (declare-const x8 Real) (declare-const x9 Real)

(check-sat)

Every xi is below 1, yet the clause says some xi is at least 1, so the assertion is unsatisfiable.

(b) Before

On the ten-bound input, the base exporter wrote the step as a chain of case splits, and Lean accepted it. The step's line was 1,048 characters long:

  let _step_41 : (formula_40 _atoms _vars) :=
    (Or.elim (_step_39.neg_resolve_left _step_35) (fun _literal => (Or.inl _literal)) (fun _tail => (Or.elim _tail (fun _literal => (Or.inr (Or.inl _literal))) (fun _tail => (Or.elim _tail (fun _literal => (Or.inr (Or.inr (Or.inl _literal)))) ...

Each kept literal gets one more Or.inr than the one before it, which is where the square comes from. On the 400-bound input of the same family, the base pipeline failed in Lean:

family400.lean:9393:0: error: (deterministic) timeout at `isDefEq`, maximum number of heartbeats (200000) has been reached
...
Lean checking failed; no proof was published.

(c) After

The current exporter on the ten-bound input. First, the clause and the conclusion of the step:

def formula_37 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := (Not (formula_34 _atoms _vars))
def formula_38 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := (Or (formula_37 _atoms _vars) (Or (formula_4 _atoms _vars) ... (formula_22 _atoms _vars)))))))))))
def formula_40 (_atoms : Nat -> Prop) (_vars : Nat -> Rat) : Prop := (Or (formula_4 _atoms _vars) (Or (formula_6 _atoms _vars) ... (formula_22 _atoms _vars))))))))))

formula_34 is the whole assertion. formula_38 is the clause "the assertion is false, or one of the ten bounds holds". formula_40 is the same clause without its first literal.

theorem unsat (_atoms : Nat -> Prop) (_vars : Nat -> Rat)
    (_h0 : (formula_34 _atoms _vars))
    : False :=

The theorem says that the assertion implies False.

  let _step_39 : (formula_38 _atoms _vars) :=
    (th_lemma_39 _atoms _vars)
  let _step_41 :=
    (_step_39.neg_resolve_left _step_35)
  ...

The new step cuts the first literal with the assertion itself and keeps the ten bounds where they stand, in one short line.

The Lean check accepted this file: Lean checks passed. On the 400-bound input, the current exporter also finished with "Lean checked the refutation". Z3 puts the cut literal in front here, so this run does not use the two helper theorems. They are written only when a cut follows a kept literal, and only the PR's hand-made test certificates do that. Their text, from the exporter's source, is: 

private theorem resolve_first {p q r : Prop} (n : Not p) (f : q -> r) : p \/ q -> r :=
  fun h => f (h.resolve_left n)

private theorem resolve_rest {p q : Prop} (n : Not q) : p \/ q -> p :=
  fun h => h.resolve_right n

The first cuts the leading literal and passes the rest on. The second cuts everything after the leading literal.

Review

The reviewer approved, with no blockers and no major findings.

  • Minor. The reviewer noticed that the helper theorems were only reached by hand-made certificates. Nothing checked them in a large text that is split into a chain of modules. That split changes how private declarations are handled, so a helper could end up out of reach. The fix is a new test that splits a 40-literal certificate using both helpers into four or more modules. It checks that the helpers come first and that Lean accepts the chain without axioms. It still remains true that no Z3-produced certificate uses this form.
  • Nit. The reviewer could not reconcile two counts of rewritten resolutions in the plan document. They came from different sets of texts. The paragraph now names the set behind each count.
  • Nit. The decision to write the helpers searched the text for their names, which is fragile. It now matches only an application of a helper. A dedicated flag was not added. The reason given is that a wrong decision either adds an unused theorem or makes Lean reject the file. It can never cause a wrong proof to be accepted.

Risks and open questions

  • Six sample texts change. All were checked in Lean after the change and verify.
  • A resolution that is its clause's tail is now bound without a stated type. Lean checks it where it is used, as it already does for one-literal resolutions.
  • The helper form is tested only on hand-made certificates. No certificate from Z3 has yet shown a cut after a kept literal.
  • The limit of eight kept literals is a chosen constant, not a measured optimum.
  • Lean's time on the family is still faster-growing than linear: 408 s at 1,600 bounds. Inputs of this shape with a few thousand literals still do not certify.

What comes next

  • The remaining cost on the family is the cnf lemma that links each literal of the simplified clause to the assertion. It is the first candidate in the backlog.
  • Resolutions that keep two to eight literals, and wide reordered or factored conclusions, still use case splits. Both are in the backlog.

Glossary

axiom
A statement Lean accepts without proof. The certificates here should depend on none beyond Lean's core.
Boolean
A value that is either true or false, written Bool in SMT-LIB.
case split
A proof that handles each alternative of a disjunction separately. In Lean it is written with Or.elim.
chain of modules
A large Lean text cut into several files, each importing the one before it, so Lean can check them in turn.
clause
A disjunction of literals: it holds if at least one literal holds. Example: (or b (<= 1.0 x0)).
cnf lemma
A clause that follows from a formula's Boolean structure alone, used to turn the formula into clauses.
heartbeat
Lean's unit of work. A declaration that uses more than its limit, by default 200,000, is rejected.
kernel
The small trusted core of Lean that checks every proof term.
linear growth
Size that doubles when the input doubles.
literal
An atom or the negation of an atom. Example: b, (not b), or (<= 1.0 x0).
quadratic growth
Size that grows with the square of the input: doubling the input makes it about four times bigger.
refutation
A proof that a set of assertions leads to False.
slow tier
The tests that take long and run only when asked, here with Z3_LEAN_SLOW_TESTS=1. The rest form the fast tier.
theorem
A named statement together with its proof, which Lean checks once and can then reuse.
unit
A clause with exactly one literal, which is therefore known to hold. Example: (not b).
unit resolution
The step that removes from a clause every literal whose negation is a unit. From (or b c d) and (not b) it gives (or c d).
